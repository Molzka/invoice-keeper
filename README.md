# Invoice Keeper

Приложение для регулярных расходов команды: аренды, подписок, серверов и других платежей. Администратор добавляет расходы, участники отмечают оплату, а бот напоминает о сроках в Telegram.

В Docker можно запустить интерфейс с демонстрационными данными и локальную PostgreSQL. Backend авторизации запускается отдельно по инструкции ниже. Подключение API и общий запуск бота в Docker будут добавлены отдельно.

## Локальный запуск

Нужен запущенный Docker Desktop с Linux containers и Docker Compose v2. Команды выполняются в корне репозитория.

1. Если `.env` ещё нет, создайте его: `Copy-Item .env.example .env` в PowerShell или `cp .env.example .env` в Linux / macOS.
2. Откройте `.env` и заполните `POSTGRES_PASSWORD` своим длинным паролем.
3. Проверьте настройки, соберите интерфейс и запустите сервисы:

```sh
docker compose config --quiet
docker compose up -d --build --wait --wait-timeout 90
docker compose ps
```

Дождитесь статуса `healthy` у `frontend` и `postgres`. Откройте [localhost:8080](http://localhost:8080), выберите демонстрационную роль и нажмите «Войти». База доступна на `127.0.0.1:5432`, имя базы и пользователя по умолчанию — `invoice_keeper`. Первая сборка скачивает образы и зависимости и может занять несколько минут.

Для остановки выполните `docker compose stop`, для повторного запуска — ту же команду `up`. Данные хранятся в отдельном томе и сохраняются после обычного `docker compose down`. **Флаг `down -v` удаляет данные.**

### Фронтенд в Docker

Для просмотра интерфейса достаточно одного сервиса; `.env` с заполненным `POSTGRES_PASSWORD` всё равно нужен для проверки общего Compose-файла:

```sh
docker compose up -d --build --no-deps --wait --wait-timeout 60 frontend
docker compose logs --tail=100 frontend
```

В этом режиме PostgreSQL не запускается. Данные демонстрации хранятся в памяти вкладки и сбрасываются при перезагрузке страницы; в базу они не записываются. Демонстрационный вход не проверяет настоящие серверные сессии. Подробности экранов и локальной разработки — в [README фронтенда](frontend/README.md).

Docker сначала устанавливает зависимости из `package-lock.json`, проверяет TypeScript и ESLint и собирает React через Vite. Затем готовые файлы копируются в небольшой образ Nginx. В запущенном контейнере нет Node.js и исходников; он работает от обычного пользователя с файловой системой только для чтения. Node.js и npm на компьютере для такого запуска не нужны.

После изменений в коде снова выполните команду с `--build`. Если порт занят, укажите, например, `FRONTEND_PORT=8081` в корневом `.env`, повторите запуск и откройте `http://localhost:8081`. Порты обоих сервисов доступны только с вашего компьютера.

Образ пока собирается с `VITE_API_MODE=mock`. Файлы `.env` фронтенда в сборку не попадают. Переменные `VITE_*` встраиваются в JavaScript при сборке: изменение окружения уже запущенного контейнера не переключит его на API. Когда бэкенд будет готов, отдельно подключим его к Compose, настроим прокси `/api` и соберём интерфейс в режиме `real`. Сейчас `/api` возвращает `503 API_NOT_AVAILABLE`; это ожидаемый ответ, демонстрация работает без него.

Проверить раздачу готовой сборки можно с Python 3.10+:

```sh
python scripts/check_frontend.py http://127.0.0.1:8080
```

Скрипт проверяет HTML, JS/CSS, изображения, кеширование, `/healthz` и ответы на отсутствующие или закрытые пути. Он проверяет сервер по HTTP; работу кнопок и форм проверяем в браузере. При ошибке запуска смотрите `docker compose ps -a` и логи `frontend`. Если изменён порт, замените его и в команде проверки.

## Резервная копия и восстановление

Нужны Python 3.10+ и запущенная база (`docker compose up -d --wait postgres`). Скрипт использует `pg_dump` и `pg_restore` из контейнера; устанавливать PostgreSQL на компьютер не нужно. Команды ниже выполняются из корня проекта; в Linux / macOS вместо `python` может понадобиться `python3`.

Создать копию рабочей БД:

```sh
python scripts/db_backup.py backup
```

Команда выведет путь к новому файлу в `backups/`. В имени указано время UTC; каждый запуск создаёт отдельный архив. Схема и данные сохраняются вместе, при ошибке незавершённый файл удаляется. Папка `backups/` и файлы `*.dump` исключены из Git.

Восстановить архив в **новую отдельную БД**, заменив путь на полученный после копирования:

```sh
python scripts/db_backup.py restore backups/postgres_YYYYMMDDTHHMMSSZ_example.dump invoice_keeper_restore
docker compose exec postgres sh -c 'psql -U "$POSTGRES_USER" -d invoice_keeper_restore'
```

В `psql` команда `\dt` покажет таблицы, `\q` закроет подключение. Имя новой БД: до 63 символов, латинские строчные буквы, цифры и `_`, первый символ — буква. Если БД с таким именем уже существует, скрипт остановится. Для следующей проверки укажите другое имя, например `invoice_keeper_restore_2`.

Рабочая база и `.env` остаются прежними. Восстановление идёт одной транзакцией; при ошибке новая БД остаётся для проверки, скрипт её автоматически не удаляет. Ошибка `already exists` означает занятое имя, `service "postgres" is not running` — что сначала нужно запустить Compose.

Это копия одной БД, без серверных ролей и их паролей. Владельцем восстановленных объектов будет пользователь из настроек контейнера. Архивы содержат данные приложения: храните их приватно и восстанавливайте только свои или доверенные файлы. Том Docker и архив на том же диске не защитят от поломки диска — важную копию сохраните отдельно.

## Проверка Docker

GitHub Actions запускает две независимые проверки в каждом PR и после обновления `main`:

- **Frontend / Compose** — типы, lint, production-сборка, запуск Nginx и HTTP-проверка. Дополнительно проверяются запуск без root, файловая система только для чтения и отсутствие Node.js, исходников и `.env` в каталоге сайта.
- **PostgreSQL / Compose** — запуск PostgreSQL, вход с паролем, сохранение записи после пересоздания контейнера, резервное копирование и восстановление в новую БД.

Каждая проверка использует собственный временный Compose-проект и удаляет его после завершения; проверка базы также удаляет свой том. Рабочий `.env` и локальная база для CI не нужны. Результаты видны во вкладке **Checks** в PR; при ошибке откройте соответствующую проверку — в ней будут шаг с ошибкой и логи контейнера.

## Что делаем

- Общий список платежей со сроками, статусами и историей по месяцам.
- Подтверждение оплаты, отмена отметки и исправление фактической даты.
- Напоминания в Telegram за три дня до срока.
- Итоги отдельно в рублях, долларах и евро, без конвертации.
- Две роли: администратор управляет платежами и пользователями, остальные работают с оплатой.

## Локальный запуск backend

Для разработки backend необходимы Python 3.12+, менеджер зависимостей [uv](https://docs.astral.sh/uv/) и PostgreSQL. Локально используем PostgreSQL 18 в Docker.

Перейдите в каталог backend:

```powershell
cd backend
```

Установите зависимости из зафиксированного `uv.lock`:

```powershell
uv sync --locked
```

Создайте локальный файл окружения, если его ещё нет (PowerShell):

```powershell
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
```

Файл `backend/.env` содержит локальные настройки и секреты и не должен попадать в Git. В `DATABASE_URL` укажите фактические имя пользователя, пароль, порт и базу из корневого `.env` для Compose. Шаблон использует `127.0.0.1:5432`, пользователя и базу `invoice_keeper`; `replace_me` нужно заменить. Специальные символы пароля в URL должны быть percent-encoded. Корневой `.env` настраивает Docker, а `backend/.env` — Python-приложение.

PostgreSQL запускается из корня проекта после настройки корневого `.env`:

```powershell
docker compose up -d --wait postgres
```

Если раньше была создана отдельная база `invoice-keeper-db-dev` на порту `55432`, её можно продолжать использовать: запустите `docker start invoice-keeper-db-dev` и оставьте соответствующий URL в `backend/.env`. Не создавайте новую базу вместо существующей без переноса нужных данных. Команды `uv` ниже выполняются из каталога `backend`.

Примените миграции и создайте первого администратора:

```powershell
uv run --locked alembic upgrade head
uv run --locked python -m app.cli create-admin --username admin
```

Команда запросит пароль и подтверждение без отображения ввода. Пароль должен содержать 8–128 символов. Повторный вызов с занятым логином завершится ошибкой и сохранит существующий аккаунт. Для существующей базы повторно создавать администратора не нужно. Миграция `0002` переводит роль `member` в `user`, сохраняя пользователей, хеши паролей, сессии и ранее введённые имена.

Запустите сервер:

```powershell
uv run --locked uvicorn app.main:app --reload --no-proxy-headers
```

После запуска доступны:

- Swagger UI: http://127.0.0.1:8000/api/v1/docs
- OpenAPI JSON: http://127.0.0.1:8000/api/v1/openapi.json
- Проверка работы API: http://127.0.0.1:8000/api/v1/health
- Проверка подключения к БД: http://127.0.0.1:8000/api/v1/ready

Остановить сервер можно сочетанием `Ctrl+C`.

Для локального запуска используем `--no-proxy-headers`, чтобы IP-лимит входа не зависел от присланного клиентом `X-Forwarded-For`. При размещении за reverse proxy необходимо отдельно настроить доверенные адреса прокси. Общий Docker Compose для API, frontend и фонового обработчика будет добавлен отдельно.

## Авторизация и пользователи

Все маршруты начинаются с `/api/v1`. Публичной регистрации нет: первый администратор создаётся локальной CLI-командой, следующих пользователей добавляет администратор.

| Метод и маршрут | Результат |
|---|---|
| `POST /auth/login` | JSON `username`, `password`; ответ `user` и `csrf_token`, сессия в HttpOnly cookie |
| `GET /auth/me` | Текущий пользователь и CSRF-токен; без действующей сессии — 401 |
| `POST /auth/logout` | Удаление текущей сессии и cookie; ответ 204 |
| `GET /users?limit=50&offset=0` | Только администратор; `items`, `total`, `limit`, `offset` |
| `POST /users` | Только администратор; создание пользователя, ответ 201 |
| `PATCH /users/{user_id}` | Только администратор; изменение логина и/или пароля обычного пользователя |
| `DELETE /users/{user_id}` | Только администратор; удаление обычного пользователя и отзыв всех его сессий, ответ 204 |

Контракт согласован с [описанием API frontend](frontend/docs/api-contract.md). Создание принимает только `username` и `password`, роль назначается сервером как `user`. Логин содержит 3–64 символа `a-z`, `0-9`, `_`, `.`, `-`; пробелы по краям убираются, буквы приводятся к нижнему регистру. Пароль — 8–128 символов, без обрезки или нормализации. PATCH принимает `username` и/или `password`; пустой PATCH, явный `null`, `role`, `display_name`, `is_active` и прочие неизвестные поля отклоняются с 422. Ответ пользователя содержит только `id`, `username`, `role`, `created_at`.

В `/users` возвращаются только обычные пользователи, включая `total` и пагинацию. Администратор доступен через `/auth/me`; изменение и удаление любого администратора через `/users/{id}` возвращает `403 ADMIN_ACCOUNT_PROTECTED`. Занятый логин даёт `409 USERNAME_TAKEN` с ошибкой поля `username`.

Все POST, PATCH и DELETE, включая login, требуют разрешённый заголовок `Origin`. Отсутствующий Origin, значение `null` или посторонний адрес дают `403 ORIGIN_NOT_ALLOWED`; `Referer` не заменяет Origin. Для logout, создания, изменения и удаления пользователя также передавайте `X-CSRF-Token` из последнего ответа login/me. Неверный CSRF-токен даёт `403 CSRF_FAILED`. Запросы с телом используют `Content-Type: application/json`. В Swagger сначала выполните login, затем вставьте полученный `csrf_token` в поле заголовка нужного запроса. Cookie браузер передаст автоматически; при ручной проверке через HTTP-клиент укажите Origin явно.

Frontend делает запросы с `credentials: "include"`. CSRF-токен можно держать в памяти; после перезагрузки страницы восстановить через `/auth/me`. Сессионный токен находится в HttpOnly cookie. Используйте один и тот же hostname для frontend и API: например, `localhost:5173` и `localhost:8000`.

Разрешённые адреса frontend/API задаются JSON-массивом `ALLOWED_ORIGINS` в `.env`. Cookie `session_id` имеет `SameSite=Lax`, фиксированный срок семь дней по умолчанию и проверяется сервером. Пароли хранятся как Argon2-хеши, сессионные токены — как SHA-256-хеши. При смене логина или пароля и удалении пользователя отзываются все его сессии. После обновления со старой версии cookie потребуется войти заново.

Ошибки имеют оболочку `error` с `code`, `message`, `details`. Каждый элемент `details` содержит `{field, code, message}`; для тела это, например, `password`, для query — `query.limit`, для пути — `path.user_id`. Исходные значения паролей в ошибки не копируются. Битый JSON возвращает `400 INVALID_JSON`, неизвестные query-параметры на всех маршрутах API — `422 VALIDATION_ERROR`.

По умолчанию за 15 минут допускаются 10 попыток входа на логин и 60 на IP, включая успешные. При превышении API возвращает 429 с `Retry-After`. Счётчики общие для всех процессов и сохраняются в PostgreSQL.

Для HTTPS-окружения задайте `APP_ENV=production`, `SESSION_COOKIE_SECURE=true` и точные HTTPS-адреса в `ALLOWED_ORIGINS`. Приложение проверяет эти условия при загрузке настроек. Срок сессии и лимиты задаются переменными из `.env.example`.

Очистка истёкших сессий и устаревших счётчиков входа:

```powershell
uv run --locked python -m app.cli cleanup-auth
```

## Проверка backend

Из каталога `backend`:

```powershell
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked python scripts/test_postgres.py
```

Тестовый скрипт подключается к серверу из `DATABASE_URL`, создаёт временную базу с уникальным именем, применяет миграции, запускает тесты и проверяет соответствие моделей схеме. Затем проверяет откат и повторное применение миграции и удаляет созданную тестовую базу. Пользователю PostgreSQL для этого нужно право `CREATEDB`; пользователь официального локального Docker-образа имеет его по умолчанию.

Если права создавать базы нет, подготовьте отдельную одноразовую базу с суффиксом `_test`, укажите её URL в переменной окружения `TEST_DATABASE_URL` и выполните `uv run --locked pytest -q`. Тесты очищают данные только в выбранной тестовой базе. Без `TEST_DATABASE_URL` интеграционные проверки завершаются ошибкой настройки, а не пропускаются. Скрипт выше задаёт эту переменную автоматически. В тестах также проверяется переход с `0001` на `0002` с существующими пользователями и сессиями.

## Правила платежей

Каждый месяц — отдельный период со своим сроком и фактической датой оплаты. Долг за прошлый месяц не мешает созданию следующего периода. Прекращение регулярного платежа останавливает новые периоды и напоминания, но сохраняет уже созданные обязательства и историю.

Все календарные расчёты идут по московскому времени (`Europe/Moscow`). Если нужного числа нет, используем последний день месяца, сохраняя исходное число: 31 января → 28/29 февраля → 31 марта. Просрочка начинается на следующий день после срока; оплата в день срока считается своевременной.

Напоминание становится готово к отправке в 00:00 МСК за три календарных дня до срока. Если платёж добавлен позже, задание создаётся сразу. Оплаченные периоды и прекращённые платежи не напоминают о себе; подтверждённые отправки не повторяются.

Сводка по умолчанию показывает текущий месяц по **срокам платежей**: всего, оплачено, не оплачено и из них просрочено. Просроченное уже входит в неоплаченное. RUB, USD и EUR считаются отдельно.

В API используем JSON с полями `snake_case`, UUID и даты `YYYY-MM-DD`. Суммы передаём строками с двумя знаками (`"45000.00"`), считаем через `Decimal` и храним в `NUMERIC(14,2)`. Календарные даты не переводим в UTC; техническое время передаём в UTC с `Z`. Ошибки имеют общий объект `error` с полями `code`, `message`, `details`.

`main` — общая согласованная версия. Для каждой небольшой задачи создаём отдельную ветку; постоянных личных веток не ведём. Изменения попадают в `main` через Pull Request (PR) — запрос на просмотр и объединение кода. Перед объединением изменения смотрит хотя бы один коллега.

```bash
cd invoice-keeper
```

Перед новой задачей обновляем `main` и создаём ветку. Во всех командах ниже замените `feat/auth` на название своей задачи; для следующей задачи выберите новое имя ветки.

```bash
git switch main
git pull --ff-only
git switch -c feat/auth
```

Когда задача готова, проверяем изменения и отправляем свою ветку. Перед `git add .` убедитесь, что в списке только файлы этой задачи и нет секретов.

```bash
git status
git diff
git add .
git diff --cached
git commit -m "Добавить вход и серверные сессии"
git push -u origin feat/auth
```

На GitHub открываем PR из своей ветки в `main`, кратко описываем результат и способ проверки. После просмотра объединяем через **Squash and merge** и удаляем завершённую ветку. Следующую задачу начинаем с обновлённой `main`.

Если за время работы коллеги обновили `main`, сначала сохраните свои изменения коммитом, затем выполните в своей ветке `git fetch origin` и `git merge origin/main`. Конфликты в общих файлах разбирайте с их автором; после объединения повторите проверки и `git push`.

Не отправляем рабочие изменения напрямую в `main` и не переписываем её историю. Общие модели, API и настройки обсуждаем до изменения; небольшие PR объединяем регулярно, чтобы не копить конфликты.

## Зависимости и база данных

- Храним `pyproject.toml` вместе с `uv.lock`, а `package.json` — с `package-lock.json`. После появления этих файлов устанавливаем зависимости через `uv sync --locked` и `npm ci`.
- У каждого своя локальная БД. Изменения таблиц передаём миграциями Alembic вместе с моделями; результат автогенерации проверяем вручную.
- Цепочку миграций координирует разработчик основы бэкенда. Применённые коллегами миграции не переписываем; при двух конечных ревизиях согласуем их объединение.
- В общем окружении миграции выполняются одним процессом до запуска новой версии API и фонового обработчика.
- Пароли, токены и рабочий `.env` в Git не добавляем. `.env.example` содержит только настройки для примера и пустое поле пароля.

Перед PR проверяем сборку, типы и работу изменённых сценариев. Первая общая цель — пройти путь «вход → создание платежа → список → отметка оплаты».
