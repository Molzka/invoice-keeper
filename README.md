# Invoice Keeper

Приложение для регулярных расходов команды: аренды, подписок, серверов и других платежей. Администратор добавляет расходы, участники отмечают оплату, а бот напоминает о сроках в Telegram.

В Docker запускаются интерфейс, API, PostgreSQL, Telegram-бот и обработчик напоминаний `worker`. Интерфейс по умолчанию работает с настоящим API и сохраняет данные в PostgreSQL. API доступно через тот же адрес, что и сайт, по пути `/api/v1`. Для отдельного показа без своих данных можно явно выбрать `FRONTEND_API_MODE=mock`.

## Локальный запуск

Нужен запущенный Docker Desktop с Linux containers и Docker Compose v2. Команды выполняются в корне репозитория.

1. Если `.env` ещё нет, создайте его: `Copy-Item .env.example .env` в PowerShell или `cp .env.example .env` в Linux / macOS.
2. Откройте `.env`, заполните `POSTGRES_PASSWORD` своим длинным паролем, `ADMIN_USERNAME` и `ADMIN_PASSWORD` (8–128 символов) для первого администратора, а также `BOT_TOKEN` токеном от `@BotFather`. Если ID чата уже известен, укажите `CHAT_ID`.
3. Остановите другие запуски этого же бота, включая `python bot.py` у коллеги: один токен допускает только один процесс polling.
4. Если `CHAT_ID` ещё неизвестен, запустите только бота: `docker compose up -d --build --no-deps bot`. Откройте нужный чат с ним или добавьте его в группу, вызовите `/id` (в группе можно `/id@имя_бота`) и запишите ответ в `CHAT_ID`. Команда показывает ID, но сама `.env` не меняет. До заполнения этой настройки worker запускать не нужно.
5. Проверьте настройки, соберите приложения, запустите базу и примените миграции:

```sh
docker compose config --quiet
docker compose build backend worker frontend
docker compose up -d --wait --wait-timeout 90 postgres
docker compose run --rm backend alembic upgrade head
```

6. Только для новой базы создайте администратора: `docker compose run --rm backend python -m app.cli create-admin`. При занятом логине команда завершится ошибкой и сохранит существующий аккаунт и пароль. При повторном запуске проекта этот шаг пропустите.
7. После успешных миграций и заполнения `CHAT_ID` запустите остальные сервисы:

```sh
docker compose up -d --build --wait --wait-timeout 90
docker compose ps
```

Дождитесь статуса `healthy` у `frontend`, `backend` и `postgres`, `running` у `bot` и `worker`. Откройте [localhost:8080](http://localhost:8080) и войдите с логином и паролем созданного администратора. API можно проверить в [Swagger](http://localhost:8080/api/v1/docs), его связь с БД — по адресу [ready](http://localhost:8080/api/v1/ready). База доступна на `127.0.0.1:5432`, имя базы и пользователя по умолчанию — `invoice_keeper`. Первая сборка скачивает образы и зависимости и может занять несколько минут. Ответ на `/help` подтверждает приём команд ботом; статус `running` не подтверждает доставку напоминаний — результат смотрите в очереди и целевом чате.

Для остановки выполните `docker compose stop`, для повторного запуска — ту же команду `up`. Данные хранятся в отдельном томе и сохраняются после обычного `docker compose down`. **Флаг `down -v` удаляет данные.**

### Backend в Docker

Все команды этого раздела выполняются из корня проекта. Python и uv на компьютере не нужны. Настройки контейнера берутся из корневого `.env`; файл `backend/.env` используется только при запуске Python без Docker. Рабочие `.env` в образы не копируются.

Бэкенд подключается к `postgres:5432` внутри сети Docker. Адрес `DATABASE_URL` собирается из `POSTGRES_DB`, `POSTGRES_USER` и `POSTGRES_PASSWORD`, включая корректное экранирование специальных символов пароля. `POSTGRES_PORT` меняет только порт доступа с компьютера. Если база уже существует, используйте её прежний пароль: изменение `.env` не меняет пароль в сохранённом томе.

Обновление API и worker с миграциями:

```sh
docker compose build backend worker
docker compose stop backend worker
docker compose run --rm backend alembic upgrade head
docker compose up -d --wait --wait-timeout 90 backend worker frontend
```

Выполняйте команды по очереди. API и worker используют общую схему, поэтому оба останавливаются перед миграциями. Если миграция завершилась ошибкой, исправьте её причину до запуска приложений. Миграции запускает один человек/процесс; сервисы не применяют их автоматически. `alembic current` показывает текущую ревизию, `alembic check` проверяет соответствие моделей схеме: запускайте их тем же способом через `docker compose run --rm backend`.

Администратор создаётся отдельной командой при первом запуске. После создания можно убрать `ADMIN_PASSWORD` из корневого `.env` и пересоздать API: `docker compose up -d --no-deps --force-recreate backend`. Это уберёт первоначальный пароль из окружения контейнера, но не изменит сохранённый хеш. Для очистки истёкших сессий: `docker compose run --rm backend python -m app.cli cleanup-auth`.

Nginx пересылает `/api/...` в `backend:8000`, сохраняя путь, cookie, Origin и CSRF-заголовок. Порт API не опубликован на компьютере. Nginx заново разрешает имя контейнера после его пересоздания; при недоступном API возвращает JSON с HTTP 503, а сайт продолжает открываться. API доверяет заголовкам прокси во внутренней сети; Nginx перезаписывает адрес клиента и протокол. Не публикуйте порт 8000 напрямую с этими настройками. Описание поведения: [proxy_pass в Nginx](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_pass).

По умолчанию разрешены Origin `http://localhost:<FRONTEND_PORT>` и `http://127.0.0.1:<FRONTEND_PORT>`. Для другого адреса задайте JSON-массив `ALLOWED_ORIGINS` в корневом `.env`. Используйте один адрес сайта во время входа и дальнейшей работы. После изменения настроек пересоздайте `backend`; обычный `restart` не перечитывает `.env`.

Режим `FRONTEND_API_MODE=real` включён по умолчанию. Если в старом `.env` осталось `mock`, замените его на `real` и выполните `docker compose up -d --build --no-deps frontend`. API требует актуального образа backend и миграций до head (`0006`); порядок обновления приведён выше. Для демонстрации без API явно задайте `FRONTEND_API_MODE=mock`. Изменение режима требует пересборки фронтенда.

Если запуск не удался:

- `docker compose ps -a` и `docker compose logs --tail=100 backend` покажут состояние API.
- HTTP 503 на `/api/v1/ready` — проверьте PostgreSQL и пароль подключения.
- Ошибка отсутствующей таблицы при входе — примените миграции.
- `ORIGIN_NOT_ALLOWED` — проверьте адрес сайта, его порт и `ALLOWED_ORIGINS`.
- `CSRF_FAILED` — войдите заново; при ручном запросе передайте `X-CSRF-Token` из login/me.

Проверка `healthy` у API подтверждает соединение с БД, но не заменяет миграции. Для запуска без Telegram используйте `docker compose up -d --build --wait backend frontend postgres` после подготовки базы.

### Telegram-бот в Docker

Бот запускается вместе с остальными сервисами. Для отдельного запуска:

```sh
docker compose up -d --build --no-deps bot
docker compose logs --tail=100 -f bot
```

`Ctrl+C` завершает просмотр логов, а контейнер продолжает работать. `docker compose stop bot` останавливает приём команд, а `docker compose stop worker` — обработку напоминаний. Для отдельного запуска фронта или базы `BOT_TOKEN` не нужен; `POSTGRES_PASSWORD` нужен для проверки общего Compose-файла.

Откройте личный чат с ботом или добавьте его в нужную группу и вызовите `/help`, затем `/id`. В группе с несколькими ботами используйте `/id@имя_бота`. Запишите полученный ID в `CHAT_ID` в `.env`. Команда `/id` только показывает ID, сама настройку не сохраняет. После изменения `BOT_TOKEN` или `CHAT_ID` пересоздайте оба процесса: `docker compose up -d --no-deps --force-recreate bot worker`. Обычный `restart` не перечитывает окружение; для worker база уже должна работать и иметь актуальные миграции.

Для команды `/site` укажите в корневом `.env` необязательный `PANEL_URL` — полный `http://` или `https://` адрес интерфейса, доступный с устройства, где открыт Telegram. После изменения пересоздайте контейнер бота командой выше; при пустом значении бот сообщит, что ссылка не настроена.

`CHAT_ID` задаёт адрес напоминаний и единственный чат, в котором доступны `/payments`, `/overdue` и кнопки списков. `/payments` показывает ближайшие неоплаченные периоды, `/overdue` — просроченные. В остальных чатах данные закрыты; `/help`, `/id` и `/site` остаются доступны. Пустой `CHAT_ID` не мешает получить `/id`.

Для списков нужен отдельный обычный пользователь API:

1. Войдите администратором в веб-панель и создайте пользователя, например `telegram_bot`, с отдельным паролем.
2. В корневом `.env` задайте его `API_USERNAME` и `API_PASSWORD`. Не используйте учётную запись администратора.
3. В Docker оставьте `API_BASE_URL=http://backend:8000/api/v1`. `API_ORIGIN` должен совпадать с одним из `ALLOWED_ORIGINS`: по умолчанию Compose использует `http://localhost:<FRONTEND_PORT>`. Это адрес сайта без пути, а не адрес внутреннего API. `API_TIMEOUT` — от 1 до 60 секунд, по умолчанию 10.
4. После изменения настроек выполните `docker compose up -d --build --no-deps --force-recreate bot`.

Бот входит через обычный `/auth/login`, хранит cookie-сессию в памяти процесса и использует её для чтения списков. Bearer-токен не нужен. Истёкшую сессию клиент обновляет одним повторным входом; неверный пароль и ограничение попыток не вызывают бесконечные входы. После смены пароля сервисного пользователя обновите `API_PASSWORD` и пересоздайте `bot`. Эти настройки не передаются во фронтенд. Без API-настроек публичные команды и доставка worker продолжают работать.

При запуске Python на компьютере вместо Docker используйте доступный с компьютера `API_BASE_URL`, например `http://localhost:8080/api/v1`; имя `backend` доступно только внутри Docker. Для production с `SESSION_COOKIE_SECURE=true` адрес API должен использовать HTTPS: браузерная Secure-cookie не передаётся клиентом по внутреннему HTTP.

Сервис `bot` получает команды через polling и читает списки из API. Сервис `worker` независимо читает PostgreSQL и отправляет готовые напоминания; `API_USERNAME` и `API_PASSWORD` ему не нужны. Worker не вызывает `getUpdates`, поэтому с ботом они используют один токен без второго polling.

Сервис не публикует порты и не подключается к PostgreSQL. Он получает настройки Telegram, адрес сайта, часовой пояс и данные отдельного пользователя API; рабочий `.env` и пароль базы в образ не копируются. Контейнер работает без root и с файловой системой только для чтения. Проверки `getUpdates` в healthcheck нет, чтобы не конкурировать с основным polling. [Ограничения polling в aiogram](https://docs.aiogram.dev/en/v3.16.0/dispatcher/long_polling.html).

После изменения `bot.py`, `api.py`, `smoke.py`, `reminders.py`, `formatting.py`, `texts.json` или зависимостей повторите запуск с `--build`. Новые файлы нужны и в списке `COPY` Dockerfile, и среди разрешённых файлов `Dockerfile.dockerignore`: разрешение файла в контексте сборки само по себе не добавляет его в образ. Окружение этого сервиса описано в `docker/bot/pyproject.toml` и `docker/bot/uv.lock`: Python `3.12.15`, uv `0.13.5`, aiogram `3.31.0`, python-dotenv `1.2.4`. Образы Python и uv закреплены по digest, зависимости устанавливаются через `uv sync --locked`. Это отдельный набор для контейнера бота; зависимости API остаются у бэкендера. При изменении библиотек обновляйте манифест и lockfile вместе, затем проверяйте сборку.

Если бот не отвечает, проверьте `docker compose ps -a` и `docker compose logs --tail=100 bot`:

- `Set BOT_TOKEN in .env` — заполните токен и пересоздайте контейнер.
- `Unauthorized` или ошибка формата токена — проверьте токен от `@BotFather`.
- `Conflict` — тот же токен уже использует другой запущенный бот; остановите второй процесс.
- Ошибка соединения — проверьте доступ компьютера и Docker к Telegram.
- Списки не настроены — заполните `API_BASE_URL`, `API_USERNAME`, `API_PASSWORD` и разрешённый `API_ORIGIN`; после изменения `.env` пересоздайте `bot`.
- Ошибка входа API — проверьте обычного пользователя и пароль; если сбросили пароль в панели, обновите его в `.env`.
- Ограничение попыток API — дождитесь срока `Retry-After`; частые перезапуски не снимают серверный лимит.
- Команда работает только в заданном чате — сравните `/id` с `CHAT_ID`, затем пересоздайте `bot` и `worker` после исправления настройки.

Не публикуйте вывод `docker compose config` или `docker inspect` с окружением: в нём могут быть секреты. Для проверки синтаксиса используйте `docker compose config --quiet`.

### Проверка Telegram-команд без отправки сообщений

После сборки образа бота можно проверить форматирование примеров и чтение настоящего API:

```sh
docker compose run --rm --no-deps bot python smoke.py --dry-run
docker compose run --rm --no-deps bot python smoke.py --backend --dry-run --limit 3
```

Первой команде API не нужен. Вторая выполняет HTTP-запросы к API и требует готового backend и настроенного обычного пользователя, но не отправляет сообщения в Telegram. Для просроченных добавьте `--kind overdue`; `--limit` допускает 1–100 записей. Переданные процессу переменные окружения имеют приоритет над `.env`.

Без `--dry-run` smoke отправляет реальные сообщения в `CHAT_ID`. Это ручная проверка, которая обходит очередь и не сохраняет подтверждение отправки: повторный запуск может отправить те же данные снова. Не используйте её как планировщик; обычными напоминаниями управляет `worker`. Smoke не запускается автоматически вместе с контейнерами.

Интеграционная проверка с отдельной БД и настоящим API:

```sh
python scripts/check_bot_api.py
```

Она не использует рабочий `.env` и не отправляет сообщения в настоящий Telegram. Для уже собранных образов доступны `--image BACKEND_IMAGE_ID` и `--bot-image BOT_IMAGE_ID`. Эта же проверка запускается в CI **Backend Compose**.

### Фронтенд в Docker

Для отдельной демонстрации без API сначала задайте `FRONTEND_API_MODE=mock` в корневом `.env`. Тогда достаточно одного сервиса; заполненный `POSTGRES_PASSWORD` всё равно нужен для проверки общего Compose-файла:

```sh
docker compose up -d --build --no-deps --wait --wait-timeout 60 frontend
docker compose logs --tail=100 frontend
```

В этом режиме PostgreSQL не запускается. Данные демонстрации хранятся в памяти вкладки и сбрасываются при перезагрузке страницы; в базу они не записываются. Демонстрационный вход не проверяет настоящие серверные сессии. Подробности экранов и локальной разработки — в [README фронтенда](frontend/README.md).

Docker сначала устанавливает зависимости из `package-lock.json`, проверяет TypeScript и ESLint и собирает React через Vite. Затем готовые файлы копируются в небольшой образ Nginx. В запущенном контейнере нет Node.js и исходников; он работает от обычного пользователя с файловой системой только для чтения. Node.js и npm на компьютере для такого запуска не нужны.

После изменений в коде снова выполните команду с `--build`. Если порт занят, укажите, например, `FRONTEND_PORT=8081` в корневом `.env`, повторите запуск и откройте `http://localhost:8081`. Порты обоих сервисов доступны только с вашего компьютера.

Образ по умолчанию собирается для настоящего API; после отдельной демонстрации верните `FRONTEND_API_MODE=real` и пересоберите frontend. Файлы `.env` фронтенда в сборку не попадают. Переменные `VITE_*` встраиваются в JavaScript при сборке: изменение окружения уже запущенного контейнера не переключит режим. Прокси `/api` работает в обоих режимах; если backend остановлен, он возвращает `503 API_NOT_AVAILABLE`.

Проверить раздачу готовой сборки можно с Python 3.10+:

```sh
python scripts/check_frontend.py http://127.0.0.1:8080 --api-ready
```

При запуске только фронтенда уберите `--api-ready`: тогда проверка ожидает HTTP 503 от отсутствующего API.

Скрипт проверяет HTML, JS/CSS, изображения, кеширование, `/healthz` и ответы на отсутствующие или закрытые пути. Он проверяет сервер по HTTP; работу кнопок и форм проверяем в браузере. При ошибке запуска смотрите `docker compose ps -a` и логи `frontend`. Если изменён порт, замените его и в команде проверки.

## Логи контейнеров

У всех сервисов (`backend`, `worker`, `frontend`, `bot`, `postgres`) одинаковые настройки в блоке `x-logging` файла `compose.yaml`: драйвер `local`, `max-size: "10m"`, `max-file: "3"`, `compress: "true"`. Когда файл достигает 10 МБ, Docker начинает следующий; хранит до трёх файлов на контейнер и удаляет самые старые. Старые файлы сжимаются. Это примерно 30 МБ несжатых логов на контейнер, а не ограничение размера БД или всего Docker. Настройка относится к выводу контейнера в stdout/stderr; отдельные файлы, которые приложение пишет само, она не ограничивает. [Как работает драйвер local](https://docs.docker.com/engine/logging/drivers/local/).

Новые контейнеры получают настройки сразу. Для уже работающего проекта примените их пересозданием контейнеров; обычного `restart` недостаточно. Будет короткий перерыв в работе, старые логи удаляемых контейнеров не сохранятся. Том PostgreSQL и данные остаются на месте:

```sh
docker compose up -d --force-recreate --wait --wait-timeout 90 postgres backend frontend
docker compose up -d --no-deps --force-recreate bot worker
```

Вторую команду выполняйте после миграций, если используете Telegram и заполнили `BOT_TOKEN` и `CHAT_ID`. Добавляя новый сервис в `compose.yaml`, подключите `logging: *default-logging`; CI проверяет наличие лимитов у каждого сервиса.

Посмотреть последние записи, следить за новыми и проверить применённые настройки без вывода паролей:

```sh
docker compose logs --tail=100 --timestamps backend
docker compose logs --tail=100 -f bot
docker inspect --format '{{json .HostConfig.LogConfig}}' $(docker compose ps -q postgres)
```

`Ctrl+C` останавливает только просмотр. В последней команде ожидаются `Type: local` и параметры `10m`, `3`, `true`. Если видите `json-file` или старые лимиты, проверьте выбранный Compose-проект и пересоздайте нужный контейнер. Для другого сервиса замените `postgres` его именем. Если старых записей больше нет, они могли уйти при ротации или пересоздании: эти логи не являются архивом. Не редактируйте внутренние файлы логов Docker вручную.

## Резервная копия и восстановление

Нужны Python 3.10+ и запущенная база (`docker compose up -d --wait postgres`). Скрипт использует `pg_dump` и `pg_restore` из контейнера; устанавливать PostgreSQL на компьютер не нужно. Команды ниже выполняются из корня проекта; в Linux / macOS вместо `python` может понадобиться `python3`.

Создать копию рабочей БД:

```sh
python scripts/db_backup.py backup
```

Команда выведет путь к новому файлу в `backups/`. В имени указано время UTC; каждый запуск создаёт отдельный архив. Схема и данные сохраняются вместе, при ошибке незавершённый файл удаляется. Папка `backups/` и файлы `*.dump` исключены из Git.

Восстановить архив в **новую отдельную БД**, заменив путь на полученный после копирования:

```sh
python scripts/db_backup.py restore backups/postgres_YYYYMMDDTHHMMSSZ_example.dump invoice_keeper_restore
docker compose exec postgres sh -c 'psql -U "$POSTGRES_USER" -d invoice_keeper_restore'
```

В `psql` команда `\dt` покажет таблицы, `\q` закроет подключение. Имя новой БД: до 63 символов, латинские строчные буквы, цифры и `_`, первый символ — буква. Если БД с таким именем уже существует, скрипт остановится. Для следующей проверки укажите другое имя, например `invoice_keeper_restore_2`.

Рабочая база и `.env` остаются прежними. Восстановление идёт одной транзакцией; при ошибке новая БД остаётся для проверки, скрипт её автоматически не удаляет. Ошибка `already exists` означает занятое имя, `service "postgres" is not running` — что сначала нужно запустить Compose.

Это копия одной БД, без серверных ролей и их паролей. Владельцем восстановленных объектов будет пользователь из настроек контейнера. Архивы содержат данные приложения: храните их приватно и восстанавливайте только свои или доверенные файлы. Том Docker и архив на том же диске не защитят от поломки диска — важную копию сохраните отдельно.

## Проверка Docker

GitHub Actions запускает независимые проверки в каждом PR и после обновления `main`:

- **Frontend / Compose** — типы, lint, production-сборка, запуск Nginx и HTTP-проверка. Дополнительно проверяются запуск без root, файловая система только для чтения и отсутствие Node.js, исходников и `.env` в каталоге сайта.
- **PostgreSQL / Compose** — запуск PostgreSQL, вход с паролем, сохранение записи после пересоздания контейнера, резервное копирование и восстановление в новую БД.
- **Telegram / Compose** — сборка образа, загрузка библиотек и модулей бота без сети, работа без root и с файловой системой только для чтения, отсутствие `.env` в образе и понятный отказ старта без токена. Настоящий токен не используется; доставку сообщений эта проверка не подтверждает.
- **Backend / PostgreSQL** — установка зависимостей из lockfile, Ruff, существующие тесты авторизации и пользователей, создание администратора из `.env`, защита от повторного создания, применение и откат миграций на временной PostgreSQL.
- **Backend / Compose, Nginx and browser** — сборка API и интерфейса, миграции и создание администратора командами Compose, настоящий вход через Nginx, cookie и CSRF, управление пользователями, повторное подключение после пересоздания API и браузерные сценарии ниже.

Каждая проверка использует собственный временный Compose-проект и удаляет его после завершения; проверка базы также удаляет свой том. Рабочий `.env` и локальная база для CI не нужны. Результаты видны во вкладке **Checks** в PR; при ошибке откройте соответствующую проверку — в ней будут шаг с ошибкой и логи контейнера.

### Браузерная проверка авторизации

В **Backend Compose** Playwright запускает Chromium и проходит настоящие React-формы через Nginx, FastAPI и PostgreSQL. Это дополняет HTTP-проверки: исправный маршрут API ещё не гарантирует, что кнопка интерфейса отправляет правильный запрос. Проверка использует `FRONTEND_API_MODE=real` и страницу `/#users`; сценарии авторизации и управления пользователями не зависят от платёжных данных.

Два сценария в `frontend/e2e/auth.spec.ts` проверяют:

- неверный и верный пароль, восстановление сессии после обновления и в новой вкладке, выход с потерей доступа в обеих вкладках;
- создание пользователя, ограничения его прав в отдельном браузерном контексте, смену логина с сохранением пароля, смену пароля и удаление; после изменений проверяется отзыв старой сессии, после смены пароля и удаления — отказ во входе с прежними данными.

Действия выполняются кнопками и формами, а результат подтверждается экраном и статусом настоящего API. Демонстрационный режим такую проверку не проходит. Тесты идут по очереди, без автоматических повторов; у каждого прогона своя база и случайные пароли. Telegram-бот не запускается.

Для ручного запуска на GitHub откройте **Actions → Backend Compose → Run workflow** и выберите ветку. После завершения скачайте артефакт `auth-e2e-report`: в нём HTML-отчёт, а при сбое — скриншот и `trace.zip` с последовательностью действий. Артефакт хранится семь дней. Trace может содержать тестовые пароли и cookie; используйте только одноразовые учётные записи и не публикуйте отчёт из рабочего окружения.

Для разработки тестов нужны Node.js `24.22.1`, npm `11.6.2` и заранее поднятый отдельный тестовый стенд с миграциями, администратором и пустым списком обычных пользователей. Подготовка такого стенда описана шагами [.github/workflows/backend-compose.yml](.github/workflows/backend-compose.yml); рабочая база для этого не подходит. Из папки `frontend`:

```sh
npm ci
npx playwright install chromium
npm run test:e2e
npm run test:e2e:report
```

Перед `test:e2e` задайте переменные окружения: `E2E_BASE_URL` — адрес тестового Nginx, например `http://127.0.0.1:8081`; `E2E_ADMIN_USERNAME` и `E2E_ADMIN_PASSWORD` — данные администратора именно тестового стенда. В PowerShell переменная задаётся через `$env:E2E_BASE_URL = 'http://127.0.0.1:8081'`. Файлы `.env` тесты автоматически не читают. На Linux для установки системных библиотек браузера используйте `npx playwright install --with-deps chromium`.

Если браузер не установлен, повторите команду установки. Тайм-аут ожидания `/auth/me` часто означает запуск демо вместо `real` или недоступное API; 403 требует проверки `ALLOWED_ORIGINS`, а 429 — новой одноразовой базы либо ожидания сброса лимита входа. Не отключайте ограничения ради зелёной проверки. Локальные отчёты в `frontend/playwright-report/` и `frontend/test-results/` исключены из Git и Docker-контекста.

## Локальный запуск backend

Для разработки backend необходимы Python 3.12+, менеджер зависимостей [uv](https://docs.astral.sh/uv/) и PostgreSQL. Локально используем PostgreSQL 18 в Docker.

Перейдите в каталог backend:

```powershell
cd backend
```

Установите зависимости из зафиксированного `uv.lock`:

```powershell
uv sync --locked
```

Создайте локальный файл окружения, если его ещё нет (PowerShell):

```powershell
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
```

Файл `backend/.env` содержит локальные настройки и секреты и не должен попадать в Git. В `DATABASE_URL` укажите фактические имя пользователя, пароль, порт и базу из корневого `.env` для Compose. Шаблон использует `127.0.0.1:5432`, пользователя и базу `invoice_keeper`; `replace_me` нужно заменить. Специальные символы пароля в URL должны быть percent-encoded. Корневой `.env` настраивает Docker, а `backend/.env` — Python-приложение.

PostgreSQL запускается из корня проекта после настройки корневого `.env`:

```powershell
docker compose up -d --wait postgres
```

Если раньше была создана отдельная база `invoice-keeper-db-dev` на порту `55432`, её можно продолжать использовать: запустите `docker start invoice-keeper-db-dev` и оставьте соответствующий URL в `backend/.env`. Не создавайте новую базу вместо существующей без переноса нужных данных. Команды `uv` ниже выполняются из каталога `backend`.

В `backend/.env` задайте `ADMIN_USERNAME` и свой `ADMIN_PASSWORD` длиной 8–128 символов. Пароль со специальными символами можно заключить в одинарные кавычки. Затем примените миграции и создайте первого администратора:

```powershell
uv run --locked alembic upgrade head
uv run --locked python -m app.cli create-admin
```

Команда читает настройки из `backend/.env` и не спрашивает пароль в терминале. Если логин или пароль не заполнены, она завершится с понятной ошибкой. Переменные окружения процесса имеют приоритет над `.env`; это позволяет передавать настройки при автоматическом запуске. Пароль не выводится в журнал, в PostgreSQL сохраняется его Argon2-хеш.

Повторный вызов с занятым логином завершится ошибкой и сохранит существующий аккаунт и пароль. Изменение `ADMIN_PASSWORD` в `.env` само по себе не меняет пароль уже созданного администратора. Для существующей базы повторно создавать его не нужно; после успешного создания `ADMIN_PASSWORD` можно удалить из `.env`. Сервер API не создаёт и не меняет администратора при каждом старте.

Ручной вариант тоже доступен: `uv run --locked python -m app.cli create-admin --username admin`. В этом режиме пароль и подтверждение запрашиваются без отображения ввода, значения `ADMIN_USERNAME` / `ADMIN_PASSWORD` не используются. Миграция `0002` переводит роль `member` в `user`, сохраняя пользователей, хеши паролей, сессии и ранее введённые имена.

Запустите сервер:

```powershell
uv run --locked uvicorn app.main:app --reload --no-proxy-headers
```

После запуска доступны:

- Swagger UI: http://127.0.0.1:8000/api/v1/docs
- OpenAPI JSON: http://127.0.0.1:8000/api/v1/openapi.json
- Проверка работы API: http://127.0.0.1:8000/api/v1/health
- Проверка подключения к БД: http://127.0.0.1:8000/api/v1/ready

Остановить сервер можно сочетанием `Ctrl+C`.

Для локального запуска через uv используем `--no-proxy-headers`, чтобы IP-лимит входа не зависел от присланного клиентом `X-Forwarded-For`. В Docker запросы идут через настроенный Nginx, как описано выше. Запуск готового обработчика напоминаний описан в [разделе доставки](#доставка-напоминаний-интеграция-с-платежами).

## Авторизация и пользователи

Все маршруты начинаются с `/api/v1`. Публичной регистрации нет: первый администратор создаётся локальной CLI-командой, следующих пользователей добавляет администратор.

| Метод и маршрут | Результат |
|---|---|
| `POST /auth/login` | JSON `username`, `password`; ответ `user` и `csrf_token`, сессия в HttpOnly cookie |
| `GET /auth/me` | Текущий пользователь и CSRF-токен; без действующей сессии — 401 |
| `POST /auth/logout` | Удаление текущей сессии и cookie; ответ 204 |
| `POST /auth/change-password` | Обе роли: текущий и новый пароль; ответ `{user, csrf_token}`, обновлённая cookie, отзыв остальных сессий |
| `GET /users?limit=50&offset=0` | Только администратор; `items`, `total`, `limit`, `offset` |
| `POST /users` | Только администратор; создание пользователя, ответ 201 |
| `PATCH /users/{user_id}` | Только администратор; изменение логина и/или пароля обычного пользователя |
| `DELETE /users/{user_id}` | Только администратор; удаление обычного пользователя и отзыв всех его сессий, ответ 204 |

Контракт согласован с [описанием API frontend](frontend/docs/api-contract.md). Создание принимает только `username` и `password`, роль назначается сервером как `user`. Логин содержит 3–64 символа `a-z`, `0-9`, `_`, `.`, `-`; пробелы по краям убираются, буквы приводятся к нижнему регистру. Пароль — 8–128 символов, без обрезки или нормализации. PATCH принимает `username` и/или `password`; пустой PATCH, явный `null`, `role`, `display_name`, `is_active` и прочие неизвестные поля отклоняются с 422. Ответ пользователя содержит только `id`, `username`, `role`, `created_at`.

В `/users` возвращаются только обычные пользователи, включая `total` и пагинацию. Администратор доступен через `/auth/me`; изменение и удаление любого администратора через `/users/{id}` возвращает `403 ADMIN_ACCOUNT_PROTECTED`. Занятый логин даёт `409 USERNAME_TAKEN` с ошибкой поля `username`.

Все POST, PUT, PATCH и DELETE, включая login, требуют разрешённый заголовок `Origin`. Отсутствующий Origin, значение `null` или посторонний адрес дают `403 ORIGIN_NOT_ALLOWED`; `Referer` не заменяет Origin. Для изменений после входа также передавайте `X-CSRF-Token` из последнего ответа login/me. Неверный CSRF-токен даёт `403 CSRF_FAILED`. Запросы с телом используют `Content-Type: application/json`, кроме загрузки файла чека с MIME самого файла. В Swagger сначала выполните login, затем вставьте полученный `csrf_token` в поле заголовка нужного запроса. Cookie браузер передаст автоматически; при ручной проверке через HTTP-клиент укажите Origin явно.

Frontend делает запросы с `credentials: "include"`. CSRF-токен можно держать в памяти; после перезагрузки страницы восстановить через `/auth/me`. Сессионный токен находится в HttpOnly cookie. Используйте один и тот же hostname для frontend и API: например, `localhost:5173` и `localhost:8000`.

Разрешённые адреса frontend/API задаются JSON-массивом `ALLOWED_ORIGINS` в `.env`. Cookie `session_id` имеет `SameSite=Lax`, фиксированный срок семь дней по умолчанию и проверяется сервером. Пароли хранятся как Argon2-хеши, сессионные токены — как SHA-256-хеши. При смене логина/пароля через администрирование пользователей и при удалении пользователя отзываются все его сессии. После обновления со старой версии cookie потребуется войти заново.

Для самостоятельной смены пароля обе роли используют `POST /auth/change-password`
с JSON `current_password`, `new_password`, Origin и CSRF. Новый пароль — 8–128
символов, без обрезки пробелов, отличается от текущего. Успех сохраняет вход в
текущем браузере, обновляет cookie и возвращает новый CSRF; остальные сессии
отзываются. Исходный срок сессии не продлевается. Неверный текущий пароль —
`422 CURRENT_PASSWORD_INVALID`, одинаковый новый — `422 NEW_PASSWORD_UNCHANGED`.
Отдельный лимит — 5 попыток за 15 минут на пользователя; настройки
`PASSWORD_CHANGE_RATE_LIMIT_ATTEMPTS` / `PASSWORD_CHANGE_RATE_LIMIT_WINDOW_SECONDS`.
Точный контракт, обработка ошибок и пример подключения находятся в
[памятке для frontend](backend/docs/frontend-password-change.md).

Ошибки имеют оболочку `error` с `code`, `message`, `details`. Каждый элемент `details` содержит `{field, code, message}`; для тела это, например, `password`, для query — `query.limit`, для пути — `path.user_id`. Исходные значения паролей в ошибки не копируются. Битый JSON возвращает `400 INVALID_JSON`, неизвестные query-параметры на всех маршрутах API — `422 VALIDATION_ERROR`.

По умолчанию за 15 минут допускаются 10 попыток входа на логин и 60 на IP, включая успешные. При превышении API возвращает 429 с `Retry-After`. Счётчики общие для всех процессов и сохраняются в PostgreSQL.

Для HTTPS-окружения задайте `APP_ENV=production`, `SESSION_COOKIE_SECURE=true` и точные HTTPS-адреса в `ALLOWED_ORIGINS`. Приложение проверяет эти условия при загрузке настроек. Срок сессии и лимиты задаются переменными из `.env.example`.

Очистка истёкших сессий и устаревших счётчиков входа:

```powershell
uv run --locked python -m app.cli cleanup-auth
```

## Календарь и журнал действий

Календарь использует существующие `GET /api/v1/payment-occurrences` и
`GET/PATCH /api/v1/payment-occurrences/{id}`. Обе роли видят сформированные периоды
по сроку оплаты, включая историю прекращённых правил. Для полного месяца нужно
загрузить все страницы. Чтение будущего месяца не создаёт новые обязательства.

`GET /api/v1/audit-events` — журнал только для администратора. Поддерживает
`date_from`, `date_to` (включительно по МСК), `actor`, `action`, `query`, `limit`
и `offset`. Возвращает `{items, total, limit, offset}`: автор и объект как
исторические снимки, время UTC и безопасные изменения до/после. События создания
и прекращения платежа, оплаты, исправления даты, операций с пользователями и
смены собственного пароля сохраняются в одной транзакции с изменением данных.
Ошибки и запросы без реальных изменений событий не создают; пароли и токены
в журнал не записываются. Снимки сохраняются после переименования/удаления пользователя.

Перед запуском новой версии примените `alembic upgrade head`: миграция `0005`
добавляет таблицу журнала поверх `0004`. История до подключения аудита не
восстанавливается. В эту ветку включены экраны из `feat/calendar-audit-ui`;
календарь и журнал подключены к настоящему API. Ошибки API показываются в интерфейсе
с возможностью повтора. Точный контракт и сценарии совместной проверки — в
[памятке календаря и журнала](backend/docs/calendar-audit-integration.md).

## Бюджет и подтверждения оплаты: API для frontend

`GET /api/v1/payments/budget?year=2026` возвращает бюджет года с разбивкой по
12 месяцам; `&month=10` выбирает один месяц. Обе роли получают суммы отдельно
для RUB, USD и EUR: `planned`, `paid`, `unpaid`, `overdue`, `forecast`.
Расчёт идёт по сроку платежа. `planned = paid + unpaid + forecast`, просрочка
входит в неоплаченное. Прогноз дополняет будущие месяцы активных правил и
не создаёт периоды или задания worker. Уже сохранённые периоды не дублируются.

К конкретному периоду можно прикрепить один файл чека (PDF, PNG, JPEG до 5 МиБ)
или HTTPS-ссылку на подтверждение через `GET`, `PUT`, `DELETE` по адресу
`/api/v1/payment-occurrences/{id}/receipt`. Файл скачивается через `GET` того же
пути с `/file`. Ссылка подтверждает совершённую оплату; это не запуск платежа.
Прикрепление чека и отметка оплаты — отдельные операции. Файлы хранятся в
PostgreSQL, попадают в обычную резервную копию и доступны только после входа.
Миграция `0006` добавляет таблицу чеков поверх `0005`. Изменения подтверждения
записываются в журнал без содержимого файла, URL и исходного имени.

Новые экраны бюджета и чеков реализует владелец frontend. Контракты, примеры
запросов, ошибки и порядок подключения описаны в
[памятке для frontend](backend/docs/budget-receipts.md).

## Доставка напоминаний: интеграция с платежами


Пакет `backend/app/delivery` содержит очередь, worker и одну попытку отправки в
Telegram. Ревизия `0003` добавляет очередь и платёжные таблицы; адаптер
`app.services.payment_source:make_source` подключает worker к платежам. Порядок
блокировок и обработка неизвестного исхода описаны в
[документе интеграции](backend/docs/reminder-integration.md).

Сервис `worker` включён в общий `docker compose up`. Он использует тот же образ,
зависимости и платёжный адаптер, что backend; отдельный планировщик не нужен.
При старте проверяется наличие таблицы очереди, но миграции не применяются.
Для отдельного запуска после подготовки БД:

```sh
docker compose up -d --build worker
docker compose logs --tail=100 -f worker
```

Настройки берутся из корневого `.env`: подключение собирается из `POSTGRES_DB`,
`POSTGRES_USER`, `POSTGRES_PASSWORD`, для доставки нужны `BOT_TOKEN` и `CHAT_ID`.
`APP_TIMEZONE` и `TZ` передаются с тем же московским часовым поясом, что API.
`REMINDER_POLL_SECONDS` задаёт паузу между циклами: по умолчанию 30 секунд,
допустимо положительное целое. Уже наступившее напоминание отправляется ближайшим
циклом; время зависит также от очереди и ответа Telegram. После изменения настроек
выполните `docker compose up -d --no-deps --force-recreate worker`.

Состояние очереди можно посмотреть без остановки worker:

```sh
docker compose run --rm worker python -m app.delivery.cli list --status sent
docker compose run --rm worker python -m app.delivery.cli list --status failed
docker compose run --rm worker python -m app.delivery.cli list --status unknown
```

Эти команды используют те же настройки БД и не отправляют сообщения. `failed`
означает подтверждённый отказ или исчерпанные безопасные повторы. `unknown` означает,
что исход отправки неизвестен; автоматического повтора нет. Команды исправления
и проверки перед повтором описаны в [документе интеграции](backend/docs/reminder-integration.md).

Если контейнер перезапускается с `Delivery command failed (ValueError)`, проверьте
`BOT_TOKEN`, `CHAT_ID` и миграции; при `ValidationError` — настройки общего backend,
включая часовой пояс и production-настройки cookie/Origin. Неположительный интервал
даёт ошибку аргументов. `Delivery cycle failed (...)` в работающем контейнере требует
проверки БД, схемы и очереди: `running` не означает успешную доставку. Отсутствие
новых строк в логах может быть нормальным — успешные циклы CLI не печатает.

Без Docker команда остаётся прежней: из `backend/` выполнить
`uv run --locked python -m app.delivery.cli run --adapter app.services.payment_source:make_source`.
Для этого способа нужны `DATABASE_URL`, `BOT_TOKEN` и `CHAT_ID` в `backend/.env`;
интервал можно задать флагом `--poll-seconds 30`. Проверки очереди используют
тестового отправителя и не отправляют сообщения в настоящий Telegram.

Проверка worker в Docker без настоящей рассылки:

```sh
python scripts/check_reminder_worker.py
```

Скрипт собирает worker и поднимает отдельный временный проект с тестовой БД,
не используя рабочий `.env`. Он проверяет запуск, наступившие и будущие сроки,
пропуск оплаченных и прекращённых платежей, восстановление периода и отсутствие
повторной подтверждённой отправки после перезапуска. Telegram заменён внутри
закрытой Docker-сети; временные контейнеры и БД удаляются после проверки.
Готовый образ можно передать через `--image IMAGE_ID`, чтобы не собирать его повторно.

## Проверка backend

Из каталога `backend`:

```powershell
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked python scripts/test_postgres.py
```

Тестовый скрипт подключается к серверу из `DATABASE_URL`, создаёт временную базу с уникальным именем, применяет миграции, запускает тесты и проверяет соответствие моделей схеме. Отдельно запускает настоящую CLI-команду с временным `.env`: проверяет создание администратора, сохранение прежнего пароля при повторном вызове и отказ с пустым паролем. Рабочий `.env` не изменяется. Затем проверяет откат и повторное применение миграции и удаляет созданную тестовую базу. Пользователю PostgreSQL для этого нужно право `CREATEDB`; пользователь официального локального Docker-образа имеет его по умолчанию.

Если права создавать базы нет, подготовьте отдельную одноразовую базу с суффиксом `_test`, укажите её URL в переменной окружения `TEST_DATABASE_URL` и выполните `uv run --locked pytest -q`. Тесты очищают данные только в выбранной тестовой базе. Без `TEST_DATABASE_URL` интеграционные проверки завершаются ошибкой настройки, а не пропускаются. Скрипт выше задаёт эту переменную автоматически. В тестах также проверяется переход с `0001` на `0002` с существующими пользователями и сессиями.

## Правила платежей

Каждый месяц — отдельный период со своим сроком и фактической датой оплаты. Долг за прошлый месяц не мешает созданию следующего периода. Прекращение регулярного платежа останавливает новые периоды и напоминания, но сохраняет уже созданные обязательства и историю.

Все календарные расчёты идут по московскому времени (`Europe/Moscow`). Если нужного числа нет, используем последний день месяца, сохраняя исходное число: 31 января → 28/29 февраля → 31 марта. Просрочка начинается на следующий день после срока; оплата в день срока считается своевременной.

Напоминание становится готово к отправке в 00:00 МСК за три календарных дня до срока. Если платёж добавлен позже, задание создаётся сразу. Оплаченные периоды и прекращённые платежи не напоминают о себе; подтверждённые отправки не повторяются.

Сводка по умолчанию показывает текущий месяц по **срокам платежей**: всего, оплачено, не оплачено и из них просрочено. Просроченное уже входит в неоплаченное. RUB, USD и EUR считаются отдельно.

В API используем JSON с полями `snake_case`, UUID и даты `YYYY-MM-DD`. Суммы передаём строками с двумя знаками (`"45000.00"`), считаем через `Decimal` и храним в `NUMERIC(14,2)`. Календарные даты не переводим в UTC; техническое время передаём в UTC с `Z`. Ошибки имеют общий объект `error` с полями `code`, `message`, `details`.

## Работа в команде

| Направление | Ответственность | Пример ветки |
|---|---|---|
| Основа бэкенда | Авторизация, пользователи, каркас API, фоновая доставка | `feat/auth` |
| Платежи | Периоды, даты, история, суммы и условия напоминаний | `feat/payments` |
| Интерфейс | Экраны React и подключение API | `feat/frontend` |
| Telegram | Настройка бота, текст и отправка готового сообщения | `feat/telegram` |
| Окружение | Docker, общий запуск и проверка приложения | `chore/docker` |

Telegram-модуль получает готовые данные и делает одну попытку отправки. База данных, расписание, очередь и повторы остаются на бэкенде.

`main` — общая согласованная версия. Для каждой небольшой задачи создаём отдельную ветку; постоянных личных веток не ведём. Изменения попадают в `main` через Pull Request (PR) — запрос на просмотр и объединение кода. Перед объединением изменения смотрит хотя бы один коллега.

После принятия приглашения в репозиторий:

```bash
git clone https://github.com/Molzka/invoice-keeper.git
cd invoice-keeper
```

Перед новой задачей обновляем `main` и создаём ветку. Во всех командах ниже замените `feat/auth` на название своей задачи; для следующей задачи выберите новое имя ветки.

```bash
git switch main
git pull --ff-only
git switch -c feat/auth
```

Когда задача готова, проверяем изменения и отправляем свою ветку. Перед `git add .` убедитесь, что в списке только файлы этой задачи и нет секретов.

```bash
git status
git diff
git add .
git diff --cached
git commit -m "Добавить вход и серверные сессии"
git push -u origin feat/auth
```

На GitHub открываем PR из своей ветки в `main`, кратко описываем результат и способ проверки. После просмотра объединяем через **Squash and merge** и удаляем завершённую ветку. Следующую задачу начинаем с обновлённой `main`.

Если за время работы коллеги обновили `main`, сначала сохраните свои изменения коммитом, затем выполните в своей ветке `git fetch origin` и `git merge origin/main`. Конфликты в общих файлах разбирайте с их автором; после объединения повторите проверки и `git push`.

Не отправляем рабочие изменения напрямую в `main` и не переписываем её историю. Общие модели, API и настройки обсуждаем до изменения; небольшие PR объединяем регулярно, чтобы не копить конфликты.

## Зависимости и база данных

- Храним `pyproject.toml` вместе с `uv.lock`, а `package.json` — с `package-lock.json`. Устанавливаем зависимости через `uv sync --locked` в `backend/` или `docker/bot/`, через `npm ci` — в `frontend/`.
- У каждого своя локальная БД. Изменения таблиц передаём миграциями Alembic вместе с моделями; результат автогенерации проверяем вручную.
- Цепочку миграций координирует разработчик основы бэкенда. Применённые коллегами миграции не переписываем; при двух конечных ревизиях согласуем их объединение.
- В общем окружении миграции выполняются одним процессом до запуска новой версии API и фонового обработчика.
- Пароли, токены и рабочий `.env` в Git не добавляем. `.env.example` содержит только настройки для примера и пустое поле пароля.

Подробный порядок установки зависимостей, создания миграций и обновления общего окружения — в [памятке команды](frontend/docs/team-workflow.md). При изменении этих правил обновляем и памятку в том же PR.

Перед PR проверяем сборку, типы и работу изменённых сценариев. Первая общая цель — пройти путь «вход → создание платежа → список → отметка оплаты».
