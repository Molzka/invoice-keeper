# Wiki: одинаковое окружение и изменения PostgreSQL

Эта памятка объясняет, как пяти участникам работать с одинаковыми зависимостями и не ломать общую историю базы данных.
Утверждённая командой основа: FastAPI, SQLAlchemy с asyncpg, Alembic, PostgreSQL, aiogram, React с Vite и TypeScript; общий запуск через Docker Compose. Авторизация — серверные сессии с HttpOnly cookie, хеширование паролей через pwdlib с Argon2, календарные правила по `Europe/Moscow`.
Для фиксации зависимостей команда выбрала **uv** для Python и **npm** для фронтенда. Форматы API и правила учёта утверждены в [контракте API](api-contract.md).

**Состояние проекта:** Compose запускает PostgreSQL, API, фронтенд с Nginx, Telegram-бот и обработчик напоминаний `worker`. Интерфейс по умолчанию обращается к настоящему API; демонстрационный режим выбирается явно через `FRONTEND_API_MODE=mock`. Работают авторизация, пользователи и платежи; сборка, миграции и браузерные сценарии проверяются в CI. Перед запуском API и worker нужны миграции до head (`0004`). Порядок запуска, резервное копирование и проверки описаны в [README](../../README.md).

## Как передавать изменения через Git

Ветка `main` хранит согласованную версию проекта. Для отдельной задачи создаём короткую ветку, например `feat/payment-periods`, и передаём изменения через pull request — запрос на включение ветки после просмотра коллегой. После проверки объединяем через **Squash and merge**, удаляем завершённую ветку и начинаем следующую задачу от обновлённой `main`.

Начало новой задачи выглядит так:

```powershell
git switch main
git pull --ff-only
git switch -c feat/payment-periods
```

Перед коммитом проверить `git status` и `git diff`, добавить только нужные файлы, затем просмотреть `git diff --staged`. Вместе с изменением зависимостей передаются манифест и lockfile; вместе с изменением моделей — проверенная миграция. Новый участник настраивает своё имя и адрес автора коммитов; можно использовать адрес GitHub noreply из настроек аккаунта.

В корне `.gitignore` исключает рабочие `.env`, приватные ключи, виртуальное окружение, `node_modules` и результаты сборки. Шаблон `.env.example`, lockfile и миграции сохраняются в Git. Если файл уже попал в историю, добавление в `.gitignore` не удалит его оттуда: случайно опубликованный секрет нужно отозвать и заменить.

При отклонённом push сначала получить изменения коллег и разобраться в расхождении; не использовать принудительную перезапись общей `main`. При конфликте миграций применять порядок из раздела ниже, а не исправлять только текстовый конфликт Git.

## Что такое фиксация версий

Зависимость — библиотека, которую использует приложение. У неё могут быть свои зависимости.
Манифест (`pyproject.toml` или `package.json`) описывает нужные библиотеки и допустимые версии.
**Lockfile** фиксирует конкретно выбранные версии и сведения для их установки, включая вложенные зависимости.
Его сохраняют в Git вместе с манифестом: коллега получает согласованный набор, а не произвольные свежие версии. [Как uv фиксирует и устанавливает зависимости](https://docs.astral.sh/uv/concepts/projects/sync/).

| Что фиксируем | Где записано | Ответственный |
|---|---|---|
| Python `3.12.15` | `backend/.python-version`, `backend/Dockerfile`, `docker/bot/Dockerfile`; допустимый диапазон — в соответствующем `pyproject.toml` | №1 и №5 |
| Node.js `24.22.1` | `frontend/.node-version`, `frontend/Dockerfile`, CI | №3 и №5 |
| uv `0.13.5`, npm `11.6.2` | Dockerfile и CI; npm также в `frontend/package.json` | №5 |
| Python-библиотеки API и worker | `backend/pyproject.toml` и `backend/uv.lock` | Автор изменения |
| Python-библиотеки контейнера бота | `docker/bot/pyproject.toml` и `docker/bot/uv.lock` | №4 и №5 |
| JavaScript/TypeScript-библиотеки | `frontend/package.json` и `frontend/package-lock.json` | №3 |
| PostgreSQL `18.6`, базовые Docker-образы | Конкретные теги и digest в `compose.yaml` и Dockerfile | №5 |

При обновлении инструмента меняем все места, где закреплена его версия, и повторяем связанные проверки. Сам по себе файл с номером Node.js не переключает установленный Node: менеджер версий или контейнер должен его учитывать.
API и worker используют один backend-образ и `backend/uv.lock`; у контейнера бота отдельное Python-окружение и lockfile. Обновляйте зависимости нужного окружения; не заводите для него ещё один ручной список вроде `requirements.txt`. Если библиотека используется в обоих окружениях, проверьте оба манифеста и lockfile.

Docker-теги могут меняться даже при конкретном номере. Digest `sha256:…` указывает точный образ; его обновление становится отдельным проверяемым изменением. Не копируйте выдуманный digest и не используйте `latest` как фиксацию. [Docker о фиксации образов](https://docs.docker.com/build/building/best-practices/#pin-base-image-versions).

## Как участник получает окружение

Для общего запуска установленные на компьютере Python, Node.js и uv не нужны: используйте [инструкцию Docker Compose](../../README.md#локальный-запуск). Compose читает **корневой `.env`**. PostgreSQL хранит данные в отдельном томе; обычное пересоздание контейнера их сохраняет. Лимиты журналов и их просмотр описаны в [разделе о логах](../../README.md#логи-контейнеров).

Для работы над API без контейнера установите закреплённые Python и uv, затем выполните **в `backend/`**:

```powershell
uv sync --locked
```

Команда установит согласованные зависимости и завершится ошибкой, если lockfile требует обновления. Она не должна молча выбирать новый набор. [Режим `--locked`](https://docs.astral.sh/uv/concepts/projects/sync/).

Для этого способа запуска нужен **`backend/.env`** из `backend/.env.example`: укажите в `DATABASE_URL` свою БД, пользователя, пароль и опубликованный порт PostgreSQL на `127.0.0.1`. Специальные символы пароля в URL должны быть percent-encoded. Корневой `.env` автоматически в Python-приложение не подставляется. Подробности — в [локальном запуске backend](../../README.md#локальный-запуск-backend).

Для работы над фронтендом установите закреплённые Node.js и npm, затем выполните **в `frontend/`**:

```powershell
npm ci
```

Команда требует согласованный lockfile, не переписывает его и заменяет существующий `node_modules`. Для одинакового результата нужны согласованные версия npm и настройки установки; необходимые настройки хранят в проектной `.npmrc`. [Поведение `npm ci`](https://docs.npmjs.com/cli/v11/commands/npm-ci/).

Контейнер бота устанавливает свой lockfile при сборке: после изменения `bot.py`, `reminders.py` или его зависимостей выполните из корня `docker compose up -d --build --no-deps bot`. Нужен `BOT_TOKEN` в корневом `.env`; не запускайте одновременно вторую копию polling с тем же токеном.

Worker запускается существующей CLI-командой `app.delivery.cli run` с адаптером `app.services.payment_source:make_source`. Он читает платежи и очередь PostgreSQL, отправляет сообщения через тот же `BOT_TOKEN` в `CHAT_ID` и не вызывает `getUpdates`. Поэтому `bot` и `worker` могут работать одновременно. Пауза между циклами задаётся `REMINDER_POLL_SECONDS` (30 секунд по умолчанию). После изменения окружения пересоздайте затронутые сервисы; `docker compose restart` не перечитывает `.env`. Получение `CHAT_ID`, диагностика очереди и команды восстановления приведены в [README](../../README.md#доставка-напоминаний-интеграция-с-платежами).

Когда нужна новая библиотека или обновление, автор делает отдельное изменение манифеста и lockfile штатным менеджером пакетов, описывает причину и проверяет затронутые сценарии.
В Git попадают оба файла; `.venv`, `node_modules`, пароли, Telegram-токен и рабочий `.env` туда не попадают.
При конфликте lockfile сначала согласуют манифесты, затем пересоздают lockfile тем же менеджером; не выбирают механически «нашу» сторону.

## Что такое миграция

**Миграция** — сохранённый в Git шаг изменения схемы БД: например, добавить таблицу сессий или поле фактической даты оплаты.
Модель SQLAlchemy описывает желаемую структуру, а миграции объясняют, как перевести уже существующую БД к ней.
Alembic хранит примененную ревизию в служебной таблице; `revision` — идентификатор шага, `down_revision` — его предшественник.
**Head** — конечная ревизия ветки миграций. Для этого проекта целевое состояние — одна согласованная конечная ревизия. [Ветки и heads в Alembic](https://alembic.sqlalchemy.org/en/latest/branches.html).

Ручное изменение таблицы через SQL-клиент не заменяет миграцию: остальные участники такое изменение не получат.
Создание таблиц через `create_all()` не использовать как второй механизм обновления схемы приложения.

## Кто за что отвечает

- **№1:** настраивает Alembic, подключение метаданных всех моделей, миграции пользователей, сессий, заданий и состояния отправок; координирует порядок объединения и проверяет heads.
- **№2:** создаёт модели и миграции платежей, периодов и связанных ограничений; согласует изменение общих таблиц с №1.
- **№4:** работает только с модулем отправки aiogram; не проектирует таблицы, не пишет миграции и не ведёт состояние отправок. Готовые поля сообщения ему передаёт №1.
- **№3:** заранее сообщает, какие поля и форматы нужны интерфейсу; не меняет схему БД напрямую.
- **№5:** поддерживает Docker Compose, отдельный шаг миграции, постоянный volume PostgreSQL, резервное копирование, ротацию логов и CI; проверяет общий запуск и браузерные сценарии с настоящим API.
- **Каждый:** использует собственную локальную БД. Общая демонстрационная БД обновляется согласованно, а не из пяти рабочих веток.

## Порядок одного изменения схемы

1. Обновить рабочую ветку изменениями основной ветки и проверить, что нет неожиданного второго head.
2. Подключить свою локальную БД с известной схемой, без ручных изменений; применить уже имеющиеся миграции. Для проверки с нуля использовать отдельную пустую БД.
3. Изменить модели SQLAlchemy. Пример: добавить периодам `paid_on` типа DATE согласно [контракту API](api-contract.md).
4. Создать кандидат миграции командой ниже.
5. Вручную прочитать файл: имена таблиц, типы, `nullable`, ограничения, индексы, `upgrade()` и смысл `downgrade()`.
6. Продумать существующие строки: новое обязательное поле может потребовать заполнения данных перед добавлением `NOT NULL`.
7. Применить миграцию, проверить ревизию и сравнение схемы с моделями.
8. Проверить два пути: все миграции на отдельной пустой БД и обновление БД предыдущей версии с представительными данными.
9. Проверить затронутый сценарий через API: сейчас — вход и пользователей; для будущих миграций платежей — чтение старых записей, создание платежа, оплату и сохранность истории.
10. Передать на проверку модели, миграцию и описание влияния на данные одним изменением; повторно проверить heads после объединения.

Следующие команды выполнять **в `backend/`** после `uv sync --locked` и настройки `backend/.env`, с подключением к своей локальной БД. Между этапами есть ручной просмотр — не запускайте весь блок без остановки.

```powershell
# До изменения моделей: привести локальную БД к текущей истории
uv run --locked alembic heads
uv run --locked alembic upgrade head

# После изменения моделей: создать файл, затем вручную проверить его
uv run --locked alembic revision --autogenerate -m "add payment period paid_on"

# После ручной проверки файла
uv run --locked alembic upgrade head
uv run --locked alembic current
uv run --locked alembic heads
uv run --locked alembic check
```

Новый файл миграции создавайте в рабочей копии через uv: он должен попасть в `backend/alembic/versions/` и в PR. Обычный контейнер API работает с файловой системой только для чтения, а исходники не подключены как каталог с компьютера. Поэтому `docker compose run ... alembic revision` не подходит для сохранения новой миграции в репозиторий.

Готовые миграции можно применять и проверять **из корня проекта через Docker**, используя корневой `.env`. Сначала пересоберите образ, чтобы он содержал актуальные файлы, а затем выполните нужную команду:

```powershell
docker compose build backend worker
docker compose stop backend worker
docker compose run --rm backend alembic heads
docker compose run --rm backend alembic upgrade head
docker compose run --rm backend alembic current
docker compose run --rm backend alembic check
docker compose up -d --wait --wait-timeout 90 backend worker frontend
```

Только для новой БД после миграций создайте первого администратора: `docker compose run --rm backend python -m app.cli create-admin`. Логин и пароль берутся из `ADMIN_USERNAME` и `ADMIN_PASSWORD` в корневом `.env`. При запуске через uv аналогичная команда выполняется из `backend/` и читает `backend/.env`. Уже созданного администратора повторно создавать не нужно; изменение переменной пароля не меняет существующий аккаунт.

`--autogenerate` предлагает изменения, но не заменяет их проверку: например, переименование может выглядеть как удаление и добавление. `alembic check` ищет оставшиеся различия тем же механизмом и имеет те же ограничения; успешный результат не доказывает сохранность данных. [Автогенерация и проверка Alembic](https://alembic.sqlalchemy.org/en/latest/autogenerate.html).

Проверки выполняются на подходящих локальных данных. Новые unit-тесты для этого процесса не требуются; использовать существующие проверки и реальные интеграционные сценарии.

## Если двое одновременно создали миграции

Две миграции от одного предшественника образуют два head. Это бывает даже без конфликта текстовых файлов.
№1 и авторы сначала сравнивают операции и зависимости. Если обе ветки совместимы, создают merge-ревизию и проверяют обновление с каждой из веток и с чистой БД.
Merge объединяет граф истории; он не исправляет конфликтующие операции над одной колонкой. [Как работает merge в Alembic](https://alembic.sqlalchemy.org/en/latest/branches.html).

Не переписывать `down_revision` вслепую. Локальную миграцию, которой никто больше не пользовался, можно согласованно пересоздать поверх новой основы.
Уже опубликованные или применённые коллегами миграции не редактировать: исправление оформляется следующей миграцией.
Не использовать `stamp head` для сокрытия ошибки: отметка версии без выполнения изменений не приводит схему к нужному состоянию.

## Порядок обновления общего окружения

1. №5 собирает приложения из согласованного коммита с зафиксированными зависимостями и образами.
2. Перед изменением существующей общей БД создают резервную копию и проверяют способ восстановления; учитывают совместимость старого приложения с новой схемой. Команды `scripts/db_backup.py` приведены в [README](../../README.md#резервная-копия-и-восстановление).
3. Останавливают API и worker командой `docker compose stop backend worker`. PostgreSQL остаётся доступен; **один** отдельный процесс применяет миграции.
4. Только после успешного результата запускают новую версию API и worker, затем проверяют пользовательский сценарий и состояние очереди.
5. Если миграция завершилась ошибкой, новая версия не запускается до выяснения причины. Откат кода сам по себе не откатывает схему и данные.

Для первой версии используется согласованное короткое окно обслуживания с остановкой API и worker. Миграции не запускаются параллельно при старте каждой копии приложения.
Volume PostgreSQL переживает пересоздание контейнера, но не является резервной копией. Его удаление уничтожает хранимые в нём данные.

## Частые проблемы

| Симптом | Что проверить |
|---|---|
| `uv sync --locked` или `npm ci` сообщает о несоответствии | Получены ли манифест и lockfile из одного коммита; совпадают ли менеджер и настройки |
| Alembic предлагает удалить почти все таблицы | Загружены ли все модели в `target_metadata`, верны ли схема и подключение; такую миграцию не применять |
| `Target database is not up to date` | Свою ли БД выбрали, получены ли все миграции и применены ли предшествующие ревизии |
| `Multiple head revisions` | Посмотреть граф, согласовать ветки с №1 и проверить совместимость операций |
| `NOT NULL` или уникальное ограничение не применяется | Есть ли старые строки без значения или дубли; нужна ли миграция данных |
| После миграции поля всё ещё нет | К какой БД подключены API и Alembic, какую ревизию показывает `current` |
| Docker и локальный API подключаются к разным данным | Корневой `.env` и `backend/.env` настраиваются отдельно; сверить БД, пользователя и опубликованный порт |
| `Read-only file system` при создании миграции | Создавать файл через uv в `backend/`, затем пересобрать образ для проверки через Docker |

Практическое правило: фиксируем **код + зависимости + историю схемы** вместе, а данные каждого окружения храним и обновляем отдельно.
