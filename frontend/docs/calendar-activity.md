# Календарь оплат и журнал действий

## Что реализовано на фронтенде

Календарь использует действующий `GET /api/v1/payment-occurrences`, детализация и отметка оплаты — прежние `GET/PATCH /payment-occurrences/{id}`. Обе роли могут работать с календарём. Журнал действий подключён к `GET /api/v1/audit-events` и доступен только администратору; backend проверяет права на каждом запросе.

Перед включением реального журнала нужно обновить backend и применить миграции до head: из каталога `backend` выполнить `uv run --locked alembic upgrade head`. Миграция `0005` добавляет таблицу серверного аудита поверх `0004`. Новые frontend-зависимости не требуются.

## Календарь

В разделе «Календарь» показаны обязательства по **сроку оплаты**, а не по фактическому дню оплаты. Месячная сетка начинается с понедельника. День раскрывает полный список своих платежей; на телефоне используется список по дням. Нажатие на платёж открывает общую панель: отметить оплату, исправить дату, отменить отметку, перейти в историю регулярного платежа. Прекращённые платежи сохраняются.

Месяц, выбранный день, валюта и статус сохраняются в `#calendar?...`; обновление страницы и переходы назад/вперёд восстанавливают состояние. «Сегодня» использует общую бизнес-дату: в демо 23 октября 2026 года, в настоящем режиме текущий день в `timezone` из ответа авторизации. По умолчанию это `Europe/Moscow`; при другом `APP_TIMEZONE` календарь использует тот же пояс, что и сервер. После смены дня календарь перечитывает статусы, не сбрасывая редактируемую дату в панели оплаты.

Для месяца загружаются все страницы периодов, по 100 записей. Незавершённая или противоречивая выдача отображается как ошибка с повтором, а не как полный месяц. Скрытого лимита отображаемых платежей нет. Суммы — строки, валюты не складываются между собой. Календарные даты рассчитываются без преобразования в часовой пояс браузера. Окончательные даты и статусы приходят с сервера.

Календарь показывает уже сформированные сервером периоды. Пустой будущий месяц не гарантирует отсутствия расходов: backend может ещё не сформировать эти периоды. Фронтенд не создаёт обязательства по прогнозу.

## Журнал

Журнал — список событий с автором, временем в часовом поясе сервера, действием и объектом изменения. Есть поиск по объекту/автору, фильтры по действию, автору и датам, страницы и панель подробностей со значениями до/после. Фильтры и страница сохраняются в `#activity?...`. «Сбросить» очищает также неприменённые поля и ошибку диапазона.

В режиме `real` адаптер `src/api/activity.ts` загружает журнал с backend: `GET /api/v1/audit-events`. Клиент передаёт cookie с `credentials: 'include'`. Параметры: `date_from`, `date_to`, `actor`, `action`, `query`, `limit`, `offset`; пустые фильтры опускаются. Параметр `q` существует только в адресной строке страницы, в API отправляется `query`. Время возвращается в UTC; фильтрация по датам, группировка по дням и показ времени используют общий `timezone` из авторизации. Порядок — от новых к старым.

Ошибки сервера и сети показываются с возможностью повторной загрузки; реальные данные не заменяются примерами или нулевым счётчиком. `401` запускает общий выход из истёкшей сессии, `403` сохраняет отказ в доступе. Если маршрут возвращает `404`, нужно обновить backend; если миграция не применена, нужно завершить обновление базы.

В `mock` события — демонстрационные, хранятся только в памяти вкладки и сбрасываются при перезагрузке. Успешные изменения платежей и пользователей добавляют новые события. Ошибки и действия без изменения данных не создают ложных записей. Демо-журнал не является долговечным серверным аудитом.

### Серверный контракт

`src/types/activity.ts` соответствует серверному ответу `{items, total, limit, offset}`. У события есть `id`, `occurred_at` (timestamp UTC), `actor: {id, username}`, `action`, `entity: {type, id, title}` и `changes: [{field, label, before, after}]`. Для платёжных событий `entity.id` — ID регулярного платежа, чтобы открыть всю его историю. Backend сохраняет снимки автора и названия объекта после удаления/переименования.

Действия: создание/прекращение платежа, отметка/отмена оплаты, изменение фактической даты, создание/изменение/удаление пользователя, смена собственного пароля. Время события задаёт сервер. Событие и успешное изменение сохраняются в одной транзакции. Отклонённые запросы и операции без изменений не создают записей. После изменения интерфейс обновляет журнал через общий `revision`. История до подключения аудита не восстанавливается вымышленными событиями.

Журнал также поддерживает серверные события `payment.receipt_updated` и `payment.receipt_deleted`: изменение и удаление подтверждения оплаты. В них отображаются только факт, тип подтверждения и период; URL, имя файла и содержимое не включаются в журнал. Экраны бюджета и прикрепления подтверждений подключает владелец frontend отдельно.

В журнал не передаются и не показываются пароли, их хеши, cookie, CSRF и другие секреты. Для смены пароля отображается только факт изменения. Клиентский интерфейс и скрытая вкладка не заменяют серверную проверку прав.

## Проверка

- Календарь: смена месяца, «Сегодня», фильтры, выбранный день, длинные названия и крупные суммы, полный список дня, оплата и переход в историю.
- Журнал: фильтры/поиск/пагинация, сброс неприменённых значений и ошибочного диапазона, подробности, события после изменений, отсутствие у обычной роли.
- Обновление и Back/Forward, мобильная и настольная раскладка, клавиатура, уменьшенная анимация, загрузка/ошибка/пустой результат.
- Автоматические проверки: `npm test`, `npm run build`, `npm run lint`.

### Результат проверки этой версии

Автоматические тесты real-адаптера проверяют фактический запрос к `/audit-events`, передачу фильтров и cookie, пустую серверную выдачу, ошибки `401/403/404/503` и сетевую ошибку без подмены демонстрационными данными. Полные параметры сервера, правила транзакций и сценарии проверки описаны в [backend-памятке](../../backend/docs/calendar-audit-integration.md).
