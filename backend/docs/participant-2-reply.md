Привет! Наша часть доставки подготовлена в ветке `feat/auth`.
Полный контракт: `backend/docs/reminder-integration.md`.

Это предложение для согласования. Расписание запуска, очередь, повторные попытки
и сохранение результата Telegram остаются у меня, участника 1. От тебя нужны
периоды, текущее состояние оплаты/активности правила, адаптер и включение таблицы
очереди в миграцию. Планировщик и повторы в сервисе платежей дублировать не нужно.

**Блокировки и транзакции.** Подтверждаю общую AsyncSession и порядок:
транзакция → `pg_advisory_xact_lock(0x494E56, 2)` → `FOR UPDATE` строки правила →
периоды/очередь. Готовый helper — `app.delivery.locking.lock_payments(db)`.
Это именно два integer-аргумента, не один bigint. Твой интерфейс
`ensure_payment_periods(db, payment_id, today, through=None)` без commit подходит.

**Очередь.** Фактическая функция:

```python
from app.delivery.queue import enqueue_payment_reminder

# В твоей текущей транзакции, после advisory lock и блокировки правила:
await db.flush()
delivery_id = await enqueue_payment_reminder(
    db,
    payment_id=rule.id,
    occurrence_id=period.id,
    due_date=period.due_date,
)
```

Она не коммитит и не открывает отдельную сессию. Правило, периоды и задание
сохраняются/откатываются вместе. В `reminder_deliveries` есть
`UNIQUE(occurrence_id)`. Повторная постановка возвращает прежнее задание и не
сбрасывает ни подтверждённую отправку, ни неизвестный исход.

Состояние хранится на период, а не на всё правило: оплата одного месяца не мешает
напоминаниям за другие. ID периода должен оставаться прежним при повторной
генерации, оплате и отмене оплаты. Прекращение сохраняет периоды и историю отправок.
При создании неоплаченного периода вызови постановку задания в той же транзакции,
не дожидаясь обхода worker. Для поздно добавленного платежа задание готово сразу
после commit, фактическая отправка — ближайшим циклом worker.

Состояния: `pending`, `in_flight`, `retry`, `sent`, `unknown`, `cancelled`, `failed`.
`sent` требует сохранённых Telegram message_id и sent_at и не сбрасывается при
изменении оплаты. Таймаут, обрыв связи, 5xx или прерванный процесс дают `unknown`
(через истечение lease для незавершённого in_flight), без автоматического повтора.
Повторяем только явно отвергнутые временные запросы, например Telegram 429.
Для unknown есть отдельное ручное подтверждение исхода оператором.

Для `failed` после исправления причины есть явная команда
`uv run --locked python -m app.delivery.cli requeue-failed JOB_UUID`
(из `backend/`). Она возвращает ту же запись в pending с новым лимитом попыток,
сохраняя ещё действующий Retry-After. Worker заново проверяет оплату и активность.
Команда не принимает `unknown`, `sent` и другие состояния. `resolve` остаётся
только для ручного разбора unknown. При изменении CHAT_ID нужно перезапустить
worker, чтобы он прочитал исправленную настройку.

**Worker.** Реализован `app.delivery.worker.DeliveryWorker`. Он вызывает общий
генератор через адаптер `PaymentSource` и восстанавливает очередь для неоплаченных
периодов. Непосредственно перед сетью повторно проверяет существование/активность
правила, оплату, время и владение попыткой. Проверка и ограниченная по времени
отправка держат общую блокировку, поэтому закоммиченное прекращение исключает
новые отправки. Уже начавшийся Telegram-запрос отменить прекращением нельзя.

Расписание: 00:00 МСК за три календарных дня до due_date, хранение TIMESTAMPTZ UTC.
Прошедшее время постановки означает готовность сразу после commit. Изменение
оплаты не сбрасывает sent. Отмена оплаты для ещё не отправленного периода снова
позволяет доставку после проверки условий.

Нужно реализовать адаптер к твоим моделям: `active_payment_ids`, `lock_rule`
(FOR UPDATE; True только для существующего активного правила),
`ensure_payment_periods`, `unpaid_occurrences`, `occurrence`.
Типы и точные сигнатуры находятся в `app.delivery.contracts`; все используют
переданную db, без commit. Саму генерацию периодов worker не дублирует.

**Миграция.** Номер 0003 оставлен за платежами: текущий head по-прежнему 0002,
конкурирующих ревизий нашей очереди нет. Предлагаемая цепочка 0002 → 0003 подходит.
В твою 0003 нужно включить схему `app.delivery.schema` и добавить
`delivery_metadata` в Alembic target_metadata — точные шаги в документе.
После фиксации 0003 её DDL нужно заморозить; последующие изменения — новыми
ревизиями. Фактическую 0003 ещё нельзя подтвердить: пришли её после написания,
тогда проверим SQL, metadata, upgrade/downgrade и совместную работу на PostgreSQL.

Наши тесты очереди/worker выполняются на PostgreSQL с тестовым адаптером платежей.
Это проверка протокола и доставки, а не ещё несуществующего платёжного сервиса.
