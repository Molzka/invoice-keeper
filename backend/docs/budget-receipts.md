# Подключение бюджета и чеков на frontend

Backend предоставляет API для бюджета месяца/года и одного чека или ссылки на
конкретный период платежа. Экраны этих функций нужно реализовать на frontend.
Все пути ниже начинаются с `/api/v1`. Swagger: `/api/v1/docs`.

## Авторизация и общие правила

- Обе функции доступны авторизованным пользователям с ролями `admin` и `user`.
- Во всех `fetch` используйте `credentials: 'include'`: авторизация работает
  через HttpOnly cookie, токен сессии читать или сохранять в JavaScript не нужно.
- Для `PUT` и `DELETE` нужен актуальный `X-CSRF-Token` из входа, `/auth/me` или
  успешной смены пароля. Браузер также должен передать разрешённый `Origin`;
  он устанавливает этот заголовок самостоятельно. Адрес frontend должен быть
  включён в `ALLOWED_ORIGINS` backend.
- GET-запросы CSRF-токена не требуют. Неизвестные query-параметры дают `422`.
- Приватные ответы возвращаются с `Cache-Control: no-store`.
- Суммы приходят строками с двумя знаками после точки. Не складывайте валюты
  между собой и не используйте двоичную арифметику `Number` для денежных итогов.

Общий формат ошибки:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Некорректные данные запроса",
    "details": [
      {
        "field": "file",
        "code": "INVALID_RECEIPT_FILE",
        "message": "Содержимое файла не соответствует выбранному формату PDF, PNG или JPEG"
      }
    ]
  }
}
```

У общих ошибок `details` может быть пустым. При `401 AUTH_REQUIRED` требуется
повторный вход. При `403 CSRF_FAILED` обновите состояние через `/auth/me`;
при `403 ORIGIN_NOT_ALLOWED` проверьте адрес frontend и настройки backend.

## Бюджет месяца и года

```http
GET /api/v1/payments/budget?year=2026&month=11
GET /api/v1/payments/budget?year=2026
```

`year` обязателен, целое число от 1 до 9999. `month` необязателен, от 1 до 12.
Без `month` ответ включает весь год и 12 записей в `months`; с месяцем — одну.
Границы диапазона включительны. Произвольных `date_from`/`date_to` здесь нет.

Пример месячного ответа, рассчитанного 24 октября:

```json
{
  "year": 2026,
  "month": 11,
  "date_from": "2026-11-01",
  "date_to": "2026-11-30",
  "as_of_date": "2026-10-24",
  "timezone": "Europe/Moscow",
  "totals": {
    "RUB": {
      "planned": "120.00",
      "paid": "20.00",
      "unpaid": "10.00",
      "overdue": "0.00",
      "forecast": "90.00"
    },
    "USD": {
      "planned": "0.00",
      "paid": "0.00",
      "unpaid": "0.00",
      "overdue": "0.00",
      "forecast": "0.00"
    },
    "EUR": {
      "planned": "0.00",
      "paid": "0.00",
      "unpaid": "0.00",
      "overdue": "0.00",
      "forecast": "0.00"
    }
  },
  "months": [
    {
      "month": 11,
      "totals": {
        "RUB": {
          "planned": "120.00",
          "paid": "20.00",
          "unpaid": "10.00",
          "overdue": "0.00",
          "forecast": "90.00"
        },
        "USD": {
          "planned": "0.00",
          "paid": "0.00",
          "unpaid": "0.00",
          "overdue": "0.00",
          "forecast": "0.00"
        },
        "EUR": {
          "planned": "0.00",
          "paid": "0.00",
          "unpaid": "0.00",
          "overdue": "0.00",
          "forecast": "0.00"
        }
      }
    }
  ]
}
```

В годовом ответе `month` равен `null`, `months` отсортирован от января до декабря,
а `totals` равен сумме соответствующих месячных полей. Все три валюты и все пять
полей присутствуют всегда, в том числе при отсутствии данных.

| Поле | Смысл и подпись для интерфейса |
| --- | --- |
| `planned` | Общий план: `paid + unpaid + forecast` |
| `paid` | Оплаченные существующие периоды |
| `unpaid` | Неоплаченные существующие периоды |
| `overdue` | Просроченная часть `unpaid`, не дополнительная сумма |
| `forecast` | Прогноз будущих сроков, для которых период ещё не создан |

Бюджет группируется по **сроку платежа `due_date`**, а не дате фактической оплаты.
Например, платёж со сроком в январе и оплатой в феврале входит в январский `paid`.
Ранняя оплата будущего периода также учитывается в месяце его срока.

`as_of_date` вычисляет сервер в `APP_TIMEZONE`, по умолчанию `Europe/Moscow`.
Просрочен только неоплаченный период со сроком строго раньше этой даты: сегодняшний
срок ещё не просрочен. Для дат `YYYY-MM-DD` не применяйте дополнительный перевод
часового пояса на клиенте.

Прогноз строится по активным ежемесячным правилам, начиная с первого срока.
Дни 29/30/31 сокращаются до последнего дня короткого месяца с сохранением исходного
дня для следующих месяцев. Существующий период учитывается один раз. Для
остановленного правила остаются существующие периоды, новые прогнозные сроки не
добавляются. Суммы берутся из текущего правила платежа, как в существующей сводке.

Просмотр бюджета не создаёт периоды и задания Telegram. Прогноз не имеет
`occurrence_id`: для него нельзя вызвать оплату или прикрепить чек. Такие действия
доступны только для реального периода из `/payment-occurrences`.

При `503 PERIODS_NOT_READY` сервер обнаружил недостающий период активного правила
в выбранном диапазоне до конца текущего месяца. Покажите «Данные периодов ещё
обновляются» и возможность повторной загрузки; не подменяйте ответ нулевым бюджетом.
При `422 VALIDATION_ERROR` проверьте год, месяц и неизвестные параметры.
Существующий `/payments/summary` сохраняет прежний контракт и не используется
вместо API прогноза на будущий год.

## Один чек или ссылка на период

Используется **ID периода `PaymentOccurrence.id`**, а не ID регулярного правила.
На период сохраняется один объект: файл либо HTTPS-ссылка. Следующий `PUT` заменяет
его целиком; список вложений и отдельная загрузка по ID чека не предусмотрены.

| Метод и путь | Результат |
| --- | --- |
| `GET /payment-occurrences/{occurrence_id}/receipt` | `200` с метаданными или JSON `null` |
| `PUT /payment-occurrences/{occurrence_id}/receipt` | `200` с созданными/обновлёнными метаданными |
| `DELETE /payment-occurrences/{occurrence_id}/receipt` | `204`, тело отсутствует |
| `GET /payment-occurrences/{occurrence_id}/receipt/file` | Файл для скачивания |

Период существует, но вложения ещё нет: `GET .../receipt` возвращает **`200 null`**.
Несуществующий период возвращает **`404 PAYMENT_OCCURRENCE_NOT_FOUND`**.
`GET .../receipt/file` возвращает **`404 RECEIPT_FILE_NOT_FOUND`**, если вложения нет
или сохранена ссылка. Повторный DELETE отсутствующего вложения существующего
периода успешен и возвращает `204`.

### Сохранение ссылки

```http
PUT /api/v1/payment-occurrences/15d3c870-dcb1-4c6c-9dca-2433e7d34387/receipt
Content-Type: application/json
X-CSRF-Token: <актуальный токен>

{"url":"https://example.com/receipts/123"}
```

Разрешена корректная HTTPS-ссылка длиной до 2048 символов без логина/пароля,
пробелов и управляющих символов. Передаётся только поле `url`. Backend сохраняет
ссылку и не скачивает документ по ней. При открытии в новой вкладке используйте
`rel="noopener noreferrer"`.

Ответ:

```json
{
  "id": "d02911df-f7d8-4262-bad6-d60e03e5edd6",
  "kind": "link",
  "url": "https://example.com/receipts/123",
  "filename": null,
  "content_type": null,
  "size_bytes": null,
  "uploaded_at": "2026-10-24T10:00:00Z"
}
```

### Загрузка файла

Допустимы `application/pdf`, `image/png`, `image/jpeg`; размер от 1 байта до
**5 МиБ включительно — 5 242 880 байт**. Проверяются тип и сигнатура содержимого.

Тело запроса — **сам файл**, без `FormData`, `multipart/form-data`, JSON или base64.
`X-Filename` необязателен: передайте `encodeURIComponent(file.name)`, чтобы имя
с кириллицей прошло через HTTP-заголовок. Backend очищает имя и устанавливает
расширение по типу содержимого. Без имени используется `receipt.pdf/png/jpg`.
Показывайте имя как обычный текст.

```ts
const allowedTypes = ['application/pdf', 'image/png', 'image/jpeg'];
if (!allowedTypes.includes(file.type) || file.size < 1 || file.size > 5 * 1024 * 1024) {
  throw new Error('Выберите PDF, PNG или JPEG размером до 5 МиБ');
}

const response = await fetch(`/api/v1/payment-occurrences/${occurrenceId}/receipt`, {
  method: 'PUT',
  credentials: 'include',
  headers: {
    'Content-Type': file.type,
    'X-Filename': encodeURIComponent(file.name),
    'X-CSRF-Token': csrfToken,
  },
  body: file,
});
if (!response.ok) {
  // Разберите обычный JSON error и покажите сообщение/ошибку поля.
  throw await response.json();
}
const receipt = await response.json();
```

Клиент для JSON нельзя применять к этой загрузке, если он автоматически вызывает
`JSON.stringify(body)` или задаёт `Content-Type: application/json`.

Пример ответа на PDF размером 12 345 байт:

```json
{
  "id": "d02911df-f7d8-4262-bad6-d60e03e5edd6",
  "kind": "file",
  "url": null,
  "filename": "Чек.pdf",
  "content_type": "application/pdf",
  "size_bytes": 12345,
  "uploaded_at": "2026-10-24T10:05:00Z"
}
```

Метаданные не содержат байты файла. Повторный идентичный PUT не меняет
`uploaded_at` и не создаёт лишнее событие журнала. При замене ID вложения сохраняется.

### Скачивание

Скачивание требует действующей cookie-сессии; публичной ссылки на файл нет.
Сделайте GET с `credentials: 'include'`, проверьте HTTP-статус до чтения `blob`,
создайте временный `URL.createObjectURL(blob)` и скачайте через ссылку с
`download={receipt.filename}`. После скачивания освободите URL через
`URL.revokeObjectURL`. Не пытайтесь прочитать файл через `response.json()`.

Backend возвращает исходный MIME-тип, `Content-Disposition: attachment` с безопасным
именем `receipt.pdf/png/jpg`, `X-Content-Type-Options: nosniff` и запрет кеширования.
Для отображаемого имени используйте метаданные, а не разбор download-заголовка.

### Ошибки чеков и ссылок

| HTTP / код | Действие frontend |
| --- | --- |
| `400 INVALID_JSON` | Исправить формат JSON запроса со ссылкой |
| `401 AUTH_REQUIRED` | Повторный вход |
| `403 CSRF_FAILED` | Обновить состояние авторизации и CSRF-токен |
| `403 ORIGIN_NOT_ALLOWED` | Проверить адрес frontend / `ALLOWED_ORIGINS` |
| `404 PAYMENT_OCCURRENCE_NOT_FOUND` | Период отсутствует; обновить список |
| `404 RECEIPT_FILE_NOT_FOUND` | Вложения нет либо оно заменено ссылкой; обновить метаданные |
| `413 RECEIPT_TOO_LARGE` | Выбрать файл до 5 МиБ |
| `415 UNSUPPORTED_RECEIPT_TYPE` | Выбрать PDF/PNG/JPEG либо отправить ссылку в JSON |
| `422 VALIDATION_ERROR` | Показать `error.details`; поле `url`, `file`, заголовок или параметр |

Для неверного содержимого файла detail содержит `field: "file"` и
`code: "INVALID_RECEIPT_FILE"`. Для неверной ссылки это поле `url` с кодом
валидации `INVALID_VALUE` либо ограничением длины. JSON-тело ссылки ограничено
64 КиБ; превышение также возвращает `413 RECEIPT_TOO_LARGE`.

### Оплата и вложение — отдельные операции

Прикрепление/замена/удаление чека **не меняет** `status` и `paid_on` периода.
Отметка оплаты через существующий PATCH периода не создаёт и не удаляет вложение.
Обе роли могут управлять вложением также у неоплаченного периода и у периода
остановленного правила.

Если форма объединяет «Отметить оплату» и «Прикрепить чек», это два запроса и две
транзакции. Показывайте частичный результат: например, оплата сохранилась, загрузка
не удалась. Не сообщайте, что оплата отменена, и не отправляйте её повторно только
из-за ошибки загрузки. После успешной оплаты обновите бюджет и данные периода;
после изменения вложения — его метаданные.

Изменения вложений попадают в административный журнал как
`payment.receipt_updated` / `payment.receipt_deleted`. Журнал содержит автора,
период и тип вложения («Файл» / «Ссылка»), без содержимого документа, имени файла
или URL с потенциально приватными параметрами.

## Проверка подключения

1. Загрузить месяц и год бюджета; годовые итоги равны сумме месяцев, валюты раздельны.
2. В будущем году прогноз показан отдельно; его нельзя оплатить без реального периода.
3. Отметить и отменить оплату реального периода; бюджет обновляется по месяцу срока.
4. Прикрепить ссылку, заменить её PDF, скачать файл, удалить вложение.
5. Проверить те же действия обычным пользователем и для остановленного правила.
6. Проверить слишком большой файл, неверный тип/содержимое, не-HTTPS ссылку,
   истёкшую сессию и ошибку одного из двух запросов общей формы.
