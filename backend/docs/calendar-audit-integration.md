# Подключение календаря и журнала действий

Ветка интеграции включает интерфейс календаря и журнала из
`feat/calendar-audit-ui` поверх `main`. Оба экрана подключены к серверному API;
в real-режиме демонстрационные данные не подставляются при ошибке запроса.

## Календарь: существующий API

Новый маршрут для календаря не требуется. Обе авторизованные роли используют:

- `GET /api/v1/payment-occurrences` — все периоды выбранного месяца;
- `GET /api/v1/payment-occurrences/{id}` — подробности периода;
- `PATCH /api/v1/payment-occurrences/{id}` — отметить оплату, исправить фактическую дату
  или отменить оплату. Для изменения нужны cookie, допустимый `Origin` и `X-CSRF-Token`.

Пример загрузки месяца:

```http
GET /api/v1/payment-occurrences?date_from=2026-10-01&date_to=2026-10-31&limit=100&offset=0
```

`date_from` и `date_to` включительны и ограничивают `due_date` — срок оплаты,
а не `paid_on`. Фильтры: `currency=RUB|USD|EUR`, `status=paid|unpaid`,
`is_overdue=true|false`, `recurring_payment_id=UUID`. Для просроченных UI передаёт
`status=unpaid&is_overdue=true`; для всех статусов параметр `status` опускается.

Ответ: `{items, total, limit, offset}`. `limit` — от 1 до 100, по умолчанию 50;
`offset` — неотрицательное число. Порядок: `due_date`, затем `id` по возрастанию.
Календарь должен дочитать все страницы, не ограничиваться первыми 100 записями.
Изменение `total` или дубликаты во время загрузки требуют обновить месяц целиком.

Каждый период содержит:

```json
{
  "id": "UUID периода",
  "recurring_payment_id": "UUID регулярного платежа",
  "title": "Аренда",
  "amount": "12345.67",
  "currency": "RUB",
  "due_date": "2026-10-31",
  "status": "paid",
  "paid_on": "2026-10-30",
  "is_overdue": false,
  "paid_late": false,
  "days_late": 0,
  "recurring_payment_is_active": true
}
```

Суммы остаются десятичными строками, валюты не складываются между собой. Даты
`YYYY-MM-DD` — календарные даты, их не следует преобразовывать через часовой пояс
браузера. Статусы и просрочку вычисляет сервер по бизнес-дате МСК.

Прекращённые правила и ранее созданные периоды сохраняются; UI использует
`recurring_payment_is_active=false` для пометки. Период прекращённого правила по-прежнему
можно отметить оплаченным. Календарь показывает только уже сформированные периоды.
Чтение будущего месяца не создаёт новые периоды или напоминания; пустой месяц не
является прогнозом расходов.

## Журнал: долговечный серверный аудит

`GET /api/v1/audit-events` доступен только администратору. Обычная роль получает
`403 FORBIDDEN`, неавторизованный запрос — `401 AUTH_REQUIRED`. Миграция `0005`
добавляет хранение аудита поверх существующего head `0004`; перед запуском новой
версии нужно выполнить `uv run --locked alembic upgrade head` из `backend`.

Параметры запроса:

| Параметр | Значение |
| --- | --- |
| `date_from`, `date_to` | Необязательные даты `YYYY-MM-DD`, включительно по календарным дням МСК; можно передать одну границу |
| `actor` | Подстрока логина автора без учёта регистра, до 64 символов |
| `action` | Одно из действий ниже |
| `query` | Поиск без учёта регистра по автору, названию объекта или русскому названию действия, до 200 символов |
| `limit` | 1–100, по умолчанию 50; интерфейс использует 12 или 24 |
| `offset` | Неотрицательное целое число |

Пустые текстовые фильтры следует опускать. `q` используется в адресной строке
frontend, но HTTP-параметр API называется **`query`**. Неверные параметры, диапазон дат
или неизвестные query-поля возвращают `422` в общем формате ошибок приложения.

Ответ:

```json
{
  "items": [
    {
      "id": "UUID события",
      "occurred_at": "2026-10-23T12:00:00Z",
      "actor": {"id": "UUID автора", "username": "admin"},
      "action": "payment.paid",
      "entity": {"type": "payment", "id": "UUID правила", "title": "Аренда"},
      "changes": [
        {"field": "status", "label": "Статус", "before": "Не оплачено", "after": "Оплачено"},
        {"field": "paid_on", "label": "Дата оплаты", "before": null, "after": "2026-10-23"}
      ]
    }
  ],
  "total": 1,
  "limit": 12,
  "offset": 0
}
```

Порядок событий: `occurred_at DESC`, затем `id DESC`. Время задаёт сервер и
возвращает в UTC; отображать и группировать следует по МСК. Фильтр одного дня,
например `2026-10-23`, включает UTC-интервал с `2026-10-22T21:00:00Z`
до `2026-10-23T21:00:00Z`, исключая правую границу.

Поддерживаемые действия:

| Действие | Когда записывается |
| --- | --- |
| `payment.created` | Создан регулярный платёж |
| `payment.stopped` | Активный регулярный платёж прекращён |
| `payment.paid` | Неоплаченный период отмечен оплаченным |
| `payment.unpaid` | Отметка оплаты отменена |
| `payment.date_changed` | Изменена фактическая дата уже оплаченного периода |
| `payment.receipt_updated` | Добавлено или заменено подтверждение оплаты |
| `payment.receipt_deleted` | Удалено подтверждение оплаты |
| `user.created` | Создан пользователь |
| `user.updated` | Администратор изменил логин или пароль пользователя |
| `user.deleted` | Пользователь удалён |
| `password.changed` | Пользователь изменил собственный пароль |

`entity.type` — `payment`, `user` или `account`. Для всех платёжных событий,
включая изменение отдельного периода, `entity.id` — ID **регулярного платежа**:
по нему открывается история. Самостоятельная смена пароля относится к `account`.

Автор и название объекта сохраняются как снимки на момент события и не исчезают
после удаления или переименования пользователя. `changes[].before/after` — строки
или `null`. Для смены собственного пароля `changes` пустой; при административном
изменении только пароля также может не быть отображаемых полей. Пароли, хеши,
cookie, токены и прочие секреты в аудит не попадают. Для подтверждений оплаты
сохраняются только срок периода и тип подтверждения (`Файл`/`Ссылка`);
URL, содержимое и имя файла в журнал не копируются.

Успешная операция и её событие фиксируются в одной транзакции. Отклонённые запросы,
откат транзакции, PATCH без изменений и повторное прекращение уже остановленного
правила не добавляют ложных событий. Старые операции, совершённые до подключения
аудита, не восстанавливаются выдуманными записями. Демо-журнал frontend остаётся
отдельным набором примеров.

## Подключение frontend и совместная проверка

В `frontend/src/api/client.ts` метод `listAuditEvents` выполняет реальный запрос
`request<AuditPage>('/audit-events' + query(filters))`. Экран показывает обычные
ошибки с повтором загрузки и не подменяет их демонстрационными событиями.

Типы в `frontend/src/types/activity.ts`, таблица действий и формат страниц уже
соответствуют описанной модели, включая оба события подтверждений оплаты.
Отдельный HTTP-запрос подробностей события не нужен:
`changes` приходит в списке. После успешного изменения данных следует обновлять
журнал через существующий счётчик `revision`; скрытая вкладка не заменяет проверку
прав на сервере.

Для совместной проверки: создать платёж, отметить оплату, исправить дату, отменить
отметку и прекратить правило; проверить календарь и по одному событию для каждого
изменения. Повторить операцию без изменений — новое событие не должно появиться.
Проверить журнал обычной ролью (`403`), даты на границе МСК, фильтры и страницы,
удалённого пользователя и отсутствие секретов. PostgreSQL-проверки backend
запускаются штатным `uv run --locked python scripts/test_postgres.py`.
