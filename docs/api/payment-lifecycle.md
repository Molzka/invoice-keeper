# Дополнительные возможности платежей

Cookie, Origin, CSRF и единый формат ошибок действуют для всех изменений. День определяется в часовом поясе приложения. Суммы передаются строками с двумя десятичными знаками. После неизвестного результата запроса frontend сначала предлагает проверить состояние; автоматического повтора мутации нет.

## Разовый платёж

`POST /api/v1/one-time-payments`, только администратор:

```json
{"title":"Разовая услуга","amount":"45000.50","currency":"RUB","due_date":"2026-10-24"}
```

Успех: `201 PaymentOccurrence`. Внутри хранится правило `periodicity=once` с одним периодом. Оно не создаёт следующих обязательств. На странице регулярных платежей используется фильтр `periodicity=recurring`; POST регулярного правила принимает `daily`, `weekly`, `monthly`, `yearly` и `recurrence_interval` от 1 до 365 (по умолчанию 1).

## Сумма и валюта

- `PATCH /payment-occurrences/{id}/amount`: `{amount,currency}`, администратор, неоплаченный и не удалённый период. Ответ `PaymentOccurrence`. Прочие периоды не меняются.
- `PATCH /recurring-payments/{id}`: `{amount,currency,title?}`, администратор, активное повторяющееся правило. Название меняется сразу для всего платежа; новые сумма и валюта действуют с первого числа следующего месяца. Ответ `{payment,effective_from,updated_periods,preserved_custom_periods}`. Прежний запрос без `title` сохраняет свой смысл.
- Оплаченные, текущие/прошлые и индивидуально исправленные периоды защищены от массового изменения. В индивидуальном периоде сохраняется `amount_is_custom=true`.
- Сводка, бюджет и Telegram используют снимки суммы/валюты периода; прогноз использует условия правила.

## Название и включение повторения

`PATCH /payment-occurrences/{id}/details`, только администратор:

```json
{"title":"Хостинг проекта","amount":"15.25","currency":"USD","periodicity":"monthly"}
```

Ответ — обновлённый `PaymentOccurrence`. `title` обязателен: от 1 до 200 Unicode-символов после обрезки крайних пробелов. Название общее для всех периодов правила. `amount` и `currency` можно опустить или передать вместе; изменение касается только выбранного неоплаченного периода. Оплаченный период допускает переименование и включение повторения, но переданные поля суммы/валюты возвращают `409 PAYMENT_ALREADY_PAID`. `null`, неизвестные поля и неполная пара суммы/валюты дают `422`. Удалённый период защищён `409 PAYMENT_CANCELLED`.

Необязательный `periodicity: "monthly"` превращает разовый платёж в ежемесячный. Исходные UUID, отметка оплаты и подтверждение сохраняются. Расписание начинается от исходного срока, включая пропущенные месяцы; короткие месяцы используют последний день и затем возвращаются к исходному числу. Новые периоды используют сумму и валюту выбранного периода. Существующие периоды не дублируются при повторе запроса. Чтобы прекратить месячные обязательства, используется отдельное действие прекращения повторения; `periodicity: "once"` здесь не принимается.

Все поля, создание периодов, очередь напоминаний и аудит фиксируются одной транзакцией с общей блокировкой платежей. Новая миграция для этого маршрута не нужна.

## Прекращение и удаление

`DELETE /recurring-payments/{id}` сохраняет прежний смысл: прекратить повторение и напоминания, сохранить существующие обязательства в итогах.

Отдельные операции администратора:

- `DELETE /payment-occurrences/{id}` → `204`: исключает неоплаченный период из обязательств, итогов и напоминаний, сохраняя `is_cancelled=true`. Наличие записи не даёт генератору создать её заново. Для разового платежа также архивируется внутреннее правило.
- `POST /recurring-payments/{id}/archive` без тела → `204`: `is_archived=true`, `is_active=false`, все неоплаченные периоды исключены из обязательств. Оплаченные периоды и материалы сохраняются.
- Повтор удаления идемпотентен. Оплаченный период защищён ответом `409 PAYMENT_ALREADY_PAID`; изменение удалённого периода — `409 PAYMENT_CANCELLED`.
- Списки по умолчанию скрывают удалённые записи. `include_cancelled=true` для периодов и `include_archived=true` для правил включают историю. Удалённые периоды и их материалы доступны только для просмотра.
- Изменения и удаления записываются в журнал в той же транзакции. Журнал доступен только администратору.

## Бюджет

`GET /payments/budget?year=2026&month=10`; без month возвращается год. Обе роли. Серверные итоги отдельно для RUB/USD/EUR: `planned = paid + unpaid + forecast`; `overdue` входит в `unpaid`. Прогноз не создаёт периоды или напоминания. Переход по сумме открывает существующие периоды истории. `503 PERIODS_NOT_READY` не изображается нулевыми итогами. Масштаб, год и месяц сохраняются в URL.

## Чеки и ссылки

Существующий контракт коллеги:

- `GET /payment-occurrences/{id}/receipt` → `PaymentReceipt | null`.
- `PUT` того же пути: JSON `{url}` с HTTPS-ссылкой либо сырое тело PDF/PNG/JPEG до 5 МиБ с percent-encoded `X-Filename`. Требуются CSRF и cookie. Подтверждение одно на период; новое заменяет предыдущее.
- `GET /payment-occurrences/{id}/receipt/file` скачивает файл с авторизацией.
- `DELETE /payment-occurrences/{id}/receipt` удаляет только материал.

Для страницы материалов добавлен `GET /payment-receipts` (обе роли): `query` до 200 символов, `currency`, `kind=all|file|link|missing`, `limit`, `offset`. Поиск и фильтры применяются на сервере до пагинации. Ответ `{items:[{occurrence,receipt}],total,limit,offset}`. Метаданные читаются без содержимого файлов; удалённые обязательства скрыты. Фильтры и страница сохраняются в URL.

## Миграции

После опубликованных миграций `0005` (журнал), `0006` (чеки), `0007` (MFA) и `0008` (заявки сотрудников) применяются `0009` (снимки сумм) и `0010` (разовые платежи и удаление). Перед запуском frontend выполнить `alembic upgrade head` обычным способом проекта. `0009` заполняет снимки существующих периодов из текущих условий правила. Миграция `0010` сохраняет все события регистрации и безопасности из `0008`; её downgrade отказывается терять уже созданные разовые платежи, удалённые обязательства и новые события журнала. Машиночитаемый контракт: `backend/openapi.json`.
