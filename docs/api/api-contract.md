# Invoice Keeper: контракт API и правила учёта v1

Дополнительные возможности описаны в [расширении контракта](payment-lifecycle.md): разовые платежи, изменение сумм, сохранённое удаление, бюджет и материалы. Обязательный DELETE регулярного правила по-прежнему означает прекращение повторения.

Контракт FastAPI и React: форматы запросов, ответов и правила учёта. Машиночитаемая версия хранится в [backend/openapi.json](../../backend/openapi.json), настройки приложения — в [вики](../README.md).

Связанные документы: [сценарий демонстрации и термины](../operations/demo-data.md), [версии и миграции](../development/team-workflow.md).

## 1. Общие правила

- Базовый путь: `/api/v1`. Тела запросов и ответов — JSON UTF-8, кроме HTML Swagger и ответов `204 No Content`.
- Имена полей и query-параметров — `snake_case`; значения перечислений — английские строчные строки.
- Ответ на создание/изменение/получение одной записи — сам объект без оболочки `data`.
- Неизвестные поля входного JSON и query-параметры отклоняются с `422`, чтобы опечатки не игнорировались. Параметры берутся из описанных ниже схем.
- `null` означает явно отсутствующее значение; это отличается от пропущенного поля в PATCH.
- Защищённые операции доступны только с действующей серверной сессией. Обычный пользователь видит общий список и может менять оплату периодов. Администратор дополнительно управляет регулярными платежами и обычными пользователями.
- Публичной регистрации, конвертации валют и редактирования регулярного правила в обязательном API нет.

Согласованное расширение добавляет заявки сотрудников с одобрением администратором и добровольную MFA. Оно не создаёт аккаунт до решения и не меняет роли или обязательный финансовый контракт. [Маршруты и безопасность расширения](../development/access-security-plan.md), [инструкция сотруднику и администратору](../operations/account-security.md).

| Значение | Формат API | Представление в приложении/БД |
|---|---|---|
| Идентификатор | UUID-строка | PostgreSQL `UUID` |
| Сумма одного платежа | Строка с точкой и ровно двумя знаками, например `"45000.00"` | Python `Decimal`, PostgreSQL `NUMERIC(14,2)` |
| Валюта | `"RUB"`, `"USD"`, `"EUR"` | Одна из трёх разрешённых валют |
| Срок и фактическая дата оплаты | `"2026-10-31"` | Python `date`, PostgreSQL `DATE` |
| Момент создания/технического события | UTC ISO 8601, например `"2026-10-23T09:30:00Z"` | timezone-aware datetime, PostgreSQL `TIMESTAMPTZ` |
| Часовой пояс бизнес-правил | Имя IANA, по умолчанию `"Europe/Moscow"` | Валидируемая настройка `APP_TIMEZONE`; поле `timezone` в `AuthResponse` |
| Статус периода | `"unpaid"` / `"paid"` | Отдельно от признаков просрочки |
| Роль | `"admin"` / `"user"` | Проверяется сервером |

Сумма отдельного платежа положительная, от `"0.01"` до `"999999999999.99"`. Принимать только десятичные строки без знака, экспоненты, запятой и разделителей тысяч; избыточные десятичные знаки отклонять, а не молча округлять. Для итогов также используются строки с двумя знаками, но сумма многих записей может превысить размер одной записи. React показывает суммы и итоги сервера, а не пересчитывает деньги через JavaScript `Number`.

`NUMERIC` предназначен для точных десятичных значений; фиксированная шкала БД сама по себе не заменяет проверку входа в API. [PostgreSQL: числовые типы](https://www.postgresql.org/docs/current/datatype-numeric.html).

Календарные даты не превращаем в UTC-полночь: строка `2026-10-31` остаётся 31 октября независимо от часового пояса браузера. «Сегодня», границы месяца и расписание напоминаний определяются в `APP_TIMEZONE`. Backend проверяет имя по базе IANA при запуске; API и worker должны получать одно значение. Браузер использует `timezone` из ответа авторизации, а не пояс устройства; Telegram-клиент получает пояс при входе в API. Технические моменты храним в UTC; при отображении используем пояс приложения. Контейнер может работать в UTC; правила приложения используют настройку явно. В образе должны быть доступны данные часовых поясов для `zoneinfo`. [PostgreSQL: даты и время](https://www.postgresql.org/docs/current/datatype-datetime.html), [Python zoneinfo](https://docs.python.org/3/library/zoneinfo.html).

## 2. Списки и пагинация

Три списочных маршрута (`users`, `recurring-payments`, `payment-occurrences`) принимают `limit` от 1 до 100, по умолчанию 50, и `offset` от 0, по умолчанию 0. `total` — число подходящих записей до применения limit/offset. Пустой список — `200` с `items: []` и `total: 0`.

```json
{
  "items": [],
  "total": 0,
  "limit": 50,
  "offset": 0
}
```

Сортировка фиксирована: пользователи — `username`, затем `id`; регулярные платежи — `created_at` по убыванию, затем `id`; периоды — `due_date`, затем `id`, по возрастанию.

## 3. Сессии и авторизация

Сервер создаёт случайный непрозрачный идентификатор сессии. В PostgreSQL хранится запись сессии с пользователем, сроком действия и хешем идентификатора; в браузере — cookie `session_id`. Пароли хешируются через `pwdlib` с Argon2. Значение cookie, хеш пароля и токен бота в JSON и журналах не выдаются.

Для первой версии принят абсолютный срок сессии 7 дней (`SESSION_TTL_SECONDS=604800`). При новом входе идентификатор обновляется; при выходе текущая сессия отзывается и cookie очищается. Удаление пользователя или изменение его пароля отзывает его сессии. Удаление пользователя не удаляет платёжную историю.

Cookie: `HttpOnly`, `SameSite=Lax`, `Path=/`, без `Domain`; на HTTPS — `Secure`. Для локального HTTP `Secure` выключается только отдельной настройкой разработки. Интерфейс и API обслуживаются с одного origin.

На всех `POST`, `PATCH`, `DELETE`, включая вход, проверяется `Origin` по разрешённому списку: отсутствующий заголовок, значение `null` и посторонний origin дают `403 ORIGIN_NOT_ALLOWED`. Нельзя обходить проверку по предположению, что запрос без заголовка пришёл не из браузера. Вход принимает только JSON; CSRF-токен до входа не нужен. Успешный вход и `GET /auth/me` возвращают токен, привязанный к сессии. Остальные `POST`, `PATCH`, `DELETE`, включая выход, требуют заголовок `X-CSRF-Token`. Для ручных API-проверок нужно передавать разрешённый Origin, cookie и токен. CORS не должен разрешать произвольный origin с credentials. [OWASP: CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

**POST `/api/v1/auth/login`**, доступен без сессии:

```json
{
  "username": "ivan",
  "password": "example-password-only"
}
```

Успех: `200`, заголовок `Set-Cookie`, тело:

```json
{
  "user": {
    "id": "9b3a2a64-c7a9-4dd0-98f4-e5e1458ad1d6",
    "username": "ivan",
    "role": "user",
    "created_at": "2026-10-23T09:00:00Z"
  },
  "csrf_token": "example-token-only",
  "timezone": "Europe/Moscow"
}
```

Неверный логин или пароль — `401 INVALID_CREDENTIALS` с одинаковым сообщением; не раскрываем, существует ли пользователь. Авторизованные ответы login/me имеют `Cache-Control: no-store`.

**GET `/api/v1/auth/me`** возвращает `200` с той же формой `{user, csrf_token, timezone}` для текущей сессии; при отсутствии или истечении сессии — `401 AUTH_REQUIRED`. Он не создаёт анонимную сессию. `timezone` — обязательная строка с именем IANA из настроек приложения; поле присутствует также в ответах login и успешной смены пароля. Клиент обновляет его вместе с сессией.

**POST `/api/v1/auth/logout`** не имеет тела запроса. При действующей сессии и правильном CSRF-токене возвращает `204` без тела. При отсутствующей/истёкшей сессии — `401`; клиент очищает своё состояние входа и в этом случае.

**POST `/api/v1/auth/change-password`** доступен только обычному пользователю. Принимает `current_password` и `new_password`, требует Origin, cookie и CSRF. Успех — `200` с `AuthResponse`, новой cookie и отзывом остальных сессий. Для администратора возвращает `403 ADMIN_ACCOUNT_PROTECTED`, сохраняя пароль и сессии; соответствующего действия в панели администратора нет. Это сохраняет запрет ТЗ на управление учётной записью администратора через панель и API. Подробности — в [контракте смены пароля](frontend-password-change.md).

## 4. Пользователи

Все четыре операции доступны только администратору. Администратор создаётся из `.env` и не входит в список редактируемых обычных пользователей. Его UUID можно получать через `auth/me`, но операции `/users/{id}` не позволяют менять или удалять его (`403 ADMIN_ACCOUNT_PROTECTED`).

Форма ответа `User` — `id`, `username`, `role`, `created_at`, как в примере входа. Поля пароля отсутствуют.

Принятая политика: `username` — 3–64 символа `[a-z0-9_.-]`, без пробелов, уникален; пароль — 8–128 символов, не обрезается и не нормализуется. Не добавлять логин администратора повторно как обычного пользователя. Дублирование username — `409 USERNAME_TAKEN`.

| Метод и путь | Вход | Успешный ответ |
|---|---|---|
| GET `/api/v1/users` | Только limit/offset | `200` со списком `User` |
| POST `/api/v1/users` | Обязательные `username`, `password` | `201` и `User` с `role: "user"` |
| PATCH `/api/v1/users/{id}` | `username` и/или `password`; минимум одно поле | `200` и обновлённый `User` |
| DELETE `/api/v1/users/{id}` | Без тела | `204` без тела |

В запросах создания/изменения `role` запрещено как неизвестное поле. В PATCH пропущенное поле сохраняется, `null` для username/password не допускается. Неизвестный UUID ресурса — `404 USER_NOT_FOUND`; синтаксически некорректный UUID — `422`.

## 5. Регулярные платежи

**POST `/api/v1/recurring-payments`**, только администратор:

```json
{
  "title": "Аренда офиса",
  "amount": "45000.00",
  "currency": "RUB",
  "first_due_date": "2026-10-31",
  "periodicity": "monthly"
}
```

Все пять полей обязательны. `title` — 1–200 символов после обрезки пробелов по краям, названия могут повторяться. `periodicity` пока только `monthly`. `first_due_date` — первый срок; прошлые даты допустимы, чтобы учитывать уже возникшие обязательства. Ограничения суммы/валюты — из раздела 1.

Успех: `201`, объект `RecurringPayment`:

```json
{
  "id": "f059226b-8948-4da4-b33e-3b22844b4587",
  "title": "Аренда офиса",
  "amount": "45000.00",
  "currency": "RUB",
  "first_due_date": "2026-10-31",
  "next_due_date": "2026-10-31",
  "periodicity": "monthly",
  "anchor_day": 31,
  "is_active": true,
  "created_at": "2026-10-23T09:30:00Z"
}
```

`anchor_day` сервер берёт из первого срока, клиент его не задаёт. `next_due_date` — ближайшая плановая дата не раньше сегодняшнего дня в часовом поясе приложения, независимо от отметки оплаты; просроченные обязательства смотрим в списке периодов. У прекращённого правила `next_due_date: null`.

**GET `/api/v1/recurring-payments`** доступен обеим ролям. Параметры: `limit`, `offset`, необязательный `is_active` (boolean). Без фильтра возвращаются активные и прекращённые правила. Ответ `200` — списочная оболочка с `RecurringPayment`.

**DELETE `/api/v1/recurring-payments/{id}`**, только администратор: прекращает правило (`is_active=false`), останавливает новое формирование и все дальнейшие напоминания по нему, возвращает `204`. Повтор для уже прекращённого правила также `204`; неизвестный id — `404 RECURRING_PAYMENT_NOT_FOUND`.

Выбранная простая семантика: уже созданные периоды остаются в истории, допускают исправление оплаты и входят в сводку по своему сроку, даже если правило прекращено. Прекращение повторения само по себе не списывает ранее созданные обязательства. Отмена будущего обязательства — отдельная возможность, которую в v1 не добавляем.

Создание правила, всех необходимых периодов с first_due_date по конец текущего месяца и заданий немедленного напоминания фиксируется одной транзакцией PostgreSQL. Дополнительно должен существовать ближайший будущий период: если первый срок ещё за пределами текущего месяца, создаётся именно он; если все сроки текущего месяца прошли, создаётся следующий. Поэтому после успешного POST история с прошлой first_due_date уже полная. Отправка Telegram происходит после commit в обработчике участника 1. Сбой Telegram не отменяет сохранение платежа и не превращает успешный POST в ошибку.

Если правило прекращается после простоя обработчика, перед сменой is_active в той же транзакции завершается создание отсутствующих периодов, срок которых уже наступил. Новые будущие периоды ради DELETE не создаются. Прекращение не должно обрывать заполнение уже возникшей истории; ограничения уникальности исключают дубли при одновременной работе обработчика.

## 6. Периоды и изменение оплаты

Форма ответа `PaymentOccurrence` (в этом примере сегодня в часовом поясе приложения — 23 октября):

```json
{
  "id": "349e2b3b-1683-490a-a0ac-608cefc30248",
  "recurring_payment_id": "f059226b-8948-4da4-b33e-3b22844b4587",
  "title": "Аренда офиса",
  "amount": "45000.00",
  "currency": "RUB",
  "due_date": "2026-10-31",
  "status": "unpaid",
  "paid_on": null,
  "is_overdue": false,
  "paid_late": false,
  "days_late": 0,
  "recurring_payment_is_active": true
}
```

Поля title/amount/currency включены в ответ, чтобы интерфейсу не приходилось загружать каждый регулярный платёж отдельным запросом. Период всегда имеет собственный UUID и связь с регулярным платежом.

| Метод и путь | Вход | Успешный ответ |
|---|---|---|
| GET `/api/v1/payment-occurrences` | Фильтры ниже, limit/offset | `200`, списочная оболочка с `PaymentOccurrence` |
| GET `/api/v1/payment-occurrences/{id}` | UUID периода | `200`, один `PaymentOccurrence` |
| PATCH `/api/v1/payment-occurrences/{id}` | Одна из двух форм ниже | `200`, обновлённый `PaymentOccurrence` |

Обе роли имеют доступ к этим операциям. Неизвестный UUID периода — `404 PAYMENT_OCCURRENCE_NOT_FOUND`.

Фильтры списка: `date_from`, `date_to` по **сроку** включительно; `status=paid|unpaid`; `currency=RUB|USD|EUR`; `recurring_payment_id`; `is_overdue=true|false`. Все фильтры применяются через И. Без фильтров видна вся созданная история, включая периоды прекращённых правил. Если задана только одна граница даты, другая не ограничена; если обе — `date_from <= date_to`.

Подтвердить оплату или исправить её дату:

```json
{
  "status": "paid",
  "paid_on": "2026-10-23"
}
```

Отменить оплату:

```json
{
  "status": "unpaid",
  "paid_on": null
}
```

Для этой операции оба поля обязательны и изменяются атомарно. Пустое тело, отсутствие одного из полей, `paid + null`, `unpaid + дата`, будущая фактическая дата в часовом поясе приложения или попытка изменить due_date/amount дают `422`. Досрочная оплата разрешена. Исправление даты — повтор первой формы с другой датой. Повтор одинаковой формы безопасен и не создаёт новую оплату или период; при конкурирующих изменениях действует последний успешно зафиксированный запрос.

Просрочку сервер вычисляет, а не принимает от клиента:

- `is_overdue = status == "unpaid" AND today_moscow > due_date` — текущая задолженность с пропущенным сроком.
- `paid_late = status == "paid" AND paid_on > due_date` — уже оплачено, но с опозданием.
- `days_late = max(0, (paid_on для paid, иначе today_moscow) - due_date)` в календарных днях.

Оплата в срок даёт оба флага `false`. При исправлении поздней фактической даты на своевременную `paid_late` становится `false`, days_late — 0; due_date не меняется. В интерфейсе поздняя оплата показывается как «Оплачено с опозданием», а неоплаченная просрочка — как «Просрочено».

## 7. Итоговые суммы: что именно складываем

**GET `/api/v1/payments/summary`**, обе роли. Это сводка обязательств **по сроку оплаты**, а не движение денег по фактической дате.

Параметры: необязательная пара `date_from`, `date_to` в формате даты. Без обоих используется текущий календарный месяц в часовом поясе приложения. Если передано только одно значение — `422`. Границы включительны, начало не позже конца. В v1 конец не может быть позже последнего дня текущего месяца: будущие бюджеты — отдельная необязательная функция кейса.

Пример: `/api/v1/payments/summary?date_from=2026-10-01&date_to=2026-10-31`.

```json
{
  "date_from": "2026-10-01",
  "date_to": "2026-10-31",
  "as_of_date": "2026-10-23",
  "timezone": "Europe/Moscow",
  "totals": {
    "RUB": {
      "planned": "60000.00",
      "paid": "45000.00",
      "unpaid": "15000.00",
      "overdue": "5000.00"
    },
    "USD": {
      "planned": "25.00",
      "paid": "0.00",
      "unpaid": "25.00",
      "overdue": "0.00"
    },
    "EUR": {
      "planned": "9.00",
      "paid": "9.00",
      "unpaid": "0.00",
      "overdue": "0.00"
    }
  }
}
```

| Поле | Какие периоды суммируются |
|---|---|
| planned | Все периоды со сроком внутри выбранного диапазона |
| paid | Из них те, которые сейчас отмечены оплаченными |
| unpaid | Из них те, которые сейчас не оплачены |
| overdue | Часть unpaid со сроком раньше as_of_date |

Для каждой валюты `planned = paid + unpaid`, а `overdue <= unpaid`. Просрочка уже входит в неоплаченное — складывать их ещё раз нельзя. Все три валюты присутствуют всегда; при отсутствии записей каждое значение равно `"0.00"`.

Состояние берётся на момент запроса. Октябрьский платёж, оплаченный в ноябре, входит в paid октябрьской сводки. Платёж с ноябрьским сроком, оплаченный в октябре, входит в ноябрьский диапазон, когда он доступен. Это не исторический снимок «что было оплачено на конец месяца» и не отчёт по движению денег.

Сводка строится по всем подходящим периодам в БД, а не только по загруженной странице списка. Уже созданные периоды прекращённых правил сохраняют участие в итогах согласно разделу 5.

Участники 1 и 2 обеспечивают полноту периодов: при создании правила действует транзакционная гарантия раздела 5, а после простоя обработчик восстанавливает недостающие периоды и ближайший будущий срок. Перед выдачей сводки за любой диапазон бэкенд проверяет полноту подходящей истории активных правил до date_to; пока восстановление не завершено, возвращает `503 PERIODS_NOT_READY`, а не неполную сумму. Для прекращённых правил используется сохранённая история с гарантией завершённого учёта наступивших сроков на момент прекращения. Это внутренняя проверка готовности, не генерация произвольного будущего бюджета по GET.

## 8. Короткие месяцы и момент напоминания

Исходный день месяца сохраняется в `anchor_day`. Срок каждого нового периода рассчитывается от этого дня и целевого месяца:

`day = min(anchor_day, число дней в целевом месяце)`.

| Исходное правило | Январь | Февраль | Март | Апрель |
|---|---|---|---|---|
| 31-го, 2027 год | 31.01 | 28.02 | 31.03 | 30.04 |
| 30-го, 2027 год | 30.01 | 28.02 | 30.03 | 30.04 |
| 31-го, 2028 год | 31.01 | 29.02 | 31.03 | 30.04 |

Нельзя последовательно прибавлять месяц к уже сдвинутому февралю: иначе правило 31-го может превратиться в правило 28-го. Новая дата всегда считается от исходного anchor_day. Если пользователь изначально выбрал 28 февраля, anchor_day равен 28 — это не отдельное правило «последний день каждого месяца».

Принятое правило: планировать обычное напоминание на 00:00 в `APP_TIMEZONE` календарной даты `due_date - 3 дня`; обработчик подбирает наступившие задания с небольшим согласованным интервалом. Это календарные дни; при переходе на летнее/зимнее время интервал в часах может отличаться от 72 часов. Для добавленного позже этого момента неоплаченного периода задание сразу готово к обработке после commit, без ожидания следующего суточного запуска. Для исторических просроченных периодов, впервые появившихся при добавлении/восстановлении правила, применяется тот же отбор; по каждому периоду не более одного подтверждённого напоминания. При массовом добавлении старой истории команда должна учитывать число таких сообщений.

Повторное исправление даты или отмена оплаты не сбрасывает сохранённый факт уже состоявшегося напоминания. Оплаченные периоды и все периоды прекращённого правила исключаются из новых отправок. Неизвестный результат сетевого вызова не считать автоматически доказанным неуспехом: его обработка принадлежит участнику 1.

## 9. Единый формат ошибок

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Проверьте поля запроса",
    "details": [
      {
        "field": "amount",
        "code": "INVALID_MONEY_FORMAT",
        "message": "Передайте положительную сумму строкой с двумя знаками после точки"
      }
    ]
  }
}
```

`error.code`, `error.message`, `error.details` присутствуют всегда; details — массив, пустой при отсутствии ошибок отдельных полей. Для query/path используется путь вроде `query.date_from` или `path.id`, для JSON — имя поля. React принимает решения по code, показывает message и привязывает details к полям; текст сообщения не является машинным идентификатором.

| HTTP | Примеры code | Значение |
|---|---|---|
| 400 | INVALID_JSON | Тело невозможно разобрать как JSON |
| 401 | AUTH_REQUIRED, INVALID_CREDENTIALS | Нет действующей сессии или неверные данные входа |
| 403 | FORBIDDEN, CSRF_FAILED, ORIGIN_NOT_ALLOWED, ADMIN_ACCOUNT_PROTECTED | Сессия есть, но действие запрещено; либо отклонена проверка источника запроса |
| 404 | USER_NOT_FOUND, RECURRING_PAYMENT_NOT_FOUND, PAYMENT_OCCURRENCE_NOT_FOUND | Ресурс не найден |
| 409 | USERNAME_TAKEN | Конфликт уникального имени |
| 415 | UNSUPPORTED_MEDIA_TYPE | Для операции с JSON-телом передан другой Content-Type |
| 422 | VALIDATION_ERROR | Неверное поле, сочетание полей, неизвестное поле/параметр или диапазон |
| 503 | PERIODS_NOT_READY, SERVICE_UNAVAILABLE | Данные периодов ещё восстанавливаются или сервис временно недоступен |
| 500 | INTERNAL_ERROR | Непредвиденная серверная ошибка без внутренних деталей |

Нормализация выполняется обработчиками FastAPI: ошибки валидации и HTTPException тоже приводятся к этой форме. Не выдавать одновременно стандартный ответ FastAPI `{"detail": ...}` и собственную оболочку. Для ошибок валидации не копировать исходный input целиком: в нём могут быть пароль или другие секреты. [FastAPI: обработчики ошибок](https://fastapi.tiangolo.com/tutorial/handling-errors/).

Если сеть оборвалась и JSON-ответ не получен, интерфейс показывает отдельное состояние сетевого сбоя. POST создания платежа/пользователя в v1 не имеет ключа идемпотентности: после таймаута нельзя автоматически повторять его; сначала проверить список. На время отправки форма блокирует повторное нажатие. Идемпотентность PATCH оплаты следует из установки значения, а не создания новой записи.

## 10. Swagger и передача контракта

**GET `/api/v1/docs`** возвращает `200 text/html` со Swagger UI. Сама схема не содержит платёжных данных или секретов и может быть доступна без сессии; вызовы защищённых операций из Swagger требуют тех же cookie, прав и CSRF, что React.

Текущая схема доступна через `/api/v1/openapi.json`; приложенный файл — [backend/openapi.json](../../backend/openapi.json). Экспорт после изменения API: из `backend` выполнить `uv run --locked python scripts/export_openapi.py`. Проверка без перезаписи: та же команда с `--check`. Это вспомогательный маршрут документации, сверх 15 обязательных операций. Экспорт строится из схем приложения без запущенной БД; он не заменяет проверку реальных HTTP-ответов.

Перед передачей фронтенду сверить на работающем API: один успешный ответ каждого типа, пустой список, ошибки полей, 401/403/404, обе формы PATCH оплаты, сводку с нулевыми валютами. Новые unit-тесты для этого контракта не требуются; проверка проводится HTTP-запросами и через интерфейс.
