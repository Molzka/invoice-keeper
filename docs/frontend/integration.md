# Подключение API

## Доступные маршруты

Backend подключает авторизацию, пользователей, платежи и журнал действий. Для реальных данных нужны актуальный образ backend и миграции до head (`0006`): `0005` добавляет серверный аудит, `0006` — подтверждения оплаты. Из каталога `backend` выполните `uv run --locked alembic upgrade head`. Порядок запуска описан в [README](../../README.md).

Фронтенд использует пути из [контракта API](../api/api-contract.md):

- `GET /api/v1/payments/summary`;
- `GET /api/v1/payment-occurrences`, `GET/PATCH /api/v1/payment-occurrences/{id}`;
- `GET/POST /api/v1/recurring-payments`, `DELETE /api/v1/recurring-payments/{id}`.
- `GET /api/v1/audit-events` — журнал действий, только для администратора.

Если коллекция возвращает 404, сначала проверьте версию backend и подключение маршрутов. Изменение URL клиента на случайный соседний маршрут не устраняет причину. 404 коллекции отображается как недоступный платёжный API с адресом запроса в раскрываемых технических деталях. Обычный 404 конкретного периода сохраняет сообщение сервера. 503 `PERIODS_NOT_READY` сохраняет отдельное состояние ожидания. Ошибки не подменяются демонстрационными данными или нулевыми итогами.

## Демонстрация интерфейса

Для показа интерфейса без собственных данных используйте `mock`:

- локально: `VITE_API_MODE=mock` в `.env.local`, затем перезапуск Vite;
- общий Docker Compose: `FRONTEND_API_MODE=mock` в корневом `.env`, затем `docker compose up -d --build frontend`.

Это демонстрация с тестовыми аккаунтами и фиксированной датой. Данные авторизации и пользователей в таком режиме также демонстрационные.

## Реальный backend

После обновления backend и применения миграций включите настоящий API:

- локально: `VITE_API_MODE=real`, `VITE_API_BASE_URL=/api/v1`, `API_PROXY_TARGET=http://127.0.0.1:8000`, затем перезапуск Vite;
- Docker Compose: `FRONTEND_API_MODE=real`, затем `docker compose up -d --build frontend`.

`VITE_*` в Docker встраиваются во время сборки. Одного перезапуска готового контейнера недостаточно. Платёжные запросы должны доходить через same-origin `/api/v1` до backend. Клиент отправляет cookie, получает CSRF из login/me и передаёт `X-CSRF-Token` при изменениях. Создающий POST после тайм-аута не повторяется автоматически.

Проверка подключения: реальный вход → `/auth/me` → сводка и список периодов → создание регулярного платежа → оплата периода → исправление даты → отмена отметки → история прекращённого платежа. Итоги остаются серверными, суммы передаются строками.


## Календарь и журнал действий

Календарь использует существующее API периодов и сохраняет фильтры в ссылке. В реальном режиме журнал загружает долговечные события через `/audit-events`; в демонстрации использует примеры и события текущей вкладки. Ошибки реального API не подменяются примерами. Контракт, права доступа и сценарии проверки описаны в [памятке](calendar-activity.md).

Проверка журнала: войти администратором → создать платёж → отметить и отменить оплату → открыть журнал и проверить автора, даты, изменения до/после и переход в историю платежа. При повторении операции без изменения данных новое событие появляться не должно. Пользователь с ролью `user` не видит раздел и получает `403` при прямом запросе API.

## Следующий этап: бюджет и подтверждения оплаты

Backend уже предоставляет бюджет месяца/года и хранение одного файла или ссылки
на подтверждение оплаты для периода. Их экраны реализует владелец frontend;
контракты и примеры запросов находятся в
[памятке бюджета и чеков](../api/budget-receipts.md).
Журнал поддерживает события изменения и удаления подтверждения.
