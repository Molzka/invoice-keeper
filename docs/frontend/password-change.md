# Смена собственного пароля

## Доступ из профиля

У обычного пользователя кнопка профиля с аватаром и значком ключа открывает панель «Сменить пароль». В панели показаны текущий аккаунт, три поля пароля и пояснение о сохранении текущего входа. У администратора этого действия нет: его учётная запись защищена от изменения через панель. Прямой запрос от администратора к API также отклоняется с `403 ADMIN_ACCOUNT_PROTECTED`.

На компьютере форма открывается сбоку; на ширине 320 px поля и действия помещаются без горизонтального переполнения. В панели удерживается клавиатурный фокус, у полей есть подписи, ошибки связаны с соответствующими полями. Кнопка показа пароля доступна для каждого поля и сообщает своё состояние через `aria-pressed`. После ошибки фокус переходит к первому ошибочному полю.

## Контракт и запрос

Исторический контекст подключения: реализация следовала [контракту backend на коммите `253ca9f`](https://github.com/Molzka/invoice-keeper/blob/253ca9f/backend/docs/frontend-password-change.md). На этом этапе для настоящего API требовался backend из [PR #17](https://github.com/Molzka/invoice-keeper/pull/17): на момент подключения интерфейса этот PR ещё не был объединён. Актуальный контракт находится в [памятке API](../api/frontend-password-change.md).

Клиент отправляет один `POST /auth/change-password` с `credentials: 'include'`, JSON и актуальным `X-CSRF-Token`. Относительный маршрут добавляется к настроенному API base URL, по умолчанию `/api/v1`. В теле ровно два поля:

```json
{
  "current_password": "...",
  "new_password": "..."
}
```

Подтверждение нового пароля проверяется только в интерфейсе и не передаётся в API. Пароли отправляются точно в том виде, в котором их ввели: без `trim`, смены регистра или нормализации Unicode.

Локальная проверка соответствует контракту:

- текущий пароль: от 1 до 128 кодовых точек Unicode;
- новый пароль: от 8 до 128 кодовых точек Unicode и отличается от текущего;
- подтверждение: полностью совпадает с новым паролем.

Длина считается через `Array.from`, поэтому символ за пределами BMP, например эмодзи, не считается двумя символами. Пробелы и разные формы Unicode сохраняются. Ограничения проверяются до запроса; окончательное решение о допустимости пароля принимает сервер.

## Успех и состояние сессии

Успешный ответ `200` имеет формат `AuthResponse` с пользователем, новым `csrf_token` и `timezone` — именем часового пояса приложения из базы IANA. Клиент заменяет CSRF-токен, обновляет пользователя и часовой пояс, очищает поля и закрывает панель. Текущий вход сохраняется. По контракту backend завершает остальные сессии пользователя; интерфейс сообщает об этом после подтверждённого успеха.

Если ответ смены пароля или последующая проверка `/auth/me` возвращает другой `user.id` или другую роль, интерфейс закрывает форму и предлагает войти заново. Данные другого аккаунта не применяются к открытой форме.

Защита от повторного нажатия разрешает только один запрос за раз. Пока идёт сохранение или проверка сессии, поля и закрытие панели заблокированы. Автоматического повторения POST нет.

## Ошибки и восстановление

| Ответ или ситуация | Поведение интерфейса |
| --- | --- |
| `422 CURRENT_PASSWORD_INVALID` | Ошибка у текущего пароля |
| `422 NEW_PASSWORD_UNCHANGED` | Ошибка у нового пароля |
| Другие ошибки полей | Сообщения из единого формата API у соответствующих полей |
| `401` | Общий клиент возвращает на вход |
| `403 CSRF_FAILED` | Общий клиент выполняет `/auth/me` и сверяет пользователя и роль. Для того же аккаунта обновляет CSRF; поля очищаются, форму нужно заполнить заново. При смене аккаунта или роли приложение возвращает на вход. POST автоматически не повторяется |
| `403 ORIGIN_NOT_ALLOWED` | Сообщение о запрете запросов с адреса сайта |
| `403 ADMIN_ACCOUNT_PROTECTED` | Учётная запись администратора защищена; пароль и сессии не изменены, действие в его профиле не показывается |
| `429` | Пауза повторной отправки с обратным отсчётом |
| Потеря сети, тайм-аут или нечитаемый успешный ответ | Результат смены пароля считается неопределённым; поля очищаются и повторная отправка в текущем состоянии формы блокируется |

Восстановление CSRF работает для всех действий, включая оплату, управление пользователями и выход. Например, после смены пароля в одной вкладке другая получает новую cookie, но ещё хранит старый CSRF. Её первое действие отклоняется сервером: клиент обновляет сессию и просит повторить действие вручную. При выходе появляется сообщение «Сессия обновлена. Чтобы выйти, нажмите „Выйти“ ещё раз». Если проверка сессии недоступна, интерфейс просит проверить соединение и обновить страницу; если изменился аккаунт или роль, старые формы закрываются и показывается вход. Ни один изменяющий запрос автоматически не повторяется.

При неопределённом результате пароль уже мог измениться на сервере. Интерфейс проверяет `/auth/me`, однако успешный ответ этой проверки подтверждает только действующую сессию. Он не подтверждает и не опровергает смену пароля. Пользователь получает предложение войти вручную с новым паролем, а если тот не подходит — с прежним. При неуспешной проверке сети доступна отдельная кнопка проверки сессии; она также не повторяет смену пароля.

Для `429` используется `Retry-After` в секундах. Некорректный или отсутствующий заголовок заменяется паузой 60 секунд; корректное значение ограничено сутками для таймера интерфейса. Конечное время паузы хранится в памяти `App` отдельно для текущего пользователя: закрытие и повторное открытие панели не сбрасывает отсчёт. Оно не сохраняется в браузерное хранилище и сбрасывается при перезагрузке приложения; серверное ограничение остаётся обязательным.

## Работа с паролями

Введённые значения находятся в состоянии формы только во время её работы. Они очищаются при подтверждённом успехе, проблеме CSRF, неопределённом результате и размонтировании панели. Интерфейс не записывает пароли в адрес, `localStorage`, `sessionStorage` или журналы. Общий объект ошибки содержит метод и путь запроса, но не его тело.

Демонстрационный транспорт хранит изменённый пароль только в памяти вкладки. После обновления страницы восстанавливаются исходные демо-пароли. Сохранённый демо-сеанс содержит имя пользователя, а не пароль. Это модель для проверки интерфейса; она не реализует настоящие cookie-сессии и отзыв сессий на других устройствах.

## Проверка

Ниже сохранены результаты этапа разработки; они не заявляют повторную проверку текущей версии.

В `frontend/` выполните `npm run lint`, `npm test` и `npm run build`. Cookie-сессии и сохранение пароля проверяйте с настоящим API; порядок запуска интеграционных проверок описан в [README](../../README.md).

- Обычный пользователь меняет пароль и продолжает работу; его остальные сессии отзываются.
- Администратор не видит действие. Прямой запрос с верными данными возвращает `403 ADMIN_ACCOUNT_PROTECTED`, сохраняя пароль и сессии.
- Неверный текущий пароль подсвечивает поле; `429` показывает время ожидания.
- После потери ответа пароль не отправляется повторно автоматически; интерфейс предлагает восстановить сессию.
- Успешные login/me/change-password возвращают `timezone` для календаря приложения.
