# Telegram: команды и проверки

## Что показывает бот

Бот читает настоящий API под отдельным обычным пользователем. Данные не копируются в локальную базу. Финансовые команды и их кнопки работают только в чате из `CHAT_ID`. `/start` и `/menu` открывают главное меню; вне рабочего чата оно объясняет ограничение доступа и не содержит финансовых кнопок. `/help`, `/id` и `/site` доступны для помощи и первоначальной настройки. Аккаунты сотрудников создаёт администратор; регистрации в боте нет.

| Команда | Результат |
| --- | --- |
| `/start`, `/menu` | Главное меню с учётом доступа текущего чата |
| `/payments` | Неоплаченные периоды со сроком сегодня и в следующие шесть дней |
| `/overdue` | Все просроченные неоплаченные периоды, включая историю прекращённых правил |
| `/all` | Все сохранённые периоды: оплаченные и неоплаченные, без ограничения ближайшей неделей |
| `/summary` | Сводка текущего месяца по срокам платежей, отдельно для RUB, USD и EUR |
| `/help` | Помощь, ID чата и настройка ссылки на веб-панель |

Списки загружаются с сервера страницами по пять записей. Заголовок показывает диапазон и общее количество, например «6–10 из 23 · страница 2/5». Каждая запись содержит полное название, сумму с валютой, срок и статус. Кнопка под списком содержит номер и название; только подпись кнопки сокращается после 32 символов. «Предыдущие» и «Следующие» переключают страницы, «Обновить» перечитывает текущую страницу.

Кнопка карточки содержит UUID — постоянный идентификатор периода, а также вид списка и номер страницы. Даже если список изменился после появления кнопки, она открывает тот же период. Карточка перечитывает статус, число дней опоздания, дату оплаты и состояние регулярного правила из API. «К списку» возвращает к прежнему виду списка и странице; если последняя страница исчезла после изменения данных, бот выбирает последнюю доступную. «Обновить» в карточке заново запрашивает этот же UUID.

Переходы по кнопкам меню, списков, карточек и сводки редактируют текущее сообщение, чтобы не заполнять рабочий чат копиями. Введённая команда создаёт новый ответ. Если Telegram сообщает, что сообщение для редактирования не найдено или его нельзя изменить, бот отправляет новый ответ; ответ «сообщение не изменено» не создаёт копию. Другие ошибки Telegram не маскируются под успешное обновление.

Сводка использует `/payments/summary`, а не сумму видимой страницы. `planned` — весь план месяца, `paid` — оплачено, `unpaid` — не оплачено; `overdue` уже входит в `unpaid`. День и часовой пояс сообщает API. История и просрочка не зависят от часов компьютера, где запущен бот.

Команды списков и сводки только читают финансовые данные. Отдельная кнопка «Оплачено» подтверждает оплату от имени связанного сотрудника. «Открыть веб-панель» ведёт на настроенный `PANEL_URL`; там можно указать другую фактическую дату или отменить оплату. Если адрес не настроен, прямой кнопки нет, а `/site` объясняет, что нужно попросить администратора задать адрес.

## Напоминание и короткий сценарий сотрудника

Личная привязка для MFA работает отдельно: сотрудник начинает её в настройках сайта и открывает `/start` по одноразовой ссылке. Бот принимает такой запуск только в личном чате и передаёт проверенный Telegram ID по отдельному внутреннему маршруту. Код доставляет backend, а привязку завершает исходный браузер. Финансовые команды по-прежнему ограничены `CHAT_ID`. [Подключение, резервные коды и настройки сервера](account-security.md).

Автоматические напоминания отправляет единственный процесс `worker` через постоянную очередь: остановка и повторный запуск бота не создают второй планировщик. Напоминание содержит название, сумму, валюту, срок, «Открыть платёж» и «Оплачено». Первая кнопка использует `card:<UUID>` и открывает свежую карточку **новым сообщением**, сохраняя исходное напоминание. Старые сообщения остаются совместимыми: открытая из них карточка тоже предложит оплату неоплаченного периода.

Например, сотрудник открывает `/menu` → «Ближайшие 7 дней» → «2. Аренда офиса» → «Оплачено». Бот показывает актуальную сумму и сегодняшнюю дату в часовом поясе приложения. После отдельного подтверждения меняется только этот период, а в журнале указан сотрудник. Для другой даты или исправления нужно открыть панель. Оплаченный период исчезает из неоплаченных при обновлении списка.

## Как разрешается оплата в Telegram

Источник решения — исходное ТЗ «Invoice Keeper — напоминания о регулярных платежах»: на **страницах 7–8** обязательны напоминания в указанный чат минимум за три дня до срока, с названием, суммой, валютой и датой. Если платёж добавлен позже, напоминание нужно сразу. Повторная проверка не создаёт дубль; оплаченные периоды и прекращённые регулярные платежи больше не вызывают напоминаний. Кнопка «Оплачено» в Telegram перечислена на **странице 16** как дополнительная возможность, а не обязательное условие. Общая карта требований находится в [сверке с ТЗ](../development/spec-compliance.md).

Служебная учётная запись бота используется для чтения. Для изменения оплаты сервер отдельно определяет реального пользователя по Telegram ID. Обычный пользователь связывает аккаунт в «Безопасность → Оплата в Telegram»: подтверждает личность, открывает одноразовую ссылку в личном чате и завершает привязку в исходной вкладке. Это не включает MFA и не использует её привязку автоматически. Администратор задаёт свой личный ID через `ADMIN_TELEGRAM_ID` в `.env`; через панель этот аккаунт не изменяется.

Подтверждение действует пять минут, привязано к человеку, чату и снимку суммы/валюты/даты. Чужое нажатие, отменённый период, изменившаяся сумма или отозванный доступ отклоняются. После неизвестного результата можно повторить **ту же** кнопку: подтверждение хранится в БД, поэтому период не оплачивается второй раз и последующая отмена в панели не перезаписывается. «Отмена» закрывает конкретное подтверждение. [Контракт, границы доверия и сценарий](../api/telegram-payments.md).

Для подключения в корневом `.env` нужны `BOT_USERNAME` без `@`, общий для backend и bot `BOT_INTERNAL_TOKEN` (случайная строка минимум 32 символа), существующие `BOT_TOKEN` и `CHAT_ID`. Секрет можно сгенерировать локально: `python -c "import secrets; print(secrets.token_urlsafe(32))"`. Не меняйте уже используемый секрет без одновременного обновления обоих сервисов. `ADMIN_TELEGRAM_ID` необязателен; его получают командой `/id` в **личном** чате, а не в группе. Этот ID не должен быть одновременно привязан обычному пользователю.

Перед запуском новой версии примените `alembic upgrade head` (миграция `0012`) по [инструкции обновления](deployment.md), пересоберите и пересоздайте backend, frontend, bot и worker. `PANEL_URL` должен открываться с устройства пользователя, если нужна кнопка перехода к другой дате оплаты.

## Настройка и обновление

Порядок Docker-запуска приведён [ниже](#telegram-бот-в-docker). Для чтения нужны `API_BASE_URL`, `API_USERNAME`, `API_PASSWORD` и разрешённый `API_ORIGIN`. Используется cookie-сессия обычного пользователя; `API_TOKEN` не нужен. Публичная `/id` работает без API-настроек и помогает заполнить `CHAT_ID`.

После изменения Python-файлов или текстов пересоберите бот с `--build`. Модули бота, включая `bridge.py`, `mfa.py` и `payment_actions.py`, явно включены в Dockerfile и разрешённый build-контекст; рабочий `.env` в образ не копируется. После изменения общих `BOT_INTERNAL_TOKEN`, `BOT_USERNAME` или `CHAT_ID` пересоздайте backend и bot, для напоминаний — также worker. Переменные окружения процесса имеют приоритет над локальным `.env`.

## Проверка без отправки

`python telegram/smoke.py` печатает локальные примеры для трёх валют, длинного названия и HTML-символов. API и Telegram для этого не нужны. `python telegram/smoke.py --backend --dry-run --limit 3` читает первые три периода из настроенного API и тоже только печатает текст. `--from-api` — синоним `--backend`, `--kind overdue` выбирает просрочку, `--limit` принимает 1–100.

Отправка возможна только с явным `--send`. Она обходит очередь и не сохраняет подтверждение доставки, поэтому повторная ручная отправка может продублировать сообщение. Для обычной эксплуатации используйте `worker`, не запускайте smoke по расписанию.

Полная проверка команд: `python scripts/checks/check_bot_api.py --timezone Asia/Tokyo`. Она создаёт отдельную PostgreSQL-базу, настоящий API и случайные учётные данные; рабочий `.env` не использует. Telegram заменён локальным адаптером в закрытой Docker-сети. Проверяются страницы, права чата, карточки по UUID, сводка, восстановление сессии и smoke. Временные ресурсы удаляются после проверки. Это проверка интеграции приложения, а не подтверждение доставки через настоящий Telegram.

При проверке UX 24 октября 2026 года этот сценарий успешно прошёл с новым ботом: переходы меню → список → карточка → прежняя страница, обновление, длинные названия с HTML-символами и emoji, устаревшие кнопки, исчезнувшая последняя страница и пустой список после настоящих API-оплат. Однократный HTTP 503 воспроизводится локальным прокси; «Повторить» сохраняет контекст и снова обращается к настоящему API. Проверяется, что каждое нажатие подтверждается до загрузки данных, а истёкшее нажатие не вызывает финансовых запросов.

Отдельно успешно выполнен `python scripts/checks/check_reminder_worker.py --timezone Asia/Tokyo`: кнопка напоминания содержит UUID реально отправленного периода, оплаченные и прекращённые платежи пропускаются, после перезапуска нет повторных отправок. Оба сценария используют изолированные базы и локальный транспорт Telegram; новых unit-тестов не добавляли. Вид сообщений в настоящем клиенте Telegram и доставка в реальный чат этим прогоном не проверялись.

Данные кнопки ограничены [64 байтами в Telegram Bot API](https://core.telegram.org/bots/api#inlinekeyboardbutton). Навигация передаёт UUID, вид списка и страницу; подтверждение оплаты — случайный одноразовый токен, привязанный сервером к пользователю. Пароли, суммы и названия в callback не передаются. Содержимое старого сообщения не считается текущим статусом оплаты.

## Если что-то не работает

- Финансовая команда недоступна: сравните `/id` с `CHAT_ID` и пересоздайте контейнер после изменения настройки.
- API не настроен или вход не удался: проверьте адрес, обычного пользователя, пароль и `API_ORIGIN`. Имя `backend` доступно внутри Docker; с компьютера используйте адрес сайта с `/api/v1`.
- Сервер ограничил попытки входа: дождитесь `Retry-After`; перезапуск бота не снимает лимит.
- В списке, карточке или сводке показана ошибка API: «Повторить» повторяет тот же запрос; «Главное меню» остаётся доступным. У карточки сохраняется и «К списку».
- Статус в старом сообщении устарел: нажмите «Обновить». Если период больше недоступен, вернитесь к списку и обновите его; бот не подменяет отсутствующий UUID другой записью.
- Кнопка недействительна или Telegram больше не предоставляет исходное сообщение: откройте `/menu`. Если сообщение доступно, но его нельзя редактировать, бот использует описанный выше ответ новым сообщением.
- Список пуст: это результат выбранного режима, а не обязательно отсутствие всех платежей. «Ближайшие 7 дней» не включает оплаченные и просроченные периоды; они доступны через главное меню.
- Неверная дата или неполная сводка: проверьте общий `APP_TIMEZONE` и состояние worker. При `503 PERIODS_NOT_READY` дождитесь восстановления периодов и повторите запрос.

### Telegram-бот в Docker

Бот запускается вместе с остальными сервисами. Для отдельного запуска:

```sh
docker compose up -d --build --no-deps bot
docker compose logs --tail=100 -f bot
```

`Ctrl+C` завершает просмотр логов, а контейнер продолжает работать. `docker compose stop bot` останавливает приём команд, а `docker compose stop worker` — обработку напоминаний. Для отдельного запуска фронта или базы `BOT_TOKEN` не нужен; `POSTGRES_PASSWORD` нужен для проверки общего Compose-файла.

Откройте личный чат с ботом или добавьте его в нужную группу и вызовите `/help`, затем `/id`. В группе с несколькими ботами используйте `/id@имя_бота`. Запишите полученный ID в `CHAT_ID` в `.env`. Команда `/id` только показывает ID, сама настройку не сохраняет. После изменения `BOT_TOKEN` или `CHAT_ID` пересоздайте процессы: `docker compose up -d --no-deps --force-recreate backend bot worker`. Обычный `restart` не перечитывает окружение; база уже должна работать и иметь актуальные миграции.

Для команды `/site` и прямой кнопки «Открыть веб-панель» укажите в корневом `.env` необязательный `PANEL_URL` — полный `http://` или `https://` адрес интерфейса без встроенного логина/пароля и пробельных символов, доступный с устройства, где открыт Telegram. После изменения пересоздайте контейнер бота командой выше; при пустом или некорректном значении бот сообщит, что ссылка не настроена.

`CHAT_ID` задаёт адрес напоминаний и единственный чат для финансовых команд и кнопок. В остальных чатах данные закрыты, `/start` и `/menu` показывают ограниченное меню, а `/help`, `/id` и `/site` остаются доступны. Пустой `CHAT_ID` не мешает получить `/id`. Переход по ссылке на веб-панель сам по себе не авторизует пользователя на сайте.

Для списков нужен отдельный обычный пользователь API:

1. Войдите администратором в веб-панель и создайте пользователя, например `telegram_bot`, с отдельным паролем.
2. В корневом `.env` задайте его `API_USERNAME` и `API_PASSWORD`. Не используйте учётную запись администратора.
3. В Docker оставьте `API_BASE_URL=http://backend:8000/api/v1`. `API_ORIGIN` должен совпадать с одним из `ALLOWED_ORIGINS`: по умолчанию Compose использует `http://localhost:<FRONTEND_PORT>`. Это адрес сайта без пути, а не адрес внутреннего API. `API_TIMEOUT` — от 1 до 60 секунд, по умолчанию 10.
4. После изменения настроек выполните `docker compose up -d --build --no-deps --force-recreate bot`.

Бот входит через обычный `/auth/login`, хранит cookie-сессию в памяти процесса и использует её для чтения списков, карточек и сводки. Bearer-токен не нужен. Истёкшую сессию клиент обновляет одним повторным входом; неверный пароль и ограничение попыток не вызывают бесконечные входы. После смены пароля сервисного пользователя обновите `API_PASSWORD` и пересоздайте `bot`. Эти настройки не передаются во фронтенд. Без API-настроек публичные команды и доставка worker продолжают работать.

При запуске Python на компьютере вместо Docker используйте доступный с компьютера `API_BASE_URL`, например `http://localhost:8080/api/v1`; имя `backend` доступно только внутри Docker. Для production с `SESSION_COOKIE_SECURE=true` адрес API должен использовать HTTPS: браузерная Secure-cookie не передаётся клиентом по внутреннему HTTP.

Сервис `bot` получает команды через polling и читает данные API. Автоматические напоминания отправляет только `worker`: он читает PostgreSQL и обрабатывает постоянную очередь; `API_USERNAME` и `API_PASSWORD` ему не нужны. Worker не вызывает `getUpdates`, поэтому с ботом они используют один токен без второго polling.

Сервис не публикует порты и не подключается к PostgreSQL. Он получает настройки Telegram, адрес сайта, часовой пояс и данные отдельного пользователя API; рабочий `.env` и пароль базы в образ не копируются. Контейнер работает без root и с файловой системой только для чтения. Проверки `getUpdates` в healthcheck нет, чтобы не конкурировать с основным polling. [Ограничения polling в aiogram](https://docs.aiogram.dev/en/v3.16.0/dispatcher/long_polling.html).

После изменения `telegram/bot.py`, `telegram/api.py`, `telegram/smoke.py`, `telegram/reminders.py`, `telegram/formatting.py`, `telegram/features.py`, `telegram/texts.json` или зависимостей повторите запуск с `--build`. Новые файлы нужны и в списке `COPY` Dockerfile, и среди разрешённых файлов `telegram/.dockerignore`: разрешение файла в контексте сборки само по себе не добавляет его в образ. Окружение этого сервиса описано в `telegram/pyproject.toml` и `telegram/uv.lock`: Python `3.12.15`, uv `0.13.5`, aiogram `3.31.0`, python-dotenv `1.2.4`. Образы Python и uv закреплены по digest, зависимости устанавливаются через `uv sync --locked`. Это отдельный набор для контейнера бота; зависимости API остаются у бэкендера. При изменении библиотек обновляйте манифест и lockfile вместе, затем проверяйте сборку.

Если бот не отвечает, проверьте `docker compose ps -a` и `docker compose logs --tail=100 bot`:

- `Set BOT_TOKEN in .env` — заполните токен и пересоздайте контейнер.
- `Unauthorized` или ошибка формата токена — проверьте токен от `@BotFather`.
- `Conflict` — тот же токен уже использует другой запущенный бот; остановите второй процесс.
- Ошибка соединения — проверьте доступ компьютера и Docker к Telegram.
- Списки не настроены — заполните `API_BASE_URL`, `API_USERNAME`, `API_PASSWORD` и разрешённый `API_ORIGIN`; после изменения `.env` пересоздайте `bot`.
- Ошибка входа API — проверьте обычного пользователя и пароль; если сбросили пароль в панели, обновите его в `.env`.
- Ограничение попыток API — дождитесь срока `Retry-After`; частые перезапуски не снимают серверный лимит.
- Команда работает только в заданном чате — сравните `/id` с `CHAT_ID`, затем пересоздайте `bot` и `worker` после исправления настройки.

Не публикуйте вывод `docker compose config` или `docker inspect` с окружением: в нём могут быть секреты. Для проверки синтаксиса используйте `docker compose config --quiet`.

### Проверка Telegram-команд без отправки сообщений

После сборки образа бота можно проверить форматирование примеров и чтение настоящего API:

```sh
docker compose run --rm --no-deps bot python smoke.py --dry-run
docker compose run --rm --no-deps bot python smoke.py --backend --dry-run --limit 3
```

Первой команде API не нужен. Вторая выполняет HTTP-запросы к API и требует готового backend и настроенного обычного пользователя, но не отправляет сообщения в Telegram. Для просроченных добавьте `--kind overdue`; `--limit` допускает 1–100 записей. Переданные процессу переменные окружения имеют приоритет над `.env`.

По умолчанию smoke только показывает тексты, даже без `--dry-run`; `--from-api` — синоним `--backend`. Для реальной отправки в `CHAT_ID` требуется явный флаг `--send`, например `docker compose run --rm --no-deps bot python smoke.py --backend --send --limit 3`. Флаги `--send` и `--dry-run` взаимоисключающие. Это ручная проверка, которая обходит очередь и не сохраняет подтверждение отправки: повторный запуск может отправить те же данные снова. Не используйте её как планировщик; обычными напоминаниями управляет `worker`. Smoke не запускается автоматически вместе с контейнерами.

Интеграционная проверка с отдельной БД и настоящим API:

```sh
python scripts/checks/check_bot_api.py
```

Она не использует рабочий `.env` и не отправляет сообщения в настоящий Telegram. Для уже собранных образов доступны `--image BACKEND_IMAGE_ID` и `--bot-image BOT_IMAGE_ID`. Для проверки другого бизнес-пояса добавьте `--timezone Asia/Tokyo`. Эта же проверка запускается в CI **Backend Compose**.

## Локальный запуск из каталога проекта

Compose остаётся общим в корне. Для запуска Telegram-модуля без контейнера выполните из корня репозитория:

```sh
uv sync --locked --directory telegram
uv run --locked --project telegram python -X utf8 telegram/smoke.py --dry-run
uv run --locked --project telegram python -X utf8 telegram/bot.py
```

Бот и smoke читают корневой `.env`; создавать копию `telegram/.env` не нужно. Переменные окружения процесса имеют приоритет. Перед запуском бота или smoke с `--backend` задайте в этом терминале доступный с компьютера адрес API и Origin. В PowerShell:

```powershell
$env:API_BASE_URL = 'http://localhost:8080/api/v1'
$env:API_ORIGIN = 'http://localhost:8080'
```

В Bash используйте `export API_BASE_URL=http://localhost:8080/api/v1` и `export API_ORIGIN=http://localhost:8080`. Если порт сайта другой, замените его в обоих значениях. Origin должен входить в `ALLOWED_ORIGINS` backend. При локальном запуске Compose не подставляет эти настройки. Значения передаются только процессам этого терминала; корневой `.env` можно оставить настроенным для контейнеров. Данные обычного пользователя `API_USERNAME` и `API_PASSWORD` по-прежнему берутся из `.env`.

В контейнере рабочий каталог — `/app`, поэтому команды остаются `python bot.py` и `python smoke.py`. На компьютере пути начинаются с `telegram/`. Запуск как `python -m telegram.bot` не предусмотрен.

Зависимости и границы сервиса описаны в [README Telegram](../../telegram/README.md); устройство общего запуска — в [карте репозитория](../development/repository-structure.md).
