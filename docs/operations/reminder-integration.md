# Интеграция платежей и доставки: участники 1 и 2

## Готовность и границы

Участник 1 реализовал пакет `app.delivery`: очередь, worker, Telegram-адаптер и
разрешение неизвестного результата оператором. Участник 2 интегрировал реальные
платёжные модели, адаптер `app.services.payment_source:make_source` и таблицу
очереди в ревизию `0003` поверх `0002`. Интеграционные тесты используют
PostgreSQL и тестового отправителя; реальные сообщения Telegram не отправляются.

Цепочка миграций — `0002 → 0003 → 0004 → 0005 → 0006 → 0007 → 0008`, текущий head — `0008`. Ревизия
`0004` исправляет default статуса периода, `0005` добавляет журнал действий,
`0006` — подтверждения оплаты; `0007` — MFA, `0008` — заявки сотрудников. Эти ревизии не меняют очередь. Worker не создаёт
таблицы при старте. В Compose он запускается отдельным сервисом `worker` после
миграций, вместе с остальными приложениями.

## Ответственность и жизненный цикл периода

Участник 1 отвечает за очередь, время готовности, запуск фонового обработчика,
повторные попытки и сохранение результата Telegram. Участник 2 отвечает за
правила платежей, генерацию периодов, оплату и адаптер `PaymentSource`. Планировщик
и повторные попытки не нужно дублировать в сервисе платежей или Telegram-модуле.
Этот документ описывает согласованный протокол интеграции.

Состояние доставки хранится **на период**, а не одним флагом в правиле платежа:
оплата ноября не запрещает напоминание за октябрь или декабрь. `period.id`
(`occurrence_id` в очереди) должен оставаться прежним при повторной генерации,
оплате и отмене оплаты. Пересоздание периода с новым UUID обходит защиту от дублей.
Прекращение правила сохраняет периоды и историю доставки; `sent` и `unknown`
нельзя удалять или сбрасывать при изменении оплаты.

При создании неоплаченного периода сервис платежей вызывает постановку задания
в той же транзакции, не дожидаясь обхода worker. Если время уже наступило, задание
готово сразу после commit; фактическую отправку делает ближайший цикл worker.
Восстановление очереди worker — дополнительная страховка после перезапуска.

## Общая транзакция и порядок блокировок

Общий протокол очереди, worker и платёжных сервисов для создания/восстановления
периодов, изменения оплаты и прекращения правила:

1. Одна `AsyncSession`, одна открытая транзакция.
2. `await app.delivery.locking.lock_payments(db)` выполняет именно
   `pg_advisory_xact_lock(0x494E56, 2)` с **двумя integer-аргументами**.
3. `SELECT ... FOR UPDATE` строки правила.
4. Периоды, затем строки очереди, когда нужны дополнительные блокировки.
5. `ensure_payment_periods`, методы адаптера и операции очереди не коммитят.
   Commit/rollback делает вызывающий платёжный сервис или worker.

Это транзакционная блокировка, а не session-level lock; она освобождается при
commit/rollback. Повторное получение в той же транзакции допустимо. Существующая
блокировка администрирования пользователей использует другой ключ и пространство
ключей и не пересекается с `(0x494E56, 2)`.

`ensure_payment_periods(db, payment_id, today, through=None)` подходит по интерфейсу.
При вызове worker передаёт `today` как календарную дату в `APP_TIMEZONE`. Сервис восстанавливает
пропущенные периоды и ближайший будущий период по общим правилам участника 2.
Worker не реализует второй календарный генератор.

## Постановка задания: фактический интерфейс

```python
from app.delivery.locking import lock_payments
from app.delivery.queue import enqueue_payment_reminder

async with db.begin():
    await lock_payments(db)
    # Участник 2: заблокировать строку правила и создать/восстановить периоды.
    # Новые ORM-объекты должны быть добавлены в ту же db.
    await db.flush()  # назначить ID объектов до передачи аргументов функции
    delivery_id = await enqueue_payment_reminder(
        db,
        payment_id=rule.id,
        occurrence_id=period.id,
        due_date=period.due_date,
    )
```

Функция делает `flush`, но не делает commit, не отправляет Telegram и не открывает
свою сессию. Очередь сохраняется или откатывается вместе с правилом и периодами.
Вызывающий код уже держит общую блокировку и блокировку правила. UUID объектов
должны быть назначены к моменту вызова. При повторе возвращается тот же ID.

В БД `UNIQUE(occurrence_id)`: одно задание на период. Повторная постановка сохраняет
ID, попытки, подтверждение Telegram и конечные состояния. При изменении часового
пояса пересчитывается расписание только ожидающих заданий, как описано ниже.
Постановка для того же occurrence_id с другим payment_id запрещена.

Время `scheduled_at` = 00:00 в настроенном `APP_TIMEZONE` в день `due_date - 3 календарных дня`,
затем перевод в UTC, тип `TIMESTAMPTZ`. По умолчанию используется `Europe/Moscow`.
Например, в этом поясе срок 10 ноября 2026 →
6 ноября 2026, 21:00 UTC. `available_at` первоначально равно scheduled_at:
если оно уже в прошлом, задание доступно сразу после commit. Новые неоплаченные
исторические периоды следуют тому же правилу.

### Смена часового пояса существующего стенда

`APP_TIMEZONE` принимает имя из базы IANA. Неизвестное имя отклоняется при запуске.
Чтобы API и обработчик не работали одновременно с разными календарями:

1. Выполните `docker compose stop backend worker`.
2. Измените общий `APP_TIMEZONE` в корневом `.env`.
3. Выполните `docker compose up -d --no-deps --force-recreate backend worker bot`.
4. Перезагрузите открытые страницы: login/me передадут браузеру новый `timezone`.

Даты `due_date` и `paid_on` остаются календарными датами и не переписываются.
При очередном обходе активных неоплаченных периодов recovery сверяет расписание:
у `pending` и `retry` пересчитывается `scheduled_at`. Если обычное задание
`pending` ожидало только календарного срока (`available_at == старое scheduled_at`),
его `available_at` переносится вместе с расписанием. Для `retry` и для `pending`
с отдельной отсрочкой (`available_at != старое scheduled_at`) используется
`available_at = max(старое available_at, новое scheduled_at)`. Поэтому смена пояса
не сокращает backoff/Retry-After, отсрочку после `requeue_failed` или
`resolve_unknown`, а также время следующей проверки оплаченного периода.
Сравниваются сохранённые значения до обновления расписания.

`sent`, `unknown`, `failed`, `in_flight` и `cancelled` не сбрасываются. Уже
оплаченный период не отправляется; при последующей отмене оплаты его расписание
проверяется снова. Полный обход может занять несколько циклов, если активных
правил больше размера страницы worker.

Бот получает календарный пояс из ответа входа API, поэтому после смены настройки
его пересоздают вместе с остальными процессами. Это обновляет cookie-сессию и
полученный `timezone`. Подтверждённые сообщения повторно не отправляются из-за
смены пояса; неизвестный результат по-прежнему требует решения оператора.

## Таблица и состояния доставки

Схема: `app.delivery.schema.deliveries` (`reminder_deliveries`).
`delivery_metadata` — ссылка на общую `Base.metadata`, в которой зарегистрированы
пользователи, сессии, платежи и очередь. Поля:

- UUID `id`, `payment_id`, уникальный `occurrence_id`.
- UTC `scheduled_at`, `available_at`, `created_at`, `updated_at`.
- `status`, `attempt_count`, UUID `attempt_id`, UTC `lease_until`.
- UTC `sent_at`, `telegram_message_id`, безопасный `last_error_code` без текста
  исключений, Telegram-токенов и содержимого сообщения.

| Состояние | Значение и переходы |
|---|---|
| `pending` | Ожидает срока и проверки условий. Оплаченный период остаётся pending с отложенной проверкой; отмена оплаты снова допускает проверку. |
| `in_flight` | Попытка зарезервирована и **уже закоммичена до сети**. Истёкшая незавершённая попытка переходит только в unknown. |
| `retry` | Telegram явно отказал во временной отправке (например, 429); повтор после Retry-After и backoff, с повторной проверкой условий. |
| `sent` | Telegram вернул подтверждённый положительный message_id, он сохранён вместе с sent_at. Автоматически никогда не сбрасывается. |
| `unknown` | Таймаут, разрыв соединения, 5xx, неизвестная ошибка или процесс прервался в in_flight. Автоматического повтора нет. |
| `cancelled` | Правило прекращено или правило/период отсутствует. Новых отправок не будет. |
| `failed` | Явный постоянный отказ Telegram либо исчерпан лимит безопасных повторов (по умолчанию 5). После исправления причины оператор может явно вернуть задание в pending командой requeue-failed. |

Для `sent` ограничение БД требует `sent_at` и `telegram_message_id`.
При повторной постановке и любых изменениях оплаты sent остаётся sent.
Если Telegram принял запрос, но процесс не смог сохранить подтверждение в БД,
сохраняется in_flight, затем unknown. Гарантии exactly-once на границе PostgreSQL /
Telegram нет; неизвестный исход нельзя автоматически считать неотправкой.

Оператор подтверждает результат через `resolve_unknown(db, delivery_id,
outcome="sent", telegram_message_id=...)` либо `outcome="not_sent"` **после проверки,
что отправки не было**. Метод не коммитит. Во втором случае запись становится
pending, а worker снова проверяет правило, оплату и время. Нельзя этим методом
сбрасывать sent.

После установки схемы доступны команды из корня проекта. `JOB_UUID` — ID записи
очереди, `TELEGRAM_MESSAGE_ID` — подтверждённый ID сообщения в целевом чате:

```sh
docker compose run --rm worker python -m app.delivery.cli list --status unknown
docker compose run --rm worker python -m app.delivery.cli resolve JOB_UUID --sent TELEGRAM_MESSAGE_ID
docker compose run --rm worker python -m app.delivery.cli resolve JOB_UUID --not-sent
```

### Восстановление failed после исправления настройки

Например, при неправильном `CHAT_ID` Telegram явно отклонил запрос, и задание
получило `failed`. После исправления причины:

1. Исправить `CHAT_ID` / `BOT_TOKEN` в корневом `.env` и пересоздать процессы:
   `docker compose up -d --no-deps --force-recreate worker bot`.
   Одного изменения `.env` или `docker compose restart` недостаточно.
2. Из корня проекта найти задания и повторно поставить выбранное:

   ```sh
   docker compose run --rm worker python -m app.delivery.cli list --status failed
   docker compose run --rm worker python -m app.delivery.cli requeue-failed JOB_UUID
   ```

Команда работает с одним ID и принимает только `failed` без `sent_at` и
`telegram_message_id`. Она возвращает ту же запись в `pending`, очищает данные
незавершённой попытки/ошибку и обнуляет `attempt_count` для новой серии попыток.
Это счётчик текущей серии, а не пожизненный счётчик отправок. ID, исходное время
напоминания и связь с периодом сохраняются. `available_at` становится максимумом
текущего времени и прежнего значения, чтобы не обойти ещё действующий Retry-After.

Команда сама ничего не отправляет: worker заново проверяет оплату, активность и
срок. Если период уже оплачен или правило прекращено, отправки не будет.
`requeue_failed(db, delivery_id)` использует общую транзакционную блокировку и
атомарное обновление строки; commit делает вызывающий код. Миграция для команды
не нужна.

Для `unknown`, `sent`, `in_flight`, `pending`, `retry`, `cancelled` и неизвестного
ID команда завершается ошибкой без изменения записи. Повтор команды после
успешной постановки тоже отклоняется. `resolve` по-прежнему работает только с
`unknown` после ручной проверки результата; автоматического повтора unknown нет.

## Worker и адаптер участника 2

`DeliveryWorker(session_factory, source, sender)` принимает `PaymentSource` из
`app.delivery.contracts`. Все методы адаптера используют переданную AsyncSession
и не коммитят:

```python
active_payment_ids(db, *, after: UUID | None, limit: int) -> Sequence[UUID]
lock_rule(db, payment_id: UUID) -> bool  # FOR UPDATE; True, если правило существует и активно
ensure_payment_periods(db, payment_id, today, through=None) -> None
unpaid_occurrences(db, payment_id) -> Sequence[PaymentSnapshot]
occurrence(db, payment_id, occurrence_id) -> PaymentSnapshot | None
```

`PaymentSnapshot` содержит `payment_id`, `occurrence_id`, `due_date`, `title`,
`amount: Decimal`, `currency`, `is_active`, `is_paid`. Проверка оплаты/активности
читает текущее состояние, а не кеш. `active_payment_ids` возвращает UUID по
возрастанию, строго после `after`, максимум `limit`.

Каждый цикл восстанавливает одну страницу активных правил через общий генератор,
проверяет и ставит задания для неоплаченных периодов, затем обрабатывает готовую
очередь. Страницы обходятся до конца; новый процесс начинает обход заново.
Восстановление периодов и постановка заданий для каждого правила атомарны.

Перед сетью worker получает общую advisory-блокировку, строку правила, повторно
читает период и проверяет: правило активно, период не оплачен, время наступило,
попытка по-прежнему принадлежит этому worker. Проверка и ограниченная по времени
отправка выполняются в одной транзакции под блокировкой. Поэтому прекращение
правила, успевшее закоммититься, исключает отправку. Если отправка уже началась,
прекращение ждёт её завершения и не может отменить уже принятый Telegram запрос.

Цена строгого протокола: общая блокировка удерживается во время сети, по умолчанию
до 20 секунд. Это сериализует отправки и кратковременно задерживает изменения
платежей. Для небольшой командной системы принято как начальная реализация;
ослаблять блокировку без нового согласованного протокола нельзя.

`TelegramSender` делает одну попытку через aiogram. В существующие `telegram/bot.py` и
`telegram/reminders.py` участника Telegram изменения не вносятся; bot polling и доставка
очереди — разные процессы. Worker не вызывает массовую рассылку.

В Compose сервис `worker` использует backend-образ и его entrypoint. Команда
сервиса — `python -m app.delivery.cli run --adapter app.services.payment_source:make_source`;
интервал передаётся через `--poll-seconds` из `REMINDER_POLL_SECONDS` (по умолчанию
30 секунд). Это пауза между циклами, а не отдельное расписание отправок.

После миграций worker входит в общий `docker compose up -d`; отдельно его можно
запустить командой `docker compose up -d --build worker`. Он ждёт готовности
PostgreSQL, но не применяет миграции. Перед обновлением схемы остановите оба
процесса: `docker compose stop backend worker`. После успешной миграции запускайте
`backend` и `worker` вместе.

Настройки берутся из корневого `.env`. EntryPoint собирает `DATABASE_URL` из
`POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`; для отправки нужны `BOT_TOKEN`
и `CHAT_ID`. `APP_TIMEZONE` и `TZ` совпадают с настройками API. Имя часового пояса
проверяется по базе IANA при запуске; неизвестное имя не подменяется Москвой. Общий класс
Settings также проверяет настройки окружения, cookie и разрешённых Origin;
worker получает их согласованно с API. После изменения `.env` нужен
`docker compose up -d --no-deps --force-recreate worker`, а после изменения токена
или чата — также пересоздание `bot`. Worker не использует Telegram polling,
поэтому не конкурирует с ботом за `getUpdates`.

Команды `compose run --rm worker ...` заменяют обычную команду сервиса: `list`,
`resolve` и `requeue-failed` не запускают второй постоянный worker и не отправляют
сообщения сами. Они используют тот же entrypoint и подключение к БД. Для просмотра
ошибок: `docker compose logs --tail=100 worker`. Состояние `running` и тишина в
логах не доказывают доставку: проверяйте записи `sent`, `failed`, `unknown` и чат.

Для разработки без Docker сохранён запуск из каталога `backend`:

```sh
uv run --locked python -m app.delivery.cli run --adapter app.services.payment_source:make_source
```

Нужны `DATABASE_URL`, `BOT_TOKEN`, `CHAT_ID` в окружении процесса / `backend/.env`.
Интервал задаётся CLI-флагом `--poll-seconds`; Compose-переменная
`REMINDER_POLL_SECONDS` сама по себе на этот способ запуска не влияет.

## Миграции и общие метаданные

1. Ревизия `0003` продолжает `0002`; `0001` и `0002` не изменяются.
2. DDL `reminder_deliveries` сохранён непосредственно в миграции после создания
   таблиц платежей. Последующие изменения очереди оформляются новыми ревизиями.
3. Таблица очереди регистрируется в общей `Base.metadata`, которую использует
   Alembic:

   ```python
   from app import models
   from app.delivery.schema import delivery_metadata

   target_metadata = delivery_metadata
   ```

4. `reminder_deliveries.payment_id` ссылается на `recurring_payments.id`, а
   `occurrence_id` — на `payment_occurrences.id`; обе связи используют `RESTRICT`,
   чтобы сохранять историю доставки и платежей. Ограничения называются
   `fk_reminder_deliveries_payment_id_recurring_payments` и
   `fk_reminder_deliveries_occurrence_id_payment_occurrences`.
   `UNIQUE(occurrence_id)` оставляет не более одного задания на период.
5. После объединения и изменений схемы повторить PostgreSQL runner: создание
   чистой БД, переход до `head`, откат и повторное обновление, `alembic check`
   и существующие проверки платежей и доставки.

## Доставка напоминаний: интеграция с платежами


Пакет `backend/app/delivery` содержит очередь, worker и одну попытку отправки в
Telegram. Ревизия `0003` добавляет очередь и платёжные таблицы; адаптер
`app.services.payment_source:make_source` подключает worker к платежам. Порядок
блокировок и обработка неизвестного исхода описаны в
[документе интеграции](reminder-integration.md).

Сервис `worker` включён в общий `docker compose up`. Он использует тот же образ,
зависимости и платёжный адаптер, что backend; отдельный планировщик не нужен.
При старте проверяется наличие таблицы очереди, но миграции не применяются.
Для отдельного запуска после подготовки БД:

```sh
docker compose up -d --build worker
docker compose logs --tail=100 -f worker
```

Настройки берутся из корневого `.env`: подключение собирается из `POSTGRES_DB`,
`POSTGRES_USER`, `POSTGRES_PASSWORD`, для доставки нужны `BOT_TOKEN` и `CHAT_ID`.
`APP_TIMEZONE` и `TZ` передаются с тем же часовым поясом, что API; по умолчанию это `Europe/Moscow`.
`REMINDER_POLL_SECONDS` задаёт паузу между циклами: по умолчанию 30 секунд,
допустимо положительное целое. Уже наступившее напоминание отправляется ближайшим
циклом; время зависит также от очереди и ответа Telegram. После изменения настроек
выполните `docker compose up -d --no-deps --force-recreate worker`.

Состояние очереди можно посмотреть без остановки worker:

```sh
docker compose run --rm worker python -m app.delivery.cli list --status sent
docker compose run --rm worker python -m app.delivery.cli list --status failed
docker compose run --rm worker python -m app.delivery.cli list --status unknown
```

Эти команды используют те же настройки БД и не отправляют сообщения. `failed`
означает подтверждённый отказ или исчерпанные безопасные повторы. `unknown` означает,
что исход отправки неизвестен; автоматического повтора нет. Команды исправления
и проверки перед повтором описаны в [документе интеграции](reminder-integration.md).

Если контейнер перезапускается с `Delivery command failed (ValueError)`, проверьте
`BOT_TOKEN`, `CHAT_ID` и миграции; при `ValidationError` — настройки общего backend,
включая часовой пояс и production-настройки cookie/Origin. Неположительный интервал
даёт ошибку аргументов. `Delivery cycle failed (...)` в работающем контейнере требует
проверки БД, схемы и очереди: `running` не означает успешную доставку. Отсутствие
новых строк в логах может быть нормальным — успешные циклы CLI не печатает.

Без Docker команда остаётся прежней: из `backend/` выполнить
`uv run --locked python -m app.delivery.cli run --adapter app.services.payment_source:make_source`.
Для этого способа нужны `DATABASE_URL`, `BOT_TOKEN` и `CHAT_ID` в `backend/.env`;
интервал можно задать флагом `--poll-seconds 30`. Проверки очереди используют
тестового отправителя и не отправляют сообщения в настоящий Telegram.

Проверка worker в Docker без настоящей рассылки:

```sh
python scripts/checks/check_reminder_worker.py
```

Скрипт собирает worker и поднимает отдельный временный проект с тестовой БД,
не используя рабочий `.env`. Он проверяет запуск, наступившие и будущие сроки,
пропуск оплаченных и прекращённых платежей, восстановление периода и отсутствие
повторной подтверждённой отправки после перезапуска. Telegram заменён внутри
закрытой Docker-сети; временные контейнеры и БД удаляются после проверки.
Готовый образ можно передать через `--image IMAGE_ID`, чтобы не собирать его повторно.
