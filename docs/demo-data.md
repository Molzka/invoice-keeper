# Тестовые данные и демонстрация Invoice Keeper

Для демонстрации используйте отдельный Compose-проект с PostgreSQL и реальным API. Данные вводятся через веб-панель; редактировать строки БД вручную не требуется.

Для первого прохода нужна новая демонстрационная БД. Если вы повторяете показ с нуля, выберите новое имя проекта и БД в приведённых настройках и командах, не удаляя прежние данные. У старого набора уже могут быть подтверждённые напоминания, которые повторно не отправляются.

## Подготовить отдельный стенд

Не добавляйте демонстрационные платежи в рабочую базу. Из корня репозитория создайте отдельный файл настроек, сохранив существующий, если он уже есть:

```powershell
if (-not (Test-Path .env.demo)) { Copy-Item .env.example .env.demo }
```

Заполните `.env.demo` своими значениями. Это локальный файл, исключённый из Git. В примере ниже угловые скобки обозначают места для замены, а не готовые пароли:

```dotenv
POSTGRES_DB=invoice_keeper_demo
POSTGRES_USER=invoice_keeper_demo
POSTGRES_PASSWORD='<отдельный-длинный-пароль-БД>'
POSTGRES_PORT=55433
FRONTEND_PORT=8082
FRONTEND_API_MODE=real
APP_TIMEZONE=Europe/Moscow
ADMIN_USERNAME=demo_admin
ADMIN_PASSWORD='<отдельный-пароль-администратора>'
BOT_TOKEN='<токен-демонстрационного-бота>'
CHAT_ID=<числовой-ID-демонстрационного-чата>
```

Остальные настройки оставьте из `.env.example`. Можно выбрать другой свободный порт и другой пояс IANA, например `Asia/Tokyo`. Часовой пояс выбирайте до ввода данных; правила изменения существующего стенда описаны в [документе доставки](../backend/docs/reminder-integration.md#смена-часового-пояса-существующего-стенда). Если переменные с такими именами уже заданы в терминале, они имеют приоритет над `--env-file`: используйте терминал без настроек другого стенда.

Для живой демонстрации используйте отдельный Telegram-чат и бота. Если `CHAT_ID` неизвестен, запустите только `bot` с теми же `--env-file` и `-p`, вызовите `/id` в нужном чате и перенесите ответ в файл. Публичная команда работает без API-учётной записи. Один токен должен обслуживаться только одним процессом polling. Подробная настройка — в [README](../README.md#telegram-бот-в-docker).

Во всех командах этого сценария сохраняйте **оба** аргумента: `--env-file .env.demo -p invoice-keeper-demo`. Имя проекта отделяет контейнеры, сеть и том от рабочего стенда; отдельное имя БД само по себе этого не делает.

Если этот демонстрационный проект уже запускался, до подготовки данных остановите его worker: `docker compose --env-file .env.demo -p invoice-keeper-demo stop worker`. Он должен оставаться остановленным до указанного ниже шага, чтобы успеть отметить подписку оплаченной.

```sh
docker compose --env-file .env.demo -p invoice-keeper-demo config --quiet
docker compose --env-file .env.demo -p invoice-keeper-demo build backend worker frontend bot
docker compose --env-file .env.demo -p invoice-keeper-demo up -d --wait postgres
docker compose --env-file .env.demo -p invoice-keeper-demo run --rm backend alembic upgrade head
docker compose --env-file .env.demo -p invoice-keeper-demo run --rm backend python -m app.cli create-admin
docker compose --env-file .env.demo -p invoice-keeper-demo up -d --wait backend frontend
```

Создавать администратора нужно только для новой БД. Повторный запуск команды не меняет его пароль. Откройте [демонстрационную панель](http://localhost:8082), войдите `demo_admin`.

## Ввести три платежа и обычного пользователя

Здесь **D** — сегодняшняя календарная дата в `APP_TIMEZONE`. Она может отличаться от даты устройства, на котором открыт браузер. Значение `timezone` можно проверить в ответе `/api/v1/auth/me` через инструменты разработчика браузера. Все относительные даты перед вводом замените конкретными `YYYY-MM-DD`.

В разделе «Пользователи» создайте `demo_user` с отдельным паролем. В разделе «Регулярные платежи» добавьте три правила с периодичностью «Ежемесячно»:

| Название | Сумма | Валюта | Первый срок | Для чего нужен |
|---|---:|---|---|---|
| Аренда офиса · демо | 45000.00 | RUB | D + 1 день | Напоминание для поздно добавленного платежа |
| Облачный сервер · демо | 29.00 | USD | D − 1 день | Просрочка, исправление даты и следующий период |
| Рабочая подписка · демо | 12.00 | EUR | D | Оплата до отправки и прекращение повторения |

Например, если D = `2026-10-24`, сроки — `2026-10-25`, `2026-10-23`, `2026-10-24`. Этот пример не нужно копировать как постоянные даты: при следующем показе пересчитайте их относительно нового D.

Суммы перечислены в формате API. В форме допустима также десятичная запятая; валюты выбираются отдельно. Не складывайте 45000 RUB, 29 USD и 12 EUR в одно число. Сводка группирует валюты и считает только периоды выбранного диапазона. На границе месяца D − 1 или D + 1 попадёт в другой месяц, поэтому текущая месячная сводка может содержать не все три примера.

Откройте второй браузер или приватное окно и войдите `demo_user`. Найдите текущий период подписки и отметьте «Оплачено» с датой D. Работайте с периодом, а не с правилом повторения: следующий месяц должен сохранить собственный статус.

## Получить напоминание и показать защиту от дублей

После заполнения `BOT_TOKEN` и `CHAT_ID` запустите демонстрационные процессы:

```sh
docker compose --env-file .env.demo -p invoice-keeper-demo up -d --no-deps --force-recreate bot worker
```

Эта команда включает реальные отправки в указанный демонстрационный чат. Для аренды срок уже ближе трёх дней, поэтому её задание готово сразу и отправляется ближайшим циклом worker. Для неоплаченного вчерашнего сервера действует catch-up: пропущенный срок не теряется. Ожидаются сообщения с названием, суммой, валютой и сроком по аренде и серверу. По оплаченной подписке сообщения быть не должно.

Посмотрите подтверждения и ошибки без дополнительной отправки:

```sh
docker compose --env-file .env.demo -p invoice-keeper-demo run --rm worker python -m app.delivery.cli list --status sent
docker compose --env-file .env.demo -p invoice-keeper-demo run --rm worker python -m app.delivery.cli list --status failed
docker compose --env-file .env.demo -p invoice-keeper-demo run --rm worker python -m app.delivery.cli list --status unknown
```

Подождите несколько циклов: по умолчанию пауза между ними 30 секунд плюс время обработки. Повторных сообщений по тем же периодам быть не должно. `running` у контейнера не доказывает доставку: нужны сообщение в чате и сохранённый `sent` с `telegram_message_id`. Если токен или сеть недоступны, используйте [памятку доставки](../backend/docs/reminder-integration.md), а не ручную отправку через smoke.

Этот короткий сценарий показывает немедленную готовность поздно добавленного платежа. Для наблюдения планового порога заранее создайте дополнительный платёж со сроком D + 4 и проверьте отправку после наступления D + 1, 00:00 в поясе приложения. Отсутствие сообщения до этого времени и одна отправка после него проверяют границу трёх календарных дней. Не меняйте часы системы ради демонстрации.

Без настоящих Telegram-настроек можно выполнить `python scripts/check_reminder_worker.py`: он использует отдельную временную БД и локальную замену Telegram. Успех этой проверки подтверждает внутренний путь доставки, но не получение сообщения в настоящем чате.

## Отметить оплату, исправить дату и показать следующий период

В окне `demo_user`:

1. Отметьте аренду оплаченной с датой D. Досрочная оплата допустима; срок D + 1 не меняется.
2. Откройте вчерашний период сервера: до оплаты он просрочен на один день. Отметьте оплату датой D — это поздняя оплата.
3. Исправьте фактическую дату сервера на D − 1. Признак поздней оплаты исчезнет, исходный срок останется D − 1.
4. Отмените оплату этого периода: статус станет «Не оплачено», фактическая дата очистится. Затем снова отметьте оплату датой D − 1.
5. В истории сервера найдите следующий месячный период. У него другой ID, собственный срок и статус «Не оплачено». Вчерашняя оплата останется в истории. При фильтрации по датам включите следующий месяц; она может быть вне текущей сводки.

Следующий период сервера появляется независимо от оплаты предыдущего. Число месяца берётся из первого срока; если такого числа нет, используется последний день месяца, а исходное число сохраняется для последующих месяцев. Например: 31 января → 28/29 февраля → 31 марта.

У обычного пользователя нет действий создания и прекращения правил или управления пользователями. Его собственный пароль менять можно. У администратора действия смены собственного пароля нет; прямой запрос `/api/v1/auth/change-password` с корректными cookie, Origin и CSRF возвращает `403 ADMIN_ACCOUNT_PROTECTED`. Такие проверки API проводите с учётными записями этого демонстрационного стенда через его [Swagger](http://localhost:8082/api/v1/docs).

## Прекратить правило и проверить сохранность

Чтобы отдельно проверить запрет напоминания для прекращённого неоплаченного периода:

1. Остановите только worker: `docker compose --env-file .env.demo -p invoice-keeper-demo stop worker`.
2. В окне `demo_user` отмените оплату подписки. Теперь её текущий период неоплачен, и напоминание по нему ещё не отправлялось.
3. В окне администратора прекратите повторение подписки. Существующий период и история остаются видимыми.
4. Запустите worker: `docker compose --env-file .env.demo -p invoice-keeper-demo up -d --no-deps worker`. После нескольких циклов сообщения о подписке быть не должно. Подтверждения по аренде и серверу не должны измениться.

Проверьте обычный перезапуск всего стенда:

```sh
docker compose --env-file .env.demo -p invoice-keeper-demo stop
docker compose --env-file .env.demo -p invoice-keeper-demo up -d --wait
```

Обновите панель и при необходимости войдите снова. Правила, оплаты, исправленная дата, следующий период и прекращённая подписка должны сохраниться. Новых сообщений по уже подтверждённым периодам быть не должно. Для завершения показа достаточно `stop`: данные останутся в томе демонстрационного проекта. Не применяйте `down -v`, если этот набор нужен для следующего показа.

## Если результат отличается

| Симптом | Что проверить |
|---|---|
| Видны готовые данные до ручного ввода | `FRONTEND_API_MODE=real`, пересборку frontend и выбранный порт; mock хранит примеры только в памяти вкладки |
| Отметка оплаты не сохраняется после обновления | Реальный режим API, успешный ответ PATCH и отсутствие ошибки в панели |
| Не приходит напоминание | `worker`, актуальные миграции, `CHAT_ID`, `BOT_TOKEN`, затем состояния `failed`/`unknown` |
| `unknown` | Результат отправки неизвестен; сначала проверить чат, затем использовать операторскую команду из памятки. Автоматически повторять нельзя |
| Срок или «сегодня» отличается | `APP_TIMEZONE` сервера и `timezone` в login/me; после смены настройки пересоздать процессы и обновить страницу |
| Следующий период не виден | Активность правила, worker, фильтры истории и диапазон дат; прошлая просрочка не должна останавливать генерацию |
| После таймаута хочется повторить создание | Сначала проверить список: первый запрос мог сохраниться |

**Термины:** правило задаёт ежемесячный расход; период — отдельный срок и отметка оплаты; очередь хранит одну доставку на период; catch-up восстанавливает работу после пропуска; `sent` означает сохранённое подтверждение Telegram, `unknown` — отсутствие достоверного результата.
