# Соответствие ТЗ и проверка правил

Источник требований — исходный кейс «Invoice Keeper — напоминания о регулярных платежах», 18 страниц. Обязательная часть находится на страницах 4–14, сценарий показа — на странице 15, дополнительные возможности — на странице 16. Контракт API уточняет формат запросов, но не отменяет ограничения исходного ТЗ.

## Что исправлено при повторной сверке

**Ответы с финансовыми данными.** К списку регулярных платежей и итогам добавлен `Cache-Control: no-store`, как у остальных закрытых маршрутов. Это запрещает HTTP-кешу сохранять ответы; авторизация по-прежнему проверяется сервером на каждом запросе.

**Недопустимые входные данные.** Нулевой символ в названии платежа и фильтрах журнала теперь отклоняется как ошибка валидации `422`, до обращения к PostgreSQL. Слишком глубокий JSON и число с чрезмерным количеством цифр в запросе ссылки на чек дают `400 INVALID_JSON`, а не внутреннюю ошибку `500`. Ограничение размера тела запроса сохраняется. Экспорт OpenAPI обновлён вместе с правилами валидации.

**Самые ранние даты.** API допускает ISO-даты начиная с года `0001`. Вычитание трёх дней или перевод такого напоминания в UTC раньше вызывали переполнение. В этом случае очередь использует минимальный представимый UTC-момент: напоминание уже наступило и обрабатывается обычными правилами очереди. Это не меняет дату срока или правило ежемесячного повторения.

**Длина Unicode-строк.** JavaScript по умолчанию считает элементы UTF-16, Python — кодовые точки. Поэтому четыре emoji могли проходить клиентскую проверку минимальных восьми символов, но отклоняться API. Проверка формы и демонстрационный транспорт теперь считают кодовые точки, как сервер. Визуально составной символ всё ещё может состоять из нескольких кодовых точек; это не подсчёт нарисованных значков.

**Запоздавшие ответы авторизации.** Если старый запрос возвращает `401` после нового успешного входа, он больше не очищает новую сессию. Аналогичная проверка защищает восстановление CSRF. Сам старый запрос остаётся неуспешным; действие автоматически не повторяется. После успешного входа прежнее уведомление о завершении сессии исчезает.

**Открытая карточка в полночь.** При смене календарного дня или пояса карточка заново получает серверный статус. Введённая пользователем дата оплаты сохраняется. Дата, предложенная при открытии карточки, также не сдвигается молча: подтверждение относится к выбранному дню.

## Границы проверки

Интеграционные проверки работают с настоящими FastAPI, Nginx и PostgreSQL. Проверка worker подменяет только внешний Telegram локальным HTTP-сервисом. Она подтверждает постановку, формат, подавление повторов и обработку ответов, но не доставку в настоящий Telegram-чат. Для приёмки с реальным ботом выполните [сценарий демонстрации](../operations/demo-data.md) с отдельным чатом.

В браузерном сценарии полуночи часы браузера управляемые, а вычисляемые поля ответа периода изменяются для следующего дня. Это проверяет обновление открытой формы и сохранение черновика. Серверные правила дат проверяются отдельно на настоящей БД; браузерный сценарий не переводит часы сервера.

Дополнительная часть ТЗ не является обязательной: календарь и журнал действий уже есть; бюджет и подтверждения оплаты доступны через API, но отдельных экранов для них нет. В календаре нет дневных валютных итогов, журнал не содержит событий входа и выхода. Кнопка оплаты внутри Telegram и дополнительные каналы SMTP/webhook не реализованы. Эти возможности нельзя считать завершёнными только по наличию смежных маршрутов или компонентов.

## Как разбирать сбои

- `422` при вводе — посмотрите `error.details`: это ошибка конкретного поля, а не отказ базы данных.
- Неожиданный экран входа — проверьте `/auth/me`, срок сессии и cookie; запоздавший ответ старого запроса не должен завершать более новую сессию.
- Разные даты на устройствах — сравните `timezone` из `/auth/me` с `APP_TIMEZONE`, затем обновите сессию. Локальный пояс устройства не определяет срок платежа.
- Нет напоминания — сначала проверьте статус периода, активность правила и состояние очереди, затем логи worker. Повторный запуск не должен заново отправлять уже подтверждённое напоминание.
- Красная проверка в PR — откройте конкретный шаг GitHub Actions и его артефакты. Успех старой ревизии не подтверждает текущие изменения.
