# Заявки сотрудников и дополнительная защита входа

## Решение и границы

ТЗ требует вход по логину и паролю, закрытые данные и создание обычных пользователей администратором. Заявка не является аккаунтом: доступ появляется только после одобрения администратором. Это заменяет прежнее решение обходиться без заявок. MFA добровольна, не меняет роль и набор функций, но после подключения обязательна при каждом новом входе. Защищённый аккаунт администратора через панель не изменяется; настройка MFA доступна роли `user`.

Обычные напоминания продолжают работать с `CHAT_ID`. Персональные коды отправляются только в личный чат. Служебный пользователь API бота и личная привязка сотрудника независимы; обхода MFA для служебного входа нет.

## Пользовательские сценарии

1. «Запросить доступ»: логин, пароль и повтор, имя или сообщение, локальная CAPTCHA. Ответ объясняет ожидание решения. Дубликаты не создаются, существование аккаунта публично не раскрывается.
2. Администратор видит список заявок и принимает либо отклоняет их. Одобрение атомарно создаёт только `user`; пароль уже хеширован. После решения хеш из заявки удаляется. Решение сохраняется в журнале.
3. Вход без подключённой MFA сразу создаёт сессию. Вход с MFA создаёт только короткий запрос подтверждения, который не даёт доступа к API данных. После кода появляется обычная сессия.
4. В «Безопасности» сотрудник может подключить приложение по QR-коду или Telegram по ссылке. Предложение подключения можно пропустить. Первое подключение подтверждается паролем; добавление, замена и отключение при уже включённой MFA требуют также текущего фактора или резервного кода.
5. Telegram-ссылка одноразовая. Бот принимает её только в личном чате и передаёт числовой ID из Telegram Update. На сайте показывается найденный аккаунт; сотрудник вводит присланный код в исходном браузере. Ручного ввода ID нет.
6. При первом подключении выдаются десять одноразовых резервных кодов. Повторное получение означает генерацию нового набора с отзывом старого. При потере всех факторов автоматического обхода защиты нет.

## Контракт API

Пути ниже имеют префикс `/api/v1`, кроме внутреннего маршрута бота. Изменяющие запросы авторизованного браузера требуют существующие Origin и CSRF. Секретные ответы имеют `Cache-Control: no-store`.

### Заявки

- `GET /registration/challenge` — свежая CAPTCHA ALTCHA, срок пять минут, одноразовая серверная запись. Проверка локальная, без стороннего сервиса.
- `POST /registration/requests` — `{username,password,password_confirm,message,altcha}`; `202 {status:"pending",message}`. Такой же безопасный ответ возвращается для уже занятого логина или активной заявки, новая запись при этом не создаётся.
- `GET /registration/requests?status=pending&limit=20&offset=0` — только admin; `{items,total,limit,offset}`. Элемент: `{id,username,message,status,created_at,reviewed_at,reviewed_by,decision_note}`; паролей и хешей нет.
- `POST /registration/requests/{id}/approve` — только admin, пустой JSON; возвращает элемент с `status:"approved"`.
- `POST /registration/requests/{id}/reject` — только admin, `{note?:string}`; возвращает элемент с `status:"rejected"`.

### Вход

- `POST /auth/login` сохраняет прежний успешный ответ для аккаунта без MFA. Для MFA возвращает `{mfa_required:true,methods:["totp"|"telegram"|"recovery"],csrf_token,expires_at}` и отдельную HttpOnly cookie незавершённого входа.
- `POST /auth/mfa/telegram/send` — `{}`, CSRF незавершённого входа; `{sent:true,retry_after:60}`. Не меняет доступные способы и не продлевает запрос входа.
- `POST /auth/mfa/verify` — `{method,code}`, CSRF незавершённого входа; обычный `AuthResponse` после успешной проверки.
- `POST /auth/mfa/cancel` — `{}`, CSRF незавершённого входа; `204` и удаление запроса.

### Настройки безопасности

- `GET /auth/security` — `{can_manage,mfa_enabled,methods,available_methods,telegram,recovery_codes_remaining}`. `methods` содержит подключённые `totp`/`telegram`; `telegram` — `null` либо `{id:string,username:string|null,display_name:string}`. Недоступная конфигурация не отключает уже включённую MFA.
- `POST /auth/security/telegram/send-code` — `{password}`, код текущему привязанному аккаунту для подтверждения изменения; `{sent:true,retry_after:60}`.
- `POST /auth/security/reauth` — `{password,method?:"totp"|"telegram"|"recovery",code?:string}`; `{expires_at}`. Создаёт одноразовое серверное разрешение на изменение, привязанное к сессии и версии защиты, срок пять минут.
- `POST /auth/security/totp/setup` — `{}`, потребляет разрешение; `{setup_id,secret,otpauth_uri,expires_at}`.
- `POST /auth/security/totp/confirm` — `{setup_id,code}`; `{security,recovery_codes?}`.
- `POST /auth/security/telegram/setup` — `{}`, потребляет разрешение; `{setup_id,link,expires_at}`.
- `GET /auth/security/telegram/setup/{id}` — только исходная сессия; `{status:"waiting"|"claimed",account:telegram|null,expires_at}`.
- `POST /auth/security/telegram/confirm` — `{setup_id,code}`; `{security,recovery_codes?}`.
- `POST /auth/security/factors/{method}/remove` и `/auth/security/disable` — `{}`, потребляют разрешение; `{security}`. Последний удалённый фактор отключает MFA и отзывает резервные коды.
- `POST /auth/security/recovery/regenerate` — `{}`, потребляет разрешение; `{security,recovery_codes}`.
- `POST /internal/v1/telegram-auth/claim` — вне публичного Nginx `/api`; отдельный `Authorization: Bearer BOT_INTERNAL_TOKEN`, JSON `{token,telegram_id,chat_id,username,display_name}`. Положительные числовые ID должны совпадать. Ответ `{accepted:true}` без кода. Backend сам доставляет код личному чату. Код подтверждения не является ответом на этот запрос.

## Защитные условия

- Argon2 для паролей; Fernet для TOTP-секретов с отдельным `MFA_ENCRYPTION_KEY`. PyOTP проверяет стандартный TOTP; использованный временной шаг повторно не принимается.
- Одноразовые токены — 32 случайных байта, в БД только хеш. Короткие коды проверяются через HMAC с серверным ключом; резервные коды имеют не менее 128 бит случайности и хранятся в виде хешей.
- Незавершённый вход и Telegram-код живут пять минут, настройка — десять минут. На запрос подтверждения не более пяти неверных кодов; повторная отправка не раньше 60 секунд и не более пяти раз за 15 минут на пользователя.
- Все лимиты и одноразовое потребление хранятся в PostgreSQL; блокировки исключают двойное использование при параллельных запросах. Смена пароля, логина или защиты делает старые запросы недействительными. Изменение факторов отзывает остальные сессии.
- Заявки и CAPTCHA ограничиваются по IP; повторная активная заявка запрещена также индексом БД. CAPTCHA не заменяет модерацию и лимиты: локальное доказательство работы повышает стоимость автоматической отправки.
- Telegram-профиль доверяется только боту с отдельным секретом. `@username` служит подписью, ключ привязки — числовой ID. Один Telegram-аккаунт нельзя одновременно привязать к двум пользователям.
- Ошибка доставки, отсутствие ключа или потерянный фактор не дают вход по одному паролю. Ошибки и аудит не содержат пароли, QR-секреты, одноразовые ссылки или коды.

## Порядок реализации и проверки

1. Миграция `0007`: MFA, запросы подтверждения, резервные коды и версия защиты; двухэтапная авторизация и настройки.
2. Миграция `0008`: заявки, одноразовые CAPTCHA, действия аудита; создание пользователя после решения администратора.
3. Личная deep-link команда бота, отдельный внутренний клиент, конфигурация контейнеров.
4. Формы входа и заявки, раздел безопасности, модерация в существующей панели; локальные QR и CAPTCHA без отправки секретов сторонним сайтам.
5. Сборка, типы, линтеры, существующие тесты. Новые unit-тесты не создаются. Реальные API/PostgreSQL/Dispatcher и браузерные сценарии проверяют отказ до MFA, пропуск подключения, повторные/истёкшие коды, две сессии, подмену чата, повтор заявки, гонку одобрения и сохранность существующих данных после миграций.
6. Просмотр на desktop/mobile, уточнение интерфейса, обновление OpenAPI и пользовательской вики.
