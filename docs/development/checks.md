# Проверки приложения

Все команды `scripts/checks/check_*.py` выполняются из корня репозитория. Подробности изоляции стендов приведены ниже.

## Проверка Docker

GitHub Actions запускает независимые проверки в каждом PR и после обновления `main`:

- **Frontend / Compose** — типы, lint, production-сборка, запуск Nginx и HTTP-проверка. Дополнительно проверяются запуск без root, файловая система только для чтения и отсутствие Node.js, исходников и `.env` в каталоге сайта.
- **PostgreSQL / Compose** — запуск PostgreSQL, вход с паролем, сохранение записи после пересоздания контейнера, резервное копирование и восстановление в новую БД.
- **Telegram / Compose** — сборка образа, загрузка библиотек и модулей бота без сети, работа без root и с файловой системой только для чтения, отсутствие `.env` в образе и понятный отказ старта без токена. Настоящий токен не используется; доставку сообщений эта проверка не подтверждает.
- **Backend / PostgreSQL** — установка зависимостей из lockfile, Ruff, существующие тесты авторизации и пользователей, создание администратора из `.env`, защита от повторного создания, применение и откат миграций на временной PostgreSQL.
- **Backend / Compose, Nginx and browser** — сборка API и интерфейса, миграции и создание администратора командами Compose, настоящий вход через Nginx, cookie и CSRF, управление пользователями, повторное подключение после пересоздания API и браузерные сценарии ниже.

Каждая проверка использует собственный временный Compose-проект и удаляет его после завершения; проверка базы также удаляет свой том. Рабочий `.env` и локальная база для CI не нужны. Результаты видны во вкладке **Checks** в PR; при ошибке откройте соответствующую проверку — в ней будут шаг с ошибкой и логи контейнера.

### Браузерная проверка авторизации

В **Backend Compose** Playwright запускает Chromium и проходит настоящие React-формы через Nginx, FastAPI и PostgreSQL. Это дополняет HTTP-проверки: исправный маршрут API ещё не гарантирует, что кнопка интерфейса отправляет правильный запрос. Проверка использует `FRONTEND_API_MODE=real` и страницу `/#users`; сценарии авторизации и управления пользователями не зависят от платёжных данных.

Два сценария в `frontend/e2e/auth.spec.ts` проверяют:

- неверный и верный пароль, восстановление сессии после обновления и в новой вкладке, выход с потерей доступа в обеих вкладках;
- создание пользователя, ограничения его прав в отдельном браузерном контексте, смену логина с сохранением пароля, смену пароля и удаление; после изменений проверяется отзыв старой сессии, после смены пароля и удаления — отказ во входе с прежними данными.

Действия выполняются кнопками и формами, а результат подтверждается экраном и статусом настоящего API. Демонстрационный режим такую проверку не проходит. Тесты идут по очереди, без автоматических повторов; у каждого прогона своя база и случайные пароли. Telegram-бот не запускается.

Для ручного запуска на GitHub откройте **Actions → Backend Compose → Run workflow** и выберите ветку. После завершения скачайте артефакт `auth-e2e-report`: в нём HTML-отчёт, а при сбое — скриншот и `trace.zip` с последовательностью действий. Артефакт хранится семь дней. Trace может содержать тестовые пароли и cookie; используйте только одноразовые учётные записи и не публикуйте отчёт из рабочего окружения.

Для разработки тестов нужны Node.js `24.22.1`, npm `11.6.2` и заранее поднятый отдельный тестовый стенд с миграциями, администратором и пустым списком обычных пользователей. Подготовка такого стенда описана шагами [.github/workflows/backend-compose.yml](../../.github/workflows/backend-compose.yml); рабочая база для этого не подходит. Из папки `frontend`:

```sh
npm ci
npx playwright install chromium
npm run test:e2e
npm run test:e2e:report
```

Перед `test:e2e` задайте переменные окружения: `E2E_BASE_URL` — адрес тестового Nginx, например `http://127.0.0.1:8081`; `E2E_ADMIN_USERNAME` и `E2E_ADMIN_PASSWORD` — данные администратора именно тестового стенда. В PowerShell переменная задаётся через `$env:E2E_BASE_URL = 'http://127.0.0.1:8081'`. Файлы `.env` тесты автоматически не читают. На Linux для установки системных библиотек браузера используйте `npx playwright install --with-deps chromium`.

Если браузер не установлен, повторите команду установки. Тайм-аут ожидания `/auth/me` часто означает запуск демо вместо `real` или недоступное API; 403 требует проверки `ALLOWED_ORIGINS`, а 429 — новой одноразовой базы либо ожидания сброса лимита входа. Не отключайте ограничения ради зелёной проверки. Локальные отчёты в `frontend/playwright-report/` и `frontend/test-results/` исключены из Git и Docker-контекста.

## Проверка backend

Из каталога `backend`:

```powershell
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked python scripts/test_postgres.py
```

Тестовый скрипт подключается к серверу из `DATABASE_URL`, создаёт временную базу с уникальным именем, применяет миграции, запускает тесты и проверяет соответствие моделей схеме. Отдельно запускает настоящую CLI-команду с временным `.env`: проверяет создание администратора, сохранение прежнего пароля при повторном вызове и отказ с пустым паролем. Рабочий `.env` не изменяется. Затем проверяет откат и повторное применение миграции и удаляет созданную тестовую базу. Пользователю PostgreSQL для этого нужно право `CREATEDB`; пользователь официального локального Docker-образа имеет его по умолчанию.

Если права создавать базы нет, подготовьте отдельную одноразовую базу с суффиксом `_test`, укажите её URL в переменной окружения `TEST_DATABASE_URL` и выполните `uv run --locked pytest -q`. Тесты очищают данные только в выбранной тестовой базе. Без `TEST_DATABASE_URL` интеграционные проверки завершаются ошибкой настройки, а не пропускаются. Скрипт выше задаёт эту переменную автоматически. В тестах также проверяется переход с `0001` на `0002` с существующими пользователями и сессиями.
