# Проверки приложения

Все команды `scripts/checks/check_*.py` выполняются из корня репозитория. Подробности изоляции стендов приведены ниже.

## Проверка Docker

GitHub Actions запускает независимые проверки в каждом PR и после обновления `main`:

- **Frontend / Compose** — типы, lint, production-сборка, запуск Nginx и HTTP-проверка. Дополнительно проверяются запуск без root, файловая система только для чтения и отсутствие Node.js, исходников и `.env` в каталоге сайта.
- **PostgreSQL / Compose** — запуск PostgreSQL, вход с паролем, сохранение записи после пересоздания контейнера, резервное копирование и восстановление в новую БД.
- **Telegram / Compose** — сборка образа, загрузка библиотек и модулей бота без сети, работа без root и с файловой системой только для чтения, отсутствие `.env` в образе и понятный отказ старта без токена. Настоящий токен не используется; доставку сообщений эта проверка не подтверждает.
- **Backend / PostgreSQL** — установка зависимостей из lockfile, Ruff, существующие тесты авторизации и пользователей, создание администратора из `.env`, защита от повторного создания, применение и откат миграций на временной PostgreSQL.
- **Backend / Compose, Nginx and browser** — сборка API и интерфейса, миграции и создание администратора командами Compose, настоящий вход через Nginx, cookie и CSRF, управление пользователями, повторное подключение после пересоздания API и браузерные сценарии ниже.

Каждая проверка использует собственный временный Compose-проект и удаляет его после завершения; проверка базы также удаляет свой том. Рабочий `.env` и локальная база для CI не нужны. Результаты видны во вкладке **Checks** в PR; при ошибке откройте соответствующую проверку — в ней будут шаг с ошибкой и логи контейнера.

### Проверка правил из ТЗ через HTTP

В **Backend Compose** скрипт `scripts/checks/check_payment_rules.py` работает через Nginx с настоящей PostgreSQL. Он создаёт отдельного пользователя и три регулярных платежа, проверяет високосный февраль, независимость периодов, оплату и отмену, исправление просрочки, суммы по валютам, права и защиту администратора. Дополнительно проверяются `no-store`, отклонение нулевого символа и обработка некорректного JSON при работе с чеком.

Для ручного запуска на отдельном стенде задайте `ADMIN_USERNAME` и `ADMIN_PASSWORD` его администратора, затем выполните из корня:

```sh
uv run --locked --project backend python scripts/checks/check_payment_rules.py http://127.0.0.1:8081
```

Скрипт использует стандартную библиотеку Python и принимает только локальный адрес. Окружение backend обеспечивает базу часовых поясов `tzdata`, нужную в Windows; в CI Linux используется системная база и `python3`. Скрипт не читает `.env` и не обращается к Telegram. После проверки созданные правила прекращаются, пользователь и чек удаляются; история периодов остаётся до удаления одноразовой БД. Worker с настоящим токеном на этом стенде запускать нельзя: исторические платежи намеренно создаются с наступившим сроком. Матрица требований и границы доказательств — в [документе соответствия ТЗ](spec-compliance.md).

### Заявки сотрудников и MFA

`scripts/checks/check_access_security.py` создаёт отдельные PostgreSQL, API и экземпляр Dispatcher бота. Проверяются настоящие HTTP-запросы, блокировки и миграции: одноразовая CAPTCHA, запрет входа до одобрения, одновременное одобрение одной заявки, права администратора, настройка TOTP и Telegram, незавершённый вход без доступа к API, повторное использование кодов, CSRF, привязка к браузеру, истечение сроков, лимиты, смена пароля и восстановление после перезапуска API.

Доставка личных кодов проходит через локальный HTTP-приёмник вместо Telegram. Dispatcher принимает синтетические Telegram Update и проверяет запрет привязки из группы, от бота и с несовпадающим ID. Так проверяется вся цепочка приложения без настоящих токенов и сообщений сотрудникам; доступность Telegram и работу реального клиента этот прогон не доказывает.

Из корня репозитория передайте точные ID уже собранных образов, полученные через `docker image inspect`:

```sh
python scripts/checks/check_access_security.py --image sha256:<backend-image-id> --bot-image sha256:<bot-image-id> --timezone Asia/Tokyo
```

Теги образов не принимаются: иначе другой build мог бы незаметно заменить проверяемый код. Скрипт использует только собственные контейнеры, сеть и том; после завершения удаляет их. Он не читает рабочий `.env`, не меняет рабочие лимиты и не очищает существующую базу. В CI этот шаг входит в **Backend Compose**.

### Браузерная проверка авторизации

В **Backend Compose** Playwright запускает Chromium и проходит настоящие React-формы через Nginx, FastAPI и PostgreSQL. Это дополняет HTTP-проверки: исправный маршрут API ещё не гарантирует, что кнопка интерфейса отправляет правильный запрос. Проверка использует `FRONTEND_API_MODE=real` и страницу `/#users`; сценарии авторизации и управления пользователями не зависят от платёжных данных.

Два сценария в `frontend/e2e/auth.spec.ts` проверяют:

- неверный и верный пароль, восстановление сессии после обновления и в новой вкладке, выход с потерей доступа в обеих вкладках;
- создание пользователя, ограничения его прав в отдельном браузерном контексте, смену логина с сохранением пароля, смену пароля и удаление; после изменений проверяется отзыв старой сессии, после смены пароля и удаления — отказ во входе с прежними данными.

Действия выполняются кнопками и формами, а результат подтверждается экраном и статусом настоящего API. Демонстрационный режим такую проверку не проходит. Тесты идут по очереди, без автоматических повторов; у каждого прогона своя база и случайные пароли. Telegram-бот не запускается.

Перед браузерным шагом CI создаёт отдельного `browser_admin` штатной CLI-командой. HTTP-проверки и браузер используют разные счётчики попыток входа по имени пользователя, поэтому вместе не превышают лимит 10 входов за 15 минут. Рабочие лимиты не меняются, счётчики не очищаются. При ручном запуске используйте свежую тестовую учётную запись или дождитесь окончания окна ограничения.

`frontend/e2e/spec-regressions.spec.ts` дополняет эти сценарии проверкой Unicode-паролей и названий, запоздавшего настоящего `401` после повторного входа, а также обновления открытой карточки в полночь без потери введённой даты. Для последнего сценария управляются часы браузера и вычисляемые поля ответа; серверные часы не меняются. Скриншоты при ширине 1440 и 390 пикселей прикладываются к отчёту и при успешном прогоне.

`frontend/e2e/access-security.spec.ts` проходит форму заявки с настоящей ALTCHA, решение администратора, вход одобренного сотрудника, добровольную настройку TOTP с QR-кодом, второй шаг входа и резервный код. Этот сценарий также сохраняет desktop/mobile-снимки. Для него у тестового backend должен быть отдельный `MFA_ENCRYPTION_KEY`; CI генерирует его на один прогон. Настоящий Telegram для браузерных проверок не требуется.

Для ручного запуска на GitHub откройте **Actions → Backend Compose → Run workflow** и выберите ветку. После завершения скачайте артефакт `auth-e2e-report`: в нём HTML-отчёт, а при сбое — скриншот и `trace.zip` с последовательностью действий. Артефакт хранится семь дней. Trace может содержать тестовые пароли и cookie; используйте только одноразовые учётные записи и не публикуйте отчёт из рабочего окружения.

Привязка Telegram для оплаты проверяется в том же браузерном сценарии с настоящим API. Для тестового стенда задаются фиктивные `BOT_USERNAME`, `CHAT_ID` и отдельный `BOT_INTERNAL_TOKEN`; `E2E_BACKEND_CONTAINER` содержит ID его backend-контейнера. Браузерный тест вызывает приватный claim внутри этого контейнера через Docker и отказывается работать при `APP_ENV != test`. Nginx не публикует приватный маршрут. `check_access_security.py` дополнительно запускает `telegram_payment_probe.py`: реальный Dispatcher и HTTP проверяют личную привязку, чужой чат/пользователя, потерянный ответ, повтор кнопки, отмену в панели и отвязку. Настоящие Telegram-сообщения не отправляются.

Для разработки тестов нужны Node.js `24.22.1`, npm `11.6.2` и заранее поднятый отдельный тестовый стенд с миграциями, администратором и пустым списком обычных пользователей. Подготовка такого стенда описана шагами [.github/workflows/backend-compose.yml](../../.github/workflows/backend-compose.yml); рабочая база для этого не подходит. Из папки `frontend`:

```sh
npm ci
npx playwright install chromium
npm run test:e2e
npm run test:e2e:report
```

Перед `test:e2e` задайте переменные окружения: `E2E_BASE_URL` — адрес тестового Nginx, например `http://127.0.0.1:8081`; `E2E_ADMIN_USERNAME` и `E2E_ADMIN_PASSWORD` — данные администратора именно тестового стенда. В PowerShell переменная задаётся через `$env:E2E_BASE_URL = 'http://127.0.0.1:8081'`. Файлы `.env` тесты автоматически не читают. На Linux для установки системных библиотек браузера используйте `npx playwright install --with-deps chromium`.

Если браузер не установлен, повторите команду установки. Тайм-аут ожидания `/auth/me` часто означает запуск демо вместо `real` или недоступное API; 403 требует проверки `ALLOWED_ORIGINS`, а 429 — новой одноразовой базы либо ожидания сброса лимита входа. Не отключайте ограничения ради зелёной проверки. Локальные отчёты в `frontend/playwright-report/` и `frontend/test-results/` исключены из Git и Docker-контекста.

## Проверка backend

Из каталога `backend`:

```powershell
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked python scripts/test_postgres.py
```

Тестовый скрипт подключается к серверу из `DATABASE_URL`, создаёт временную базу с уникальным именем, применяет миграции и проверяет соответствие моделей схеме. Отдельно запускает настоящую CLI-команду с временным `.env`: проверяет создание администратора, сохранение прежнего пароля при повторном вызове и отказ с пустым паролем. Рабочий `.env` не изменяется. Откат и повторное применение миграций выполняются до функциональных тестов: они создают историю, которую нельзя откатить без потерь. После тестов скрипт снова сверяет модели и схему и удаляет созданную БД. Запрет потери истории при downgrade проверяется отдельным миграционным тестом. Пользователю PostgreSQL для этого нужно право `CREATEDB`; пользователь официального локального Docker-образа имеет его по умолчанию.

Если права создавать базы нет, подготовьте отдельную одноразовую базу с суффиксом `_test`, укажите её URL в переменной окружения `TEST_DATABASE_URL` и выполните `uv run --locked pytest -q`. Тесты очищают данные только в выбранной тестовой базе. Без `TEST_DATABASE_URL` интеграционные проверки завершаются ошибкой настройки, а не пропускаются. Скрипт выше задаёт эту переменную автоматически. В тестах также проверяется переход с `0001` на `0002` с существующими пользователями и сессиями.
